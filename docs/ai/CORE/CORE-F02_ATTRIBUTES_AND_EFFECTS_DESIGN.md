## 1 问题与动机

总纲把「属性 base/current 分离 + 全量重聚合、不做逆运算」写成了本设计最值得迁移的一条契约（C6），但契约只说明了结论，没有说明**这条结论在一份可执行的数值核里长什么样**。参考宿主没有 Gameplay Ability System，这一段必须完全自建；自建时最容易发生的不是「算不出来」，而是「算出来的值无法解释」。

需要被解决的五个具体问题：

1. **current 的可解释性。** 只要 current 由一串增量加减乘维护（施加时 `+=`、移除时 `-=`），任意一次移除路径的漏算都会让 current 永久漂移，且漂移量与时间成正比、与施加历史强相关，事后无法从任何单一状态推断当前值是从哪来的。总纲第 7 节失败模式 1 已点名这条，本节把它落成唯一的写入方向：**current 永远是「重算出来的」，不是「改出来的」**。
2. **同一属性上多个效果的合成顺序。** 一个目标身上同时挂着装备加成、buff、debuff，它们各自贡献修饰器。如果合成语义依赖施加先后，同一个目标在不同会话里会算出不同数值，而这种差异不可复现、无法写测试。
3. **效果的生命周期推进。** 引擎没有 GAS 的效果容器，也没有「效果时钟」。若直接引计时器，效果状态只能挂在宿主时间轴上，暂停、多实例（PIE）与确定性重放都会立刻变复杂。
4. **施加前的准入。** 参考实现（作者此前的 CardGameDemo 原型）只在效果**生效后**用条件判断去挂起或补偿，目标侧没有「施加前拒绝」这一道闸，导致效果落在不该落的目标上再回滚，回滚路径本身就是漂移源。
5. **框架与策略的边界。** 同一个原型里，框架提供了 pre-apply / pre-modify 回调，业务代码在回调里改写数值与规则。回调一旦可以改写数值，框架就必须为「谁先谁后」「谁赢」作承诺，而这与 C27（不得依赖顺序）正面冲突；更严重的是带副作用的回调让「重算一次」与「运行到此处」不再等价，重聚合的可对账性从根上被破坏（该原型的 F13 教训）。

本文档定义这三段的最小完整形态：**属性容器**（谁能写、写什么）、**修饰器**（怎么合成）、**效果**（谁在什么时候贡献修饰器）。能力编排（何时施加、消耗什么、选什么目标）不在本 spec（CORE-F07）。

## 2 目标与非目标

### 2.1 目标

- **G1** 给出属性容器唯一的数据形态：一个 tag 键索引的容器、三个隔间（base / 修饰器集合 / current），并说清哪一段落盘。
- **G2** 给出修饰器的封闭运算集合、封闭幅度来源集合，以及一条**全序确定**的聚合规则：同一输入必得同一输出。
- **G3** 给出效果的生命周期封闭集合与一个与驱动者解耦的推进入口，使「tick 推进」只是该入口的一个调用者，而不是语义。
- **G4** 给出「到期/移除后 current 必须等于以剩余集合重算的值」这条可对账的不变量，并给出用例形态。
- **G5** 给出目标侧施加前准入，使拒绝发生在任何状态变更之前。
- **G6** 把框架与策略切开：框架只提供机制与只读通知，业务改写走标准施加/移除路径，不回灌结算。

### 2.2 非目标（这版明确不做）

- **能力运行期**（何时施加、消耗、目标选择、打断、动画与表现）——归 CORE-F07，本 spec 只提供「施加 / 移除 / 查询」的机制入口。
- **网络复制与预测**：不做 replication、不做客户端预测、不做回滚。执行模型沿用总纲的单线程同步假设。
- **伤害公式与战斗规则**：暴击、抗性、护甲穿透都是内容的组合，不是框架规则；框架**不内置任何具体公式**，也不提供「公式插件点」。
- **存档槽、读档恢复剩余时长、跨版本效果迁移**（C15）：本版不持久化效果集合，读档后效果由上层重建。
- **暂停 / 倍速 / 多时间源**：V1 只有一个推进源；引入第二个时间源时才需要新的驱动者，语义不变（见 4.7）。
- **周期性结算（period）**：本版不做。它需要「同一效果多次结算 + 每次结算独立原子边界」的新语义，见第 11 节 Q9。
- **数值显示格式化与 UI 绑定**：框架只给数值与变更通知，不给展示层约定。

## 4 设计

### 4.1 属性容器：一个容器、三个隔间

属性状态不是「两张表」——不是「实例增量表」加「另一份属性表」。它是**一个容器**，每个属性条目内部有三段：

```cpp
// Sketch only; the final signature may differ.
struct MGFAttributeEntry {
    MGFAttributeTag m_key;       ///< Attribute identity, a gameplay tag name.
    float m_base = 0.0f;         ///< Definition default already merged with instance overrides.
    MGFModifierSet m_modifiers;  ///< Live contributions; rebuilt from the live effect set.
    float m_current = 0.0f;      ///< Derived cache; never authored, never persisted.
};
```

三段各自的写入者与生命周期：

| 隔间 | 真值来源 | 谁写 | 何时失效 | 落盘 |
| --- | --- | --- | --- | --- |
| base | 定义的默认值 ← 实例增量条目覆盖 | 只有「实例状态变更路径」（片段覆盖、内容装配、上层显式设置） | 变更即触发重聚合 | 只落**增量条目**（覆盖层），定义默认值不落盘 |
| 修饰器集合 | 当前驻留的效果集合 | 只有效果施加 / 移除 / 叠层 / 挂起切换路径（C29） | 每次效果集合变化 | 不落盘 |
| current | base + 修饰器集合全量重聚合 | 只有结算提交（见 4.12） | 每次提交 | 不落盘 |

**为什么增量表与属性容器是同一个东西而不是两层。** 持久化文档里的「tag 键的增量属性表」（C5/C11）在运行期就是容器 base 隔间的覆盖层：一条增量条目存在的意义是「这个属性的 authored 值被改写成 X」。如果把它做成第二张表，同一次「把 Health 设为 120」就有两个入口、两份可写状态，任何一处漏写都会让 C31 的单真值归属表同时指向两个持有者，而 C29 也无法再断言「每个状态只有一个写入点」。因此：

- **增量表是 base 隔间的持久化投影，不是第二份状态。** 容器 base 是「定义默认 ← 增量条目」的物化结果，本身也是可重算的派生值。
- **属性值本身不全部可持久化。** 只有增量条目（覆盖）落盘；`current`、修饰器集合、效果实例集合都不落盘。理由：`current` 是纯派生（C6/C11），而修饰器集合与效果实例携带施加上下文（instigator/source 等运行期对象引用），无法安全跨会话重建，且 C11 的文档形状里没有这一段。
- 于是「读档后 current 从哪来」有唯一答案：**从 base 重聚合**。读档时没有效果，所以 current 等于 base；这是自洽的，不是特例。

### 4.2 值类型与精度

V1 的属性值类型只有 `float`（采纳总纲 Q10 建议 a）。三条必须写明的后果：

1. **浮点意味着「数学等价」不等于「位级一致」。** 加法与乘法都不满足结合律，同一集合按不同顺序求和会差最后几个尾数位。本节因此把「顺序」当成一等公民（4.4），并把可交换性的承诺分级：数学等价在相对容差内，位级一致只在排序键完全一致时承诺。
2. **非有限值是传染病。** 一个 `NaN` 会污染整条依赖链，且 `NaN != NaN` 让所有相等性检查失效。契约要求每次提交前做有限性闸（见 4.12）。
3. **定点化登记为可选技术债。** 理由：第一版的目标是验证规则而不是数值精度；定点化会污染所有算术语义（乘法的标度、溢出的处理、与内容作者对「乘 1.15」的直觉冲突），而当前没有任何用例需要逐帧确定性重放。登记内容与退出条件见 4.2.1。

#### 4.2.1 定点化登记为技术债的内容

TECH_DEBT 当前只有空表（本 spec 不改动该文件），以下内容在 Wave1 落地时按原样登记：

- **摘要**：属性值用 `float`，聚合结果的位级可重复性依赖排序键，不保证跨平台/跨编译器一致。
- **影响**：任何需要逐帧确定性重放（回放、联机校验、录像）的功能不可用；跨平台截图比对类测试（数值敏感）不可用。
- **退出条件**：全仓属性值类型改为定点整数（或定点标度类型），四则运算语义与舍入规则写进契约，且「可交换性分级」从「容差内」升级为「位级」，并有一条跨平台的位级一致用例通过。
- **触发提前的条件**：出现第一个必须以位级一致性验收的用例（例如回放推进一致性）。

### 4.3 修饰器

```cpp
// Sketch only; the final signature may differ.
struct MGFModifier {
    MGFModifierOp m_op;             ///< Add, Multiply or Override.
    MGFMagnitudeSource m_magnitude; ///< Constant, attribute-based or caller-provided.
    int m_priority = 0;             ///< Ordering key inside a bucket.
    MGFStageTag m_stage;            ///< Optional stage name; empty means the implicit stage.
};
```

#### 4.3.1 运算种类：Add / Multiply / Override，不做 Divide

- **Add**：加法桶的一个加数。
- **Multiply**：乘法桶的一个因子；`1.0` 是恒等，`0.0` 表示清零，负值表示变号。数据里写 `0` 是合法输入，不做特判。
- **Override**：替换「起点值」——把 base 换成自己的幅度，其余桶照常在其上运算。
- **不做 Divide**（契约 K5）：(1) 表达力冗余，`÷x` 等价于 `× (1/x)`；(2) 除法桶不可交换，`a/b/c` 与 `a/(b·c)` 在浮点下结果不同，直接破坏 4.4 的可交换性分级；(3) 除零需要引入 `0` 特判与 `Inf/NaN` 规则，等于给内容作者第二种错误值形态；(4) 一旦同时存在乘桶与除桶，「先乘后除」还是「先除后乘」变成内容作者必须理解的新语义，而这一条无法用数据自解释。
- **Override 不得绑定阶段**（契约 K7）：Override 会丢弃上一阶段的输出，与「阶段间流水」不可组合；修饰器的 op 为 Override 且带了非空阶段名，装载期即报问题。

#### 4.3.2 幅度来源：三种，封闭

| 来源 | 形态 | 说明 |
| --- | --- | --- |
| 固定值 Constant | 一个常数 | 绝大多数内容用这一种 |
| 基于其他属性 AttributeBased | (取值域 Source 或 Target) × (基准 Base 或 Current) × 系数 | 从「谁」身上取哪个属性、取基值还是当前值，再乘一个系数 |
| 调用方给定 SetByCaller | 一个 tag 键 | 施加时由调用方在上下文里给出，**施加时冻结**进修饰器实例 |

- **SetByCaller 必须冻结。** 冻结后修饰器实例的幅度是常数，重聚合才是纯函数；若在每次结算时回查可变来源，同一份状态在不同时刻会算出不同 current，对账立刻失效。
- **缺键是调用方违约**，不是数据错误：施加入口返回结构化失败码且零状态变更，调试期同时断言（符合 C20「断言不得作为唯一防线」）。
- **AttributeBased 的取值域 Target 指向效果宿主自身，Source 指向施加上下文里的 source 实例**；source 在被引用期间消失时，该修饰器实例被置为 0 并报一条运行期问题（不崩溃、不静默改语义）。

### 4.4 聚合

#### 4.4.1 桶与全序

每个阶段内按运算种类分桶：Add 桶求和、Multiply 桶求积。桶内的全序键是 (priority 升序, 注册序升序)；注册序 = (施加序号, 该效果内修饰器索引)，施加序号在实例内单调递增且唯一，因此**任何修饰器实例集合都能被排成一个全序**。

排序键必须存在，理由不是「为了可配」，而是浮点求和/求积依赖顺序：没有全序键，「同一集合」就不是「同一输入」。

#### 4.4.2 聚合公式

```cpp
// Sketch only; the final signature may differ.
float aggregate(const MGFAttributeEntry& entry, const MGFAttributeSnapshot& snapshot)
{
    float value = snapshot.baseOf(entry.m_key);

    // Override replaces the starting value; it never participates in a stage.
    if (const MGFModifierInstance* winner = pickOverride(entry.m_modifiers()))
        value = winner->magnitude();

    // Stages run as a pipeline: each stage consumes the previous output.
    for (const MGFStageTag& stage : snapshot.stageOrder(entry.m_key)) {
        value = value + sumOfAddBucket(entry.m_modifiers(), stage);
        value = value * productOfMultiplyBucket(entry.m_modifiers(), stage);
    }
    return value;
}
```

要点：Override 先裁决（不在阶段流水内），随后每个阶段「先加满、再乘满」。乘法在加法之后，是因为内容作者心算的模型几乎都是「先算基础加成、再算百分比放大」，且这个顺序让「+10 再 ×2」与「×2 再 +10」这类歧义不会出现在数据里。

#### 4.4.3 阶段（stage）

阶段是**数据绑定到「实体 × 属性」**的有序计算段，不是全局常量，也不是效果的私有属性。理由：同一个属性在不同实体上需要不同上游——角色身上的 `Attr.Health` 可能是「先装备加成、再 buff 区、再 debuff 区」，而环境物件上的同名属性完全不需要 buff 区。

- **阶段内聚合**：同一阶段内的各桶按 4.4.1 排序后聚合。
- **阶段间流水**：阶段按声明顺序执行，阶段 i 的输出是阶段 i+1 的输入。
- **未声明阶段时的降级规则（契约 K11）**：
  - 属性在实体定义里**没有任何阶段声明** → 所有修饰器落入**隐式阶段**，聚合退化为单段（先加满再乘满）。这是 V1 的默认路径，**不报警告**，因为它不是数据缺陷。
  - 属性已声明阶段，但某个修饰器引用了**该属性未声明的阶段名** → 装载期 fail-fast，问题项指出属性名、阶段名与所属效果。理由：这是内容词汇不一致，运行期无法安全猜测（C17 第一级）。
  - 属性已声明阶段，修饰器未绑定阶段 → 落入**隐式阶段**，隐式阶段固定排在所有显式阶段**之后**。理由：「显式声明的顺序」必须是作者可控的前缀，框架不得把自己的隐式段插到中间。

#### 4.4.4 可交换性：哪些组合与施加顺序无关

「同一 target 上多个效果写同一属性」的**写入顺序不影响最终值**，不是靠约定，而是靠结构：效果不是「写入」，是往集合里放元素；提交的值只依赖 (元素集合, 排序键, base, 阶段声明)。

| 组合 | 是否可交换 | 承诺强度 | 依据 |
| --- | --- | --- | --- |
| Add × Add（不同 priority） | 是 | 位级一致 | 排序键固定求和顺序 |
| Add × Add（同 priority） | 是 | 相对误差 ≤ 1e-6 | 顺序由施加序决定，浮点加法非结合 |
| Multiply × Multiply（不同 priority） | 是 | 位级一致 | 同上 |
| Multiply × Multiply（同 priority） | 是 | 相对误差 ≤ 1e-6 | 浮点乘法非结合 |
| Add × Multiply | 是 | 位级一致 | 跨桶顺序由公式固定，与施加顺序无关 |
| Override × Add / Override × Multiply | 是 | 位级一致 | Override 只改起点，加乘桶照常作用 |
| Override × Override | **否** | — | 由最高 priority 裁决；同 priority 时按注册序取最后者 |
| 任意修饰器 × 不同阶段的同 op | **否** | — | 阶段流水是有序语义，作者必须显式声明顺序 |
| AttributeBased 引用 × 被引用属性的变更 | 是（有界延迟） | 数学等价，最多一次结算延迟 | 只读结算开始时的已提交快照（4.4.5） |

两条由此导出的强制规则：

1. **同 priority 的多个 Override 上到同一属性是内容缺陷**：调试期断言，发布期取注册序最后者并记错误日志（C17 运行期断言类 + C20）。
2. 「相对误差 ≤ 1e-6」写成用例时的比较方式是**相对误差**而不是绝对值，因为属性的量级跨越好几个数量级（生命值上千、倍率在 1 附近）。

#### 4.4.5 引用其他属性：只用快照，不迭代

`AttributeBased(Source 或 Target, Base 或 Current, 系数)` 读取被引用属性时，**只读本次结算开始时的已提交值**，不读「本次结算算到一半的中间值」，也不做不动点迭代。

理由与代价：

- **理由**：这是让重聚合保持纯函数、让「A 依赖 B、B 依赖 A」不可能死循环的唯一低成本做法。若允许读中间值，聚合结果就依赖属性遍历顺序，全序性丢掉。
- **代价**：取当前值时有**最多一次结算的延迟**（一次重聚合的最坏情况）。这条延迟是显式的、可测量的，而不是随机的。
- **不做的**：不动点迭代（多算几轮直到收敛）。它会让结算成本不可预测，且收敛性需要内容作者证明——超出「框架该承担的责任」。

### 4.5 效果的定义形态：效果是内容定义

**效果是内容定义，不是内联结构。** 一份 `EffectDef` 是内容注册表里的一族定义（`kind` 为效果种类的 ContentId），施加时按 ContentId 引用：

- 与 CORE-F03 的关系：`EffectDef` 是 ContentDef 的一个族（与物品、图节点 payload 同层），**由 CORE-F03 提供内容 id、注册表、装载校验与包闭包**；本 spec 只定义 `EffectDef` 的字段语义与它会引发的装载期问题种类。
- 施加入口的形状因此是「按 ContentId + 上下文施加」，不是「传一个结构体进去」。这样效果数据可以只改数据不重编（C7），且效果可被图节点 payload、物品定义、能力定义按 C2 以 id 引用。
- **唯一的例外是运行期合成效果**：由代码（能力、脚本、测试）构造的临时效果。它**形态与定义相同**（同一套修饰器/生命周期/层数描述），但**不进注册表、不进持久化、不参与包闭包检查**，其 id 为空并在调试期打标记录来源。这不是第二条语义，只是同一个描述类型的第二个来源。

`EffectDef` 的字段划分见第 6 节（C9 的落点：修饰器列表必须是 Instanced 对象数组，不能是 `ME_STRUCT` 数组）。

### 4.6 效果生命周期：Instant / Duration / Infinite

生命周期封闭为三种（契约 K14），没有第四种：

| 类型 | 驻留 | 推进 | 修饰器何时生效 |
| --- | --- | --- | --- |
| Instant | 不驻留 | 不推进 | 施加当次结算生效一次，随即丢弃；不进入效果集合 |
| Duration | 驻留 | 计入推进，耗尽即移除 | 驻留期全程生效 |
| Infinite | 驻留 | 不推进 | 驻留期全程生效，只能被显式移除 |

- **Instant 不走「施加 → 结算 → 移除」三步。** 它直接作为一次结算的输入参与重聚合：把它的修饰器临时并入集合算出候选值，提交后丢弃。这样「瞬时效果」不会在集合里出现过一帧的中间态（否则同一帧内查询会看到不该存在的效果）。
- **Duration 的剩余时长是整数单元数**（4.7），`0` 单元是非法值（装载期拒绝），避免「施加即到期」的语义歧义。
- **到期与移除是同一条路径**（`RemoveEffect` 的到期原因不同而已），因此「到期后 current 与非到期移除后 current 一致」是结构性的，不是两次实现碰巧一致（见 4.14 对账）。

### 4.7 时长推进：事件驱动，单入口，不引计时器

时长的权威表示是**整数推进单元数**（契约 K15）。内容作者写秒，装载期按量子（quantum）换算：

```text
units = ceil(seconds / quantum)
```

- 量子是代码常量（C8：结算规则属代码），装载期校验量子大于零。
- 换算向上取整，保证「写了 10 秒」的效果不会比 10 秒更早消失。
- 驱动者每次推进给的是**整数** `deltaUnits`；若驱动者的时间片不是量子整数倍，**余数必须由驱动者自己吸收**（累加器保留余数），禁止框架内部对余数做取整——否则长期运行会出现系统性偏快/偏慢，且偏多少取决于帧率。

**唯一入口（契约 K16）**：

```cpp
// Sketch only; the final signature may differ.
/// @brief Advances every effect hosted by the instance by whole advance units.
/// @param unit_key Time source being advanced; only one source exists today.
/// @param delta_units Whole units to advance; fractional remainders are the caller's to keep.
/// @return Problem list describing effects that failed to settle, empty on success.
MGFProblemList Advance(MGFAdvanceUnitTag unit_key, int delta_units);
```

推进的效果：对每个 Duration 效果，剩余单元减去 `deltaUnits`；剩余不大于零标记为到期，进入待移除集合；随后在一次结算批次里统一移除并重聚合。Infinite 与挂起的效果不计。

**为什么是事件驱动而不是计时器。** 计时器把效果状态挂到宿主时间轴上，于是「暂停」需要一个额外的暂停语义、「倍速」需要缩放所有计时器、PIE 双实例需要两套时钟。事件驱动把这三件事全部变成「驱动者发不发、发多少」的问题，效果侧只认整数单元。

**为什么第一版可能退化为 tick 推进，以及切换条件（写进契约的降级规则）。** 当前只有一个时间源（Variable 相位每帧一次），没有暂停与倍速，此时「tick 推进」与「事件驱动」在可观测行为上完全等价，而 tick 推进少一个事件通道与一层订阅。因此第一版允许由 tick 直接调用 `Advance`（这也是唯一的调用者）。三条切换条件，任一条成立就必须切到真正的推进事件（unitTag + 通道）：

1. 出现第二个时间源（暂停、倍速、不同单位的不同推进速率）；
2. 出现必须逐帧确定性重放的用例；
3. 某个效果需要在非 Variable 相位推进（例如固定步长物理相关）。

之所以允许先 tick：**语义已经与驱动者解耦**——切换只是多一个调用者与一条订阅，`Advance` 的签名、单元语义、对账判据都不变。这是「降级不改语义」的合法形态，不是过渡双路径。

### 4.8 tag 闸门：grantedTags / assetTags / ongoingTagRequirements / applicationTagRequirements

四组 tag，语义各自独立，**不允许互相顶替**（契约 K17、K18）：

| 组 | 何时生效 | 作用 | 能否用于批量清理 |
| --- | --- | --- | --- |
| `grantedTags` | 驻留期（挂起时撤回） | 向目标集合授予 tag；参与其他效果的准入与免疫判定 | 否 |
| `assetTags` | 始终（只读分类） | 纯分类标签，供「移除所有带某 assetTag 的效果」使用 | **是**，这是它存在的唯一目的 |
| `ongoingTagRequirements` | 驻留期持续评估 | 生效闸门：不满足即**挂起**（不是移除） | 否 |
| `applicationTagRequirements` | 施加前一次性评估 | 目标侧准入：不满足即**拒绝施加** | 否 |

全部内容里 tag 只能是名字（C39），载入期统一走词汇表校验（C19）。

**grantedTags 与 ongoingTagRequirements 的相互作用必须批次化。** 一次状态变更可能让多个效果的闸门同时失效，其中一个效果的挂起又会撤回它的 `grantedTags`，从而可能再影响别的效果。规则：

- **tag 变更触发的重评估是一次批量的重算，不递归**（契约 K19）：本批次开始时对目标效果集合求一次「应该挂起谁」的完整判定，本批次产生的 tag 变化**排队到下一批次**。
- 因此闸门判定对 tag 的依赖有**最多一次结算的延迟**，与 4.4.5 的引用延迟同构、同样可测量。禁止在同一次重评估里「挂起 A → 撤 tag → 重新判定 B → 又影响 A」的固定点求值：它是重入源（C27 明确禁止依赖重入与顺序）。

**挂起 vs 移除（契约 K18）**：挂起不贡献修饰器、不推进时长，效果仍在集合里；恢复后重新贡献并继续从原剩余单元推进。对账在挂起态也必须成立（挂起的效果视为「不在贡献集合中」，但仍占层数）。选择挂起而非移除，是因为移除会丢失层数与剩余时长，恢复时无法还原，且移除/重施加会推进施加序号——把一次临时条件变化变成永久的顺序扰动。

### 4.9 施加上下文

一次施加携带固定五元组（契约 K20），**在施加时冻结**：

| 字段 | 语义 |
| --- | --- |
| instigator | 谁发起了这次施加（实体引用，可为空）；只用于归属与日志，不参与数值 |
| source | 承载效果的来源实体（提供 AttributeBased 的 Source 取值域，可为空） |
| target | 效果宿主 |
| setByCaller | tag 键到 float 的冻结表，供 SetByCaller 幅度取值 |
| payload | 可选的内容 id（C2），用于效果内部再引用内容（例如「施加时附带哪个子效果」）；**不携带任意对象指针** |

施加上下文里只有实体引用与内容 id，**没有可变的业务结构**（否则冻结不成立，重聚合不再是纯函数）。

### 4.10 层数（Stacking）

效果的层数是效果实例上的一个整数，配合三个数据字段：

| 字段 | 语义 |
| --- | --- |
| stackLimit | 层数上限；`1` 表示不可叠（重施加走刷新策略），大于等于 2 表示可叠到该数，`0` 表示无上限，负值装载期拒绝 |
| reapplyPolicy | 重施加策略：刷新时长 / 叠层 / （可选）累加幅度 |
| stackAggregation | 层数如何进入数值：每层独立贡献 / 幅度乘以层数 |

**聚合方式（契约 K22）**：默认是**每层独立贡献**，即 n 层就是 n 条修饰器实例，各自带自己的注册序。这条默认与前面所有规则同构，且对两种 op 给出不同的自然结果：

- Add：n 层 → `+ n·m`（与「幅度乘层数」相同）。
- Multiply：n 层 → `m^n`（**与「幅度乘层数」不同**！`1.1^3 ≈ 1.331`，而 `1.1×3 = 3.3`）。

`stackAggregation = 幅度乘以层数` 是显式开关，只改数值不改集合形态。**同一个效果不允许在同一属性的不同层上混用两种聚合方式**（数据里只有一个字段，天然禁止；写这一条是为了让读者看到它为什么只有一层开关）。

**重施加策略（契约 K23，CardGameDemo 教训）**：枚举里出现的每个值都必须在装载期被支持并有对应用例。原型里 `AddMagnitude` 策略在数据里可选、运行期未实现，结果是「数据写了、行为静默地没发生」——这种缺陷比对缺失更难发现，因为装载期是干净的。三条硬规则：

1. 枚举里的每个值都有实现与用例；
2. 未实现的值**不出现在枚举里**（数据里出现即装载期 `UnknownReapplyPolicy`），不做「出现但拒绝」的半步；
3. 「累加幅度」若在 V1 不实现，是因为它的语义成本最高：幅度随重施加无界累积、移除时「撤哪一份」没有唯一答案、且它与「重聚合可交换」正面冲突（幅度成了历史的函数）。见第 11 节 Q5。

**移除时的对齐语义（契约 K24）**：移除只有两种形态，都不允许「部分逆运算」：

- `RemoveEffect(effectInstance)`：整条移除，包含它的所有层。
- `RemoveStacks(effectInstance, n)`：移除 n 层（n 不小于剩余层数时等价于整条移除）。

两种形态都必须满足：**移除后的 current 等于「以移除后的效果集合重新聚合」的结果**。实现上不是「扣掉 n 层贡献」，而是「从集合里删掉 n 条修饰器实例然后重聚合」，所以对齐是结构性的。

### 4.11 目标侧施加前准入

`applicationTagRequirements` 在**任何状态变更之前**评估（契约 K21）。不满足时：

- 返回结构化失败结果（C21），带上具体是哪个 tag 要求未满足；
- **零状态变更**：不创建效果实例、不递增施加序号、不触发结算、不发通知；
- 不记断言（这是合法业务路径，不是框架不变量被破坏）；
- 不消耗任何东西（消耗是 CORE-F07 的职责，它在拿到失败结果后自行决定）。

这一条补的是原型的缺口：原型只在效果生效后用 `ongoingTagRequirements` 去挂起，于是「不该中的目标」先中了一次、再被挂起，中间那一帧的 current 是被污染过的，且补偿路径本身要靠「记得撤回」——正是漂移的来源。

### 4.12 结算与通知

**原子边界（契约 K25）**：一次结算 = 一个目标上「受影响的属性键集合」的一次批量重算。

1. **先算**：对每个受影响的属性键，用当前 base 与修饰器集合全量聚合出候选值（只读，不改任何状态）。
2. **校验**：全部候选值必须有限；任一非有限即**整批放弃**，保留上一次已提交的 current，报运行期问题。不做「跳过坏的那一个，提交其余部分」——部分提交会让对账在语义上不可判定。
3. **提交**：写入 current 缓存、递增实例 revision、把该目标加入待通知集合。提交是 current 的唯一写入点（C29）。
4. **通知**：帧末 drain 时按 (target, 通道) 去抖投递（C28）。一次结算对每个目标最多一次通知；通道只有一条（`Event.Attribute.Changed` 一族），**事件里不带业务载荷**（C24），接收方回查实例的 revision 与快照自行 diff。

**pre / post 回调（契约 K27，CardGameDemo F13 教训）**：

- **只提供 post 只读通知，不提供 pre 修改钩子。** post 通知是「机制」：它告诉世界「这批值变了」，不参与计算。
- **pre 钩子属于策略，框架不承载。** 一旦允许业务在结算前改写数值，框架就必须承诺「多个钩子谁先谁后」与「后一个钩子看到前一个的结果吗」，这与 C27（不得依赖广播顺序）直接矛盾；更根本的是带副作用的钩子让「重算一次」不再等于「运行到此处」，4.14 的对账判据立刻不可判定。原型正是踩了这一条：数值正确性依赖钩子的执行顺序，最终只能在框架里加「优先级字段」来掩盖，框架被迫承载了本该属于玩法的规则。
- 需要改数值的业务有两条合法路径：施加一个效果（下一批次生效，有明确延迟）、或修改内容的 base 增量（走实例状态变更路径）。两者都留下可对账的痕迹。

**相位约束（契约 K28）**：结算入口在 Fixed 相位调用即触发运行期断言（C22）。推进与结算都挂在 Variable 相位的链上。

### 4.13 一次施加的时序（Duration 效果）

1. 校验：`EffectDef` 已解析（C13）、`setByCaller` 覆盖了所有 SetByCaller 键、`applicationTagRequirements` 通过。任一失败 → 返回失败结果，零状态变更。
2. 去重与叠层：同一目标上是否已有同 ContentId（且同来源策略）的效果实例。
   - 不存在 → 新建实例，层数 1，剩余单元为定义值，分配新的施加序号。
   - 存在且不可叠或已满 → 按 `reapplyPolicy` 处理（刷新剩余单元 / 追加层并递增施加序号 / 拒绝）。
3. 生成修饰器实例：对每层、每条修饰器，冻结幅度。SetByCaller 在此刻冻结；AttributeBased **保留引用语义**，在每次聚合时按快照取值。
4. 把修饰器实例并入目标的属性容器，标记受影响属性键。
5. 一次结算批次（4.12）。
6. 通知在帧末投递。

### 4.14 边界情况与对账

**对账不变量（K24 的核心）**：对任意目标、任意时刻、任意效果操作序列，

> 已提交的 current 逐字段等于「用当前 base、当前驻留效果集合（挂起的不参与贡献）、当前层数与阶段声明重新全量聚合」的结果。

**到期与移除为什么与重聚合结果一致（必答问题）。** 因为实现里根本没有「到期时扣掉这次贡献」的路径。到期做的唯一事情是「把该效果实例从集合里删掉并标记受影响属性」，随后走同一个聚合函数。也就是说「移除」不是 `current -= contribution`，而是「集合变化 → 重算」。一致性来自代码路径的唯一性，而不是两处实现互相对齐。由此还可推出两条推论：到期与显式移除走同一函数，因此二者结果必然一致；任意多次「施加 → 移除」循环后 current 必然回到施加前的值（因为集合回到了空集合，聚合是同一输入）。

对账用例形态（doctest 用例名即语义描述）：

- `reaggregation_after_effect_expiry_matches_fresh_container`：施加 → 推进到到期 → 比对 current 与「从 base 重算」的结果；再对同一目标施加/移除若干次后仍然一致。
- `removing_stacks_equals_reaggregation_without_them`：叠 3 层后移除 1 层，比对与「只叠 2 层」的 current 位级相同。
- `inhibited_effect_contributes_nothing_but_keeps_stacks`：挂起后 current 等于「该效果不存在但层数仍占位」的重算值；恢复后位级回到挂起前。
- `effect_apply_order_does_not_change_current_within_tolerance`：两个同 priority 的 Add 效果交换施加顺序，current 相对误差不超过 1e-6。

其余边界情况：

| 情况 | 处理 |
| --- | --- |
| Instant 效果在同一帧被施加多次 | 每次都是独立的一次结算批次；最终 current 等于全部批次按序提交后的值（每次都在前一次结果上重算，不是累加增量） |
| 目标在效果驻留期被销毁 | 效果随实例一起消失，**不发通知、不回查其他子系统**（C34 关闭期不回调） |
| 同一效果被移除两次 | 运行期断言 + 发布期返回失败码，**不改变任何数值**（C17/C20） |
| 效果驻留期间 base 被改（片段覆盖、装备变化） | 走实例状态变更路径，触发重聚合；效果本身不受影响 |
| 层数已满再重施加 | 按 `reapplyPolicy` 处理；不静默丢弃（否则「为什么没生效」不可查） |
| 候选值非有限（NaN/Inf） | 整批放弃提交 + 运行期问题（4.12 第 2 步） |
| 被引用属性的 source 实体消失 | 该修饰器实例贡献 0 + 运行期问题；不改变语义为「忽略整个效果」 |
| 效果对自己施加 | 合法；source 与 target 同一实例，AttributeBased 的 Source/Target 取值域在该情形下等价 |
| 一次 tag 变更让多个效果同时失效 | 一次批量重评估，不递归（4.8） |

## 5 契约（K1..K30）

每条都是「规则 + 可检验」。标注「细化 Cn」表示只补充该契约未覆盖的部分，不重新定义它。可检验项可直接落成 doctest 用例或 grep / 审查判据。

### 5.1 属性容器与值类型

**K1 属性容器是唯一形态：一个容器、三个隔间。** 每个属性条目只有 base / 修饰器集合 / current 三段，不存在「每属性私有字段」或第二份属性表。
*细化 C5。*
可检验：容器的公开字段表与三段一一对应（审查项）；用例：给实例增加一个新属性 tag 键不需要改容器类型。

**K2 增量条目是 base 隔间的持久化投影，不是第二份状态。** 持久化只写增量条目（覆盖），运行期 base 由「定义默认 ← 增量条目」物化；改变 base 只有一条入口。
*细化 C5 / C14。*
可检验：代码里不存在对「增量表」与「属性容器」分别提供的两个 set-base 入口（审查项 + 一条断言：base 写入路径计数为 1）；写入值为 0 的覆盖后往返，条目数不变且读到 0 而非默认值。

**K3 值类型 V1 只有 float，且非有限值不得提交。** 每次提交前对全部候选值做有限性检查，任一非有限则整批放弃。
*细化 C5（值类型）+ 采纳总纲 Q10 建议 a；定点化按 4.2.1 登记为技术债。*
可检验：用例 `non_finite_candidate_aborts_whole_batch`（注入一个会产出无穷的修饰器，current 保持上一次值且返回问题项）；grep 属性值类型声明，只出现一个浮点类型别名。

**K4 current 只由全量重聚合产生，禁止逆运算写入。** 全仓不得存在「把贡献扣掉」的路径（对 current 做减等于或除等于）。
*细化 C6 / C29。*
可检验：grep 对 current 的赋值点只有结算提交一处（审查项）；用例 `removal_goes_through_aggregation_not_subtraction`（用一个非线性的 Multiply 组合验证扣减会失败而重算正确）。

### 5.2 修饰器与聚合

**K5 运算种类封闭为 Add / Multiply / Override，不做 Divide。** 未知运算种类在装载期 fail-fast。
*细化 C8。*
可检验：枚举只有三个值（审查项）；数据里写第四个运算名装载失败并给出名字。

**K6 幅度来源封闭为三种，SetByCaller 在施加时冻结。** AttributeBased 保留引用语义、按结算快照取值。
*细化 C8 / C36。*
可检验：用例 `set_by_caller_is_frozen_at_apply_time`（施加后修改调用方持有的值表，current 不变）；用例 `attribute_based_reads_snapshot_not_self`（A 依赖 B 的当前值，改变 B 后 A 在下一次结算才变化）。

**K7 聚合顺序固定：Override 先裁决，随后逐阶段「先加满、再乘满」；桶内按 (priority 升序, 注册序升序)。** Override 修饰器不得绑定阶段。
*细化总纲 Q4 建议 a + C6。*
可检验：用例 `override_with_stage_binding_fails_at_load` 通过；用例 `bucket_order_matches_priority_then_registration`（构造三个修饰器验证求和顺序）。

**K8 注册序是实例内全序且唯一。** 施加序号在实例内单调递增，每次成功施加或叠层递增；修饰器实例带 (施加序号, 效果内索引)。
*细化 C6。*
可检验：断言同一实例内不存在两条修饰器实例共享注册序；用例：连续施加/移除 100 次后施加序号仍单调。

**K9 可交换性分级必须被承诺并测试。** 4.4.4 表格的每一行都是一条判据：位级一致的组合用逐字段相等比较，容差组合用相对误差不超过 1e-6；表里标为「否」的组合必须被文档化而不是被测试忽略。
*细化 C6 / 总纲 Q4。*
可检验：用例 `effect_apply_order_does_not_change_current_within_tolerance` 与 `cross_bucket_order_is_bitwise_stable`；同 priority 多个 Override 触发断言（用例 `ambiguous_override_priority_asserts`）。

**K10 引用其他属性只用结算开始时的快照，不做不动点迭代。**
*细化 C6。*
可检验：用例 `mutual_attribute_reference_terminates_with_one_settle_delay`（A 与 B 互相引用，一次结算后两者都只前进一拍，且聚合调用次数被计数器断言为 1）。

**K11 阶段绑定「实体 × 属性」，阶段内聚合、阶段间流水；未声明阶段退化为隐式阶段；引用未声明阶段名装载期 fail-fast；未绑定阶段的修饰器落隐式阶段且隐式阶段排最后。**
*细化 C17 + 总纲 Q4。*
可检验：三个用例——`undeclared_attribute_uses_single_implicit_stage`（无警告）、`unknown_stage_name_fails_at_load`（问题项含属性名与阶段名）、`unbound_modifier_lands_in_implicit_stage_last`。

**K12 重聚合是确定函数。** 输入相同（base、修饰器实例序列、阶段声明、层数）则输出位级相同，与调用次数、调用时刻、广播顺序无关。
*细化 C6 / C11。*
可检验：用例 `aggregate_twice_yields_bitwise_identical_result`；用例：在两次结算之间插入若干次无关事件广播，结果不变。

### 5.3 效果

**K13 效果是内容定义一族（kind 为效果种类），引用走 ContentId；运行期合成效果形态相同但不进注册表、不落盘、不可被内容引用。**
*细化 C2。*
可检验：`EffectDef` 的字段表里对子内容的引用字段类型只有 ContentId（审查项）；用例 `runtime_synthesized_effect_is_not_registered`（按空 id 施加后注册表计数不变）。

**K14 生命周期封闭为 Instant / Duration / Infinite。** Instant 不进入效果集合；Duration 与 Infinite 进入集合并参与重聚合。
*细化 C8。*
可检验：用例 `instant_effect_leaves_no_residue`（施加并结算后效果集合为空且 current 正确）；未知生命周期名装载失败。

**K15 时长以整数推进单元为权威量；秒到单元向上取整；量化余数由驱动者吸收。**
*细化 C22。*
可检验：用例 `duration_rounds_up_to_whole_units`（0.25 秒、量子 0.1 → 3 单元）；用例 `remainder_is_not_dropped_by_the_driver`（0.4 量子推进三次后累计 1 单元、余 0.2）。

**K16 推进只有一个入口 `Advance`；tick 只是它的一个调用者；新增时间源只新增调用者，不改语义。**
*细化 C22 / C23。*
可检验：grep 对「剩余时长」的写入点只有 `Advance` 一处（审查项）；用例 `second_driver_does_not_change_semantics`（用测试驱动者代替 tick 推进，同一序列得到相同 current）。

**K17 四组 tag 语义独立、不得互相顶替**：grantedTags（驻留授予、挂起撤回）/ assetTags（纯分类，唯一用途是批量清理）/ ongoingTagRequirements（生效闸门）/ applicationTagRequirements（施加前准入）。
*细化 C39 / C29。*
可检验：用例 `asset_tag_only_selects_effects_it_never_grants_behavior`（带 assetTag 的效果不改变任何准入判定）；用例 `remove_effects_by_asset_tag_removes_only_matching`。

**K18 挂起与移除是两个状态。** 挂起的效果不贡献修饰器、不推进时长、仍占层数；恢复后继续从未耗尽的单元推进。
*细化 C6。*
可检验：用例 `inhibited_effect_contributes_nothing_but_keeps_stacks`；用例：挂起 5 单元后恢复，剩余单元与挂起前相同。

**K19 tag 变更触发的重评估是批次化的一次重算，不递归。** 本批次产生的 tag 变化排队到下一批次。
*细化 C27 / C6。*
可检验：用例 `tag_driven_inhibition_converges_in_one_repass`（构造互相影响的两个效果，断言重评估轮数为 1、第二次结算后达成稳定）；审查项：重评估路径里没有对结算入口的递归调用。

**K20 施加上下文五元组在施加时冻结，且不含可变业务结构。** 上下文里只有实体引用、数值表与 ContentId。
*细化 C36。*
可检验：审查项——上下文结构体的字段类型只有实体引用、数值表与 ContentId；用例 `mutating_source_state_does_not_change_frozen_context`。

**K21 目标侧施加前准入先于一切状态变更。** 不满足时返回结构化失败码，零状态变更、零通知、不递增施加序号。
*细化 C21。*
可检验：用例 `application_requirement_rejection_changes_no_state`（比对施加前后的效果集合、施加序号、current 与通知计数全部不变）。

### 5.4 层数与重施加

**K22 层数的默认聚合是「每层独立贡献」；「幅度乘以层数」是显式开关，且两者对 Multiply 的结果不同（`m^n` 对 `m·n`）。**
*细化 C6 + 总纲 Q4。*
可检验：用例 `three_multiply_stacks_compound_not_linear`（m=1.1、3 层 → 1.331 而非 3.3）；用例 `stack_aggregation_switch_changes_value_but_not_set_shape`。

**K23 重施加策略枚举里的每个值都必须有实现与用例；未实现的值不得出现在枚举里。**
*细化 C17 / C8。*
可检验：枚举值与实现分支一一对应（审查项 + 用例逐个覆盖）；数据里写一个不在枚举里的策略名 → 装载失败且问题项给出该名字（不允许静默按默认处理）。

**K24 移除后的 current 必须等于以剩余集合重聚合的结果；重复移除触发断言且不改变数值。**
*细化 C6。*
可检验：4.14 的四条对账用例；用例 `double_removal_asserts_and_keeps_value`。

### 5.5 结算与通知

**K25 结算原子边界：先算后提交，提交是 current 的唯一写入点；任一候选值非有限则整批放弃。**
*细化 C29 / C17。*
可检验：审查项——current 写入点只有一处；用例 `non_finite_candidate_aborts_whole_batch`（同批次另一个合法属性也不被提交，验证「全或无」）。

**K26 通知去抖且无业务载荷。** 一次结算对每个目标最多一次通知，接收方凭 revision 回查；广播期间不改订阅集合。
*细化 C28 / C24 / C26。*
可检验：用例 `three_settlements_in_one_frame_yield_one_notification`（且读到最终值）；审查项——事件类型无业务字段；用例 `subscribe_during_broadcast_arrives_next_time`。

**K27 只提供 post 只读通知，不提供 pre 修改钩子。** 数值改写只能走施加效果或实例状态变更两条路径。
*细化 C27 / C29。*
可检验：审查项——结算入口不接受回调参数；用例 `settlement_is_pure_without_listener_side_effects`（挂一个只读监听者，结算结果与无监听者时位级相同）。

**K28 结算与推进入口在 Fixed 相位调用即断言。**
*细化 C22。*
可检验：用例 `settlement_in_fixed_phase_asserts`（调试期断言，发布期返回失败码，C20）。

### 5.6 持久化与校验

**K29 只有 base 增量条目进持久化；current、修饰器集合、效果实例集合一律不落盘；加载后 current 由重聚合重建。**
*细化 C11 / C14。*
可检验：用例 `save_load_save_is_byte_identical_with_live_effects`（施加若干效果后存盘，两次字节序列等价且文档里无 current 字段）；用例 `current_after_load_equals_reaggregation_of_base`。

**K30 内容里出现未注册的属性 tag 或未注册的阶段 tag 是装载期 fail-fast，问题项给出完整 tag 名。**
*细化 C19。*
可检验：用例 `unknown_attribute_tag_fails_at_load`（问题项文本包含完整 tag 名）；用例 `multiple_unknown_tags_all_reported`（至少两条同时报告，C18）。

## 6 数据与序列化

### 6.1 进 DataAsset 的字段（EffectDef，CORE-F03 一族内容定义）

| 字段 | 形态 | 备注 |
| --- | --- | --- |
| id | ContentId（kind = 效果种类） | C1；加载期唯一性与字符合法性校验 |
| modifiers | **Instanced 对象数组** | C9 落点：修饰器有多个字段，不能内联为 `ME_STRUCT`，必须是反射派生对象数组 |
| duration | 枚举 + 秒（可选） | 只有 Duration 需要秒；Instant / Infinite 不读取该字段 |
| stacking | stackLimit / reapplyPolicy / stackAggregation | 4.10 |
| grantedTags / assetTags / ongoingTagRequirements / applicationTagRequirements | tag 名字数组 | C39 / C40：只写名字，载入后重建容器 |
| 其他内容引用（如有） | ContentId | C2：禁止资产引用 |

单个修饰器对象（`MGFModifierDef`）的字段：op、magnitudeKind 及该种类的参数、priority、stage。**stage 的顺序声明不在效果里**，而在实体定义（CORE-F03 的片段）里按属性声明（4.4.3）。

### 6.2 运行期字段（不进 DataAsset，也不落盘）

- 效果实例集合：EffectDef 的 ContentId、层数、剩余推进单元、冻结的 setByCaller 表、施加上下文、挂起标志、施加序号。
- 属性容器的修饰器集合与 current 缓存。
- 实例 revision 与待通知集合。

### 6.3 进持久化文档的字段（CORE-F03 的实例状态文档）

只有四样：实例身份、Definition 的 ContentId、**tag 键增量条目**（属性 tag 到 base 覆盖值）、显式 fragment 覆盖列表，加 schemaVersion。本 spec 在这一段里的贡献只有一条：**增量条目的值类型是属性基值，且条目顺序按属性 tag 名字典序输出**。

### 6.4 往返等价如何保证

1. **条目用存在性表达覆盖**（C14），不用哨兵值；值为 0 的条目照样写出。
2. **顺序确定**：增量条目按属性 tag 名字典序输出；名字是稳定 ASCII（C1 的字符集），因此排序跨平台一致。
3. **不存派生**：current、修饰器集合、效果实例、revision 都不写盘，所以存档内容不包含任何随运行时间变化的东西。
4. **加载后自洽**：文档里没有效果，因此 current 必然等于 base；这与「重聚合」是同一个函数在同一种输入下的输出，不需要额外分支。

## 7 校验与失败

按 C17 的三级归类，本 spec 的落点如下（问题种类名属代码词汇表，C8）。

### 7.1 加载期 fail-fast

| 问题种类 | 触发 | 定位粒度 |
| --- | --- | --- |
| UnknownAttributeTag | 修饰器或阶段声明引用了未注册的属性 tag | 定义 id + 字段 + tag 全名 |
| UnknownStageTag | 修饰器引用了未注册的阶段 tag，或该属性未声明的阶段名 | 定义 id + 属性 + 阶段名 |
| UnknownModifierOp | 运算种类不在封闭集合内 | 定义 id + 修饰器索引 |
| OverrideWithStage | Override 修饰器绑定了阶段 | 定义 id + 修饰器索引 |
| UnknownMagnitudeKind | 幅度来源不在三种之内 | 定义 id + 修饰器索引 |
| NonPositiveDuration | Duration 效果的秒数不大于零 | 定义 id + 字段 |
| NegativeStackLimit | 层数上限为负 | 定义 id + 字段 |
| UnknownReapplyPolicy | 策略名不在枚举里（K23） | 定义 id + 字段 + 名字 |
| UnknownStackAggregation | 层数聚合方式不在枚举里 | 定义 id + 字段 |
| InvalidQuantum | 推进量子配置不大于零（代码常量配置错误） | 配置项（非内容定位） |
| ModifierWithoutMagnitude | 修饰器缺幅度参数（数据不完整） | 定义 id + 修饰器索引 |

### 7.2 运行期断言

| 问题种类 | 触发 | 发布期行为 |
| --- | --- | --- |
| ReaggregationMismatch | 提交值与重算值不一致（不变量被破坏） | 以重算值为准并记错误日志 |
| DuplicateEffectRemoval | 同一效果实例被移除两次 | 返回失败码，不改变数值 |
| AmbiguousOverridePriority | 同一属性上同 priority 的多个 Override | 取注册序最后者 + 错误日志 |
| NonFiniteCandidate | 候选值 NaN / Inf | 整批放弃提交 + 错误日志 |
| SettlementInFixedPhase | Fixed 相位调用结算或推进 | 返回失败码 |
| MissingSetByCallerKey | 调用方未提供声明的 SetByCaller 键 | 返回失败码，零状态变更 |
| DuplicateRegistrationOrder | 修饰器实例注册序冲突 | 丢弃新实例 + 错误日志 |
| AttributeSnapshotStale | 快照在批次内被二次读取且版本变化 | 以批次快照为准 + 错误日志 |

这些种类都符合 C20：断言不是唯一防线，发布期都有明确返回值或确定性兜底。

### 7.3 允许的降级

| 问题种类 | 触发 | 行为 | 关闭降级后 |
| --- | --- | --- | --- |
| NoOpEffect | 效果没有任何修饰器也没有任何 tag | 警告并允许（纯 tag 载体是合法用法） | 升为装载失败 |
| OptionalEffectMissing | 内容引用的可选效果定义缺失 | 警告并跳过该引用 | 升为未知内容 id |
| AttributeBasedSourceMissing | 施加上下文缺 source，而修饰器需要 Source 取值域 | 警告并把该修饰器贡献置 0 | 升为施加失败 |

### 7.4 调用方违约的归类

「SetByCaller 缺键」「在 Fixed 相位结算」「重复移除」都属于调用方违约而不是数据错误，统一落在**运行期断言**一级：调试期断言 + 打印不变量名，发布期返回结构化失败码且不改变状态。这样既满足 C17 的三级封闭（不新增级别），也满足 C20。目标侧准入失败不属于故障（它是合法业务结果），只返回失败码、不断言。

逐条判断：去掉 C++ 与 minEngine 的具体 API 之后，这一条是否仍然成立。

| 条目 | 判断 | 说明 |
| --- | --- | --- |
| 一个属性容器三段式、base 与 current 分离（K1–K4） | 成立 | 常量数据 / 运行期贡献 / 派生值三分是通用形状；任何语言都能表达 |
| 全量重聚合 + 永不逆运算（K4） | 成立 | 这是本 spec 最值得迁移的一条，与语言和引擎无关 |
| 修饰器分桶 + priority + 注册序全序（K7、K8） | 成立 | 纯算术与排序规则 |
| 可交换性分级（位级 / 相对容差）（K9） | 成立 | 浮点的结合律问题在任何语言里都一样；若目标语言用定点或大数，分级可升级为位级 |
| 阶段绑定「实体 × 属性」并由数据声明（K11） | 成立 | 数据形态，与承载方式无关 |
| 引用其他属性只读快照、不迭代（K10） | 成立 | 快照语义是通用做法 |
| 效果是内容定义、按 id 引用（K13） | 条件成立 | 需要「稳定 id + 注册表」；若目标引擎无资产对象，用 JSON 定义表替代，契约不变 |
| 修饰器在 DataAsset 里必须是 Instanced 对象数组（6.1） | **不成立（作为约束）** | 这是宿主反射没有 inline struct 的结果。迁移时应改为「值类型数组」，意图（嵌套内容的单一权威来源）成立 |
| 时长整数单元 + 单一 Advance 入口（K15、K16） | 成立 | 只要目标运行时能提供「一次推进」的调用点；事件驱动与 tick 驱动的切换条件同样适用 |
| 四组 tag 闸门语义（K17） | 条件成立 | 需要「层级字符串 tag + 集合判定」；无 tag 系统时用字符串前缀集合替代，规则不变 |
| 挂起与移除两态（K18） | 成立 | 状态机语义，与引擎无关 |
| 施加上下文冻结（K20） | 成立 | 冻结是让结算成为纯函数的前提 |
| 结算原子边界（先算后提交，K25） | 成立 | 与语言无关；单线程假设只是让实现更简单 |
| 通知去抖 + 无载荷 + revision 回查（K26） | 条件成立 | 需要「帧末 drain」或等价的批处理点；无事件系统时用「待通知集合 + 每帧一次派发」实现 |
| 只给 post 只读通知、不给 pre 钩子（K27） | 成立 | 这条是策略与机制分离的判据，任何框架都适用 |
| 只存 base 增量、不存派生（K29） | 成立 | 与引擎无关 |

结论：不成立项只有一条，且是宿主反射能力的限制而非设计意图；其余条目可原样写进另一种语言的实现。

## 9 与其它块的关系

### 9.1 依赖方向

- **本 spec 依赖**：CORE-F01（契约与分层）、CORE-F03（内容 id、注册表、EffectDef 作为内容定义一族的装载与校验）、CORE-F06（结算子系统所在的子系统宿主与 Variable 相位链）。
- **本 spec 被依赖**：CORE-F03（实例状态文档要容纳属性增量条目）、CORE-F04（装备对属性的贡献走修饰器路径而不是直接改 base，见 9.2）、CORE-F07（能力通过施加/移除效果改变数值）、CORE-F05（图节点推进可触发一次施加，但不改数值规则）。
- **禁止的反向依赖**：核心层的聚合函数不得调用注册表、资产、事件总线（C46）；适配层不得把结算规则复制一份（C4 / C29）。

### 9.2 真值归属（对齐 C31）

| 状态 | 真值持有者 | 只读访问者 |

| current 缓存 | 实例对象自身（唯一写入点是结算提交） | 全体（只读） |

## 10 实现波次与验收判据

### 10.1 波次归属

- **Wave1（与总纲第 9 节一致）**：属性容器三段式、修饰器三种运算与三种幅度来源、聚合与阶段、Instant 效果、结算原子边界、通知去抖、加载期问题项、持久化的增量条目。总纲 Wave1 的产物条目「属性与效果结算子系统（瞬时效果）」即本 spec 的 5.1–5.2 与 5.5–5.6 部分。
- **Wave4（与总纲 Q5 建议 a 一致，不新增波次）**：Duration / Infinite、推进入口、层数与重施加、四组 tag 闸门的完整形态、目标侧施加前准入。理由：这些机制由示例内容驱动（示例需要「增益 10 秒」「叠 3 层」），而 Wave1 的目标只是验证 base/current 重聚合；单列一个波次会与总纲第 9 节的四波结构冲突。若 Wave2 / Wave3 的验收必须先有持续效果，见第 11 节 Q7。

### 10.2 验收判据（可执行）

1. ctest 全绿，且下列用例存在并通过：K1–K30 每条至少一个用例（用例名是语义描述句，不含编号，C43）。
2. 重聚合对账，按波次拆成两段（原因见 10.3）：
   - Wave1：aggregate_twice_yields_bitwise_identical_result 与 instant_effect_leaves_no_residue 全绿——只有 Instant 效果时「聚合是确定函数」与「瞬时效果不残留」是可测的全部内容。
   - Wave4（有了 Duration 与层数之后）：reaggregation_after_effect_expiry_matches_fresh_container、removing_stacks_equals_reaggregation_without_them、inhibited_effect_contributes_nothing_but_keeps_stacks 全绿（这才是总纲 Wave1 判据 5 的完整语义）。
3. 可交换性：effect_apply_order_does_not_change_current_within_tolerance 与 cross_bucket_order_is_bitwise_stable 全绿，且用例里用相对误差比较。
4. 只存增量：save_load_save_is_byte_identical_with_live_effects 全绿，且序列化文档的字段表里 grep 不到 current（C11）。
5. 三级失败各有落点：装载期用例至少 6 个（未知属性 tag、未知阶段、Override 带阶段、未知重施加策略、非正时长、非法量子）；断言类用例至少 3 个（非有限候选、重复移除、Fixed 相位结算）；降级用例至少 1 个（NoOpEffect 且关闭降级开关后升为失败）。
6. 单一写入点审查项：current 的赋值点、base 的写入入口、剩余时长的写入点各只有一处（审查清单落进 PR 检查项）。
7. 核心层可迁移性：本 spec 的类型全部位于 mgf-core（属性值、修饰器、效果描述、聚合函数、问题种类），mgf-core 引擎符号 grep 为空（CORE-F01 的 4.2 检查项）。
8. 相位：settlement_in_fixed_phase_asserts 全绿，且发布期配置（断言关闭）下返回失败码（C20）。

### 10.3 与总纲 Wave1 判据 5 的张力（不自改总纲，提请作者裁定）

总纲 Wave1 验收判据 5 写的是「施加与移除效果后当前值与从基值重算一致」，而总纲 Q5 建议 a 主张 Wave1 只做瞬时效果。瞬时效果不驻留，因此 Wave1 里**没有可被「移除」的对象**，该判据无法按字面执行。三条可选处置（不自行决定）：

- (a) Wave1 纳入一个最小驻留形态（Duration 的最简实现，无层数、无阶段），使判据 5 可原样执行；
- (b) 把判据 5 改写为「瞬时效果施加后 current 与从基值重算一致」，把「施加与移除」的对账整体推到 Wave4；
- (c) 保留字面判据，但在 Wave1 用「施加 → 显式移除」的测试形态验证——这需要 Wave1 就有驻留效果，实际等同于 (a)。

本 spec 的 §10.2 判据 2 按 (b) 拆分表述，因为它不改总纲且不引入半成品路径；若作者选 (a)/(c)，只需把 Wave4 的三条对账用例前移到 Wave1，其余契约不变。

## 11 待决问题

每条给选项、我的建议、什么会推翻建议。建议不是决定。

**Q1 阶段声明的粒度。** 选项：(a) 绑定「实体 × 属性」，每个实体定义可给每个属性声明自己的阶段顺序；(b) 全局每属性一种顺序（只在属性定义处声明一次）。
建议 (a)。理由：同一属性在不同实体上的上游需求不同（角色需要装备区与 buff 区，环境物件不需要），(b) 会逼出「用一个全局最长的阶段表给所有实体」的隐式耦合。
什么会推翻它：若实践中所有实体对同一属性都用同一种顺序，(b) 更省一次查询与一层间接。

**Q2 引用其他属性是否做不动点迭代。** 选项：(a) 单次快照，最多一次结算延迟；(b) 迭代到收敛（带上限）。
建议 (a)。理由：收敛性需要内容作者证明，成本不可预测，而 (a) 的延迟是可测量的常数。
什么会推翻它：若出现「A 依赖 B 当前值且 B 依赖 A 当前值」的内容需求，且一次延迟在玩法上不可接受（例如护甲与减伤互为函数并要求同帧稳定）。

**Q3 效果集合是否持久化。** 选项：(a) 不持久化，读档后由上层重建；(b) 持久化 Duration / Infinite 效果，含剩余单元。
建议 (a)。理由：效果携带施加上下文（实体引用、SetByCaller 表、source），跨会话重建这些引用的语义成本远高于「重施加一次」；而 C11 的文档形状里本来就没有这一段。
什么会推翻它：出现「读档后 buff 必须仍在且剩余时长精确」的产品需求；那时需要为跨存档效果设计一套只含 ContentId、层数与剩余单元的窄持久化形态。

**Q4 ongoingTagRequirements 失效时挂起还是移除。** 选项：(a) 挂起，条件恢复后继续；(b) 直接移除。
建议 (a)。理由：移除会丢层数与剩余单元，恢复时无法还原；且移除/重施加会推进施加序号，把一次临时条件变化变成永久的顺序扰动。
什么会推翻它：若挂起态在查询与表现层的成本高于重建效果（例如需要给 UI 一份「被抑制的效果」列表且这层耦合不可接受）。

**Q5 「累加幅度」重施加策略是否进 V1。** 选项：(a) 不进枚举（V1 只有刷新时长与叠层）；(b) 进枚举并完整实现；(c) 进枚举但运行期忽略。
建议 (a)。理由：它的语义成本最高（幅度随重施加无界累积、移除时「撤哪一份」没有唯一答案、幅度变成施加历史的函数，与可交换和可对账冲突）。(c) 被明确禁止——那正是原型里「数据声明了但没实现」的坑（K23）。
什么会推翻它：若示例内容需要「同一 buff 连续叠加幅度但不加层」（例如层数不变但每层更强），则需要 (b)，且必须先写清上界与移除对齐规则。

**Q6 层数进入数值的默认方式。** 选项：(a) 每层独立贡献（Multiply 上是 m 的 n 次幂）；(b) 幅度乘层数（m·n）。
建议 (a)。理由：与「集合重算 + 全序 + 移除即删元素」全部同构，不需要第二套算术；幂也是内容作者对「每层再乘一次」的直觉。
什么会推翻它：若内容作者普遍写「每层 +10% 伤害」而实际期望线性叠加，那说明他们本该用 Add 修饰器，(a) 不应为此改语义——只有在出现「Multiply 但期望线性」的强制用例时才改默认。

**Q7 Duration / Infinite 与层数的波次归属。** 选项：(a) 落在 Wave4（不新增波次）；(b) 新增一个 Wave1 之后的独立小波次。
建议 (a)。理由：总纲第 9 节是四波结构，新增波次需要先改总纲；这些机制由示例内容驱动，与 Wave4 同批的成本最低。
什么会推翻它：若 Wave2（背包）或 Wave3（图）的验收必须先有持续效果（例如装备套装效果需要驻留期），则必须提前，且应回到总纲调整波次而不是在本 spec 里私开一个波次。

**Q8 定点化何时做。** 选项：(a) 只登记技术债，触发条件满足时再做；(b) Wave1 就做。
建议 (a)。理由：见 4.2；当前没有任何用例需要位级确定性。
什么会推翻它：出现必须以位级一致性验收的用例（回放推进、联机校验），或目标平台浮点差异导致同一份内容的数值在不同机器上不可比。

**Q9 周期性结算（period）是否进 V1。** 选项：(a) 不做，重复结算由能力层「多次施加 Instant」表达；(b) 做 period 字段。
建议 (a)。理由：period 会让「一次结算」的原子边界与「一帧内同一效果结算多次」耦合，需要新的推进规则（一帧内补算几次、欠账怎么算），而价值可以由 Instant 的组合表达。
什么会推翻它：若出现必须在单个效果内表达「每 N 单位跳一次」的内容（例如持续伤害），且用能力层组合会造成效果数量爆炸。
