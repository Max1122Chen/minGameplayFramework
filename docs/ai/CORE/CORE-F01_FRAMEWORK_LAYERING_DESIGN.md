## 1 问题陈述

仓库当前只有协作规范，没有分层、没有代码、没有任何跨块约定。接下来的七份设计文档（F02–F07 与 INFRA-F01）会并行撰写；如果它们各自发明「内容 id 长什么样」「实例状态怎么存」「加载失败怎么办」「谁来持有真值」，集成时就会出现一批无法调和的差异——每份文档单看都自洽，合起来跑不通。这是本总纲要解决的第一件事。

第二件事是引擎缺口。参考宿主 minEngine 提供了反射、序列化、资产系统、子系统与事件总线，但它没有 Gameplay Ability System，没有 SaveGame 设施，DataAsset 的反射属性**不支持 inline struct**（只有 primitive / object / objectptr / array / delegate 五类），GameplayTag 只能在静态构造期注册、未知 tag 走 Log+Assert，GameplayTagContainer 持有 manager 裸指针因而不可序列化。这些缺口如果散落在各 spec 里被各自绕过，同一个坑要踩七次，而且每个 spec 会绕出不同的形状。

第三件事是迁移愿景。仓库的成功判据是「去掉 C++ 与 minEngine 的 API 之后这条设计仍然成立」。若不在总纲里显式切出可迁移层，设计会在实现过程中被引擎细节慢慢污染，等到想迁移时已经无法把「设计」从「实现」里剥出来。

因此本文档的定位是：**先定分层、依赖方向与跨块契约，再让其余六份 spec 逐条遵守**。它不描述某个 Feature 的内部实现，只描述所有 Feature 必须共处的规则面。

### 1.1 本文档依据的事实基线

以下事实来自对参考宿主的调研，本文档的所有约束都在它们之上成立；后续 spec 若与它们冲突，以事实为准并回来修本文档。

| 事实 | 对本设计的含义 |
| --- | --- |
| `GameInstance` 是会话宿主（Standalone 一份、PIE 每实例一份），引擎只提供 `CreateGameInstance` / `CreateGameInstanceForPIE` 工厂，运行期不自动创建，类可由项目设置 `GameInstanceClass` 指定 | 框架通过「指定 GI 子类 + 宿主显式创建」注入自己，不另造会话单例 |
| 子系统家族（Engine / GameInstance / World / Tickable 变体）由反射发现、SubsystemCollection 拥有，初始化与关闭顺序由引擎决定 | 全局服务一律做成子系统；跨子系统依赖必须惰性获取，不得假设初始化顺序 |
| `LogicalTick` = Fixed 相位 → Variable 相位；Fixed 相位每步派发 GI 的 `OnFixedTick`，**不会自动遍历 GI 子系统** | 派生 GI 必须自己派发固定步长；框架的更新模型必须写明这一条 |
| `GameplayTag` 身份是 TagName 字符串，只能静态构造期注册，未知 tag Log+Assert；`GameplayTagContainer` 计数式、不可序列化 | tag 词汇表是代码契约；持久化 tag 集合必须写名字符串再重建容器 |
| `GameplayEventSystemComponent` 是 Scene 作用域组件，channel 用 GameplayTag，同步单线程，无队列无 payload，重入深度上限 16，`OnDeactivate` 全退订 | 事件只做冒泡通知；订阅走 RAII 句柄；顺序与重入不能成为语义依赖 |
| DataAsset 由 `DataAssetLoader` 按 `AssetMeta::RuntimeClassName` 多态实例化，反射属性**无 inline struct 类别**，但数组 + Instanced 对象引用可用 | 内容定义用 DataAsset 派生类；嵌套内容用 Instanced 对象或扁平化为内容 id 引用，不能内联 ME_STRUCT |
| 序列化由反射驱动（JSON / Binary Archive），带 `schemaVersion` 与 `engineVersion` 闸；**没有 SaveGame 设施**（无存档槽、无迁移层），二进制存盘未做 | JSON 是唯一存盘路径；版本与迁移策略由框架自带；存档槽不做，登记技术债 |
| 模块契约：游戏 SHARED 模块必须导出 C 符号 `MinEngine_GameModuleEntry`，由宿主链接期强制引用，无运行期热插拔 | 框架的装配入口只有一个，且是静态链接期确定的 |
| 引擎无 GAS，执行模型单线程同步 | 「小 GAS」完全由本仓设计并自建；并发问题在第一版不进入设计范围 |

## 2 目标与非目标

### 2.1 目标

- **G1 一份可被逐条引用的跨块契约。** 第 5 节的契约条目必须能写成测试或检查项，其余六份 spec 逐条对齐，冲突处必须回来改本文档而不是各自例外。
- **G2 一条可执行的可迁移判据。** 明确划出核心可迁移层与引擎适配层，并给出「核心层不得出现引擎符号」的可检查判据（第 4.3 节）。
- **G3 一张与既有引擎机制的三栏边界表。** 复用 / 包装 / 自建，逐项落到具体机制名（第 8 节），避免重复造轮子，也避免把引擎没做的事假装成引擎会做。
- **G4 一套三级失败策略。** 加载期 fail-fast / 运行期断言 / 允许的降级，逐类故障归位（第 5.4 节）。
- **G5 一条从设计到可运行载体的路径。** 四波实现，每波都有可编译、可验证产物（第 9 节）。
- **G6 一个统一的实例状态形态。** 「实例 = Definition 引用 + tag 键的增量属性表 + 显式 fragment 覆盖列表」成为所有 gameplay 对象的唯一形态，不再有枚举键方案。

### 2.2 非目标

- 不做编辑器工具面板。第一版保留编辑器宿主，但只用于填写 DataAsset；任何「可视化编辑 gameplay 数据」的面板都在范围外。
- 不做 SaveGame 存档槽、自动存档、跨版本存档迁移层。只做实例状态快照的序列化契约（第 5.3 节），存档产品化登记为技术债。
- 不做网络同步、不做多线程安全设计。执行模型按单线程同步假设；任何引入并发的改动都需要新文档。
- 不设计渲染、物理、输入、音频；框架只消费它们的信号。
- 不定具体数值、平衡与玩法内容。示例内容在 Wave4 才落地，且只用于验证契约。
- 不做资源热重载与运行期内容注册。内容包在加载闸口一次性装载。
- 不提供运行时反射注册内容类型；新增内容片段种类必须改代码（第 5.2 节）。

## 3 术语表

| 术语 | 定义 | 归属层 |
| --- | --- | --- |
| 内容定义 Definition | 只读的内容原型：id、装配的片段、静态数值。对应引擎里的一份 DataAsset 资产 | 核心概念 / 适配层载体 |
| 内容 id ContentId | `(kind, name)` 二元组，name 是稳定 ASCII 字符串。定义之间互相引用的唯一形态 | 核心 |
| 片段 Fragment | 附加在定义或实例上的行为与数据块，用种类（kind）判别，用显式覆盖列表在实例层面改写 | 核心概念 / 适配层载体 |
| 实例 Instance | 运行期可写对象：Definition 引用 + tag 键的增量属性表 + 显式 fragment 覆盖列表 | 核心概念 / 适配层载体 |
| tag 键 TagKey | 用 GameplayTag 名字符串做键，替代枚举键。用于实例增量的索引与准入判定 | 核心值类型 / 适配层绑定 |
| 属性基值 AttributeBase | 由定义与片段共同给出的、未经效果修改的值 | 核心 |
| 属性当前值 AttributeCurrent | 由基值 + 生效修饰器**全量重聚合**得到的值，不做逆运算 | 核心 |
| 修饰器 Modifier | `(op, magnitude, priority, sourceTag)` 描述的一次加减乘；合成规则确定且可排序 | 核心 |
| 效果 Effect | 一组修饰器 + 施加条件 + 生命周期描述；结算单位 | 核心 |
| 内容注册表 ContentRegistry | 加载期把所有定义装入的内存索引，按 ContentId 查询；由 GameInstance 子系统持有 | 适配层（装配）/ 核心（查询契约） |
| 内容包 ContentPack | 一组定义资产 + 一份索引资产的装载单位 | 适配层 |
| 图文档 GraphDoc | 节点 id 集合 + 边集合 + 节点 payload 引用 + 节点状态表（决策状态 Active/Done 必须持久化，派生状态 Locked/Available 加载后重算） | 核心（结构）/ 适配层（资产） |
| payload | 挂在图节点上的多态对象，一种图对应一种解析业务，内部再用 GameplayTag 指向技能/科技等内容 | 适配层（反射派生）/ 核心（接口） |
| 背包语义 Inventory | 只有接口语义（TryAdd / TryRemove / TryQuery）的容器抽象；容量策略由派生类与数据共同决定 | 核心（语义）/ 适配层（派生实现） |
| 槽位 Slot | 背包抽象里的一个持有单位；语义由派生类定义（不可上限 / 有上限 / 可扩容） | 核心 |
| 几何 Geometry | 物品实例上由片段赋予的多格占位信息；与之配对的二维网格由背包派生类持有，是**另一套坐标** | 核心概念 / 适配层载体 |
| 核心可迁移层 Core | 只依赖语言标准库、不出现任何引擎符号的层 | — |
| 引擎适配层 Adapter | 把核心层规则接到反射、资产、序列化、子系统、事件总线上的层 | — |
| 组合根 Composition root | 唯一知道全部实现并完成装配的地方（游戏 SHARED 模块入口） | 适配层 |
| fail-fast | 发现不可恢复的内容错误时立刻终止加载并给出完整问题列表，不猜测、不修补 | 契约 |
| 加载闸口 Load gate | 允许执行资产装载的明确时刻（启动、切场景、显式请求），tick 中不允许 | 契约 |
| 波次 Wave | 一段可独立编译、独立验收的实现阶段 | — |

## 4 分层与依赖方向

### 4.1 模块清单与职责

模块名是构建目标名，不是类名；迁移到其他语言时目标名可换，职责划分必须保留。

| 模块 | 层 | 负责 | 不负责 | 产物 |
| --- | --- | --- | --- | --- |
| `mgf-core` | 核心可迁移层 | ContentId、TagKey 值语义、属性值类型与聚合规则、修饰器与效果描述、增量表与覆盖列表的数据形态、图文档结构与校验规则、背包接口语义与结果码、失败问题列表类型 | 反射注册、资产加载、落盘、子系统挂载、事件投递 | 静态库，无引擎依赖 |
| `mgf-engine-adapter` | 引擎适配层 | ME 反射类型（定义类、实例类、payload 类）、AssetManager 装载、Serializer 读写与版本闸、Subsystem 实现、GameplayTag 绑定与校验、事件总线 RAII 适配 | gameplay 规则的判定逻辑（必须调用核心层） | 静态库，链接 minEngine |
| `mgf-game-module` | 组合根（SHARED 游戏模块） | 导出 `MinEngine_GameModuleEntry`；装配注册表与子系统；声明 GI 子类与项目设置；提供内容包清单 | 规则实现、宿主窗口与循环 | SHARED 动态库 |
| `mgf-game-host` | 宿主 | 进程启动与关闭、`CreateGameInstance` / `CreateGameInstanceForPIE` 的调用点、帧循环驱动 | gameplay 逻辑 | 可执行文件 |
| `mgf-editor-host` | 宿主 | 打开工程与资产、填写并保存 DataAsset；**无 gameplay 面板** | gameplay 逻辑 | 可执行文件 |
| `mgf-tests` | 验证 | doctest 测试可执行 + ctest 注册；每个契约条目至少一个用例或一条检查命令 | 生产逻辑 | 测试可执行 |

装配只有一个入口：游戏 SHARED 模块的 C 入口。宿主不得自己拼装注册表，适配层不得在静态初始化期装配（静态初始化顺序不可控，且 tag 注册是唯一允许的静态构造期动作）。

### 4.2 依赖方向（禁止反向依赖，给依赖图）

```text
  mgf-game-host        mgf-editor-host
        \                  /
         v                v
         mgf-game-module   (组合根, SHARED, 导出 C 入口)
              |       \
              v        \  (测试可直连核心层)
   mgf-engine-adapter   mgf-tests
              |
              v
           mgf-core
```

外部依赖只有一条：`mgf-engine-adapter`、`mgf-game-module`、宿主与测试链接 minEngine。`mgf-core` **不链接** minEngine，也不 include 其任何头文件。

禁止的反向依赖（每条都是可检查项）：

1. `mgf-core` 不得 include minEngine 头、不得 include `mgf-engine-adapter` 头。
2. `mgf-engine-adapter` 不得 include 宿主的头、不得包含宿主入口逻辑。
3. `mgf-game-host` / `mgf-editor-host` 不得被任何库依赖；库不知道宿主存在。
4. 任何模块不得绕过组合根自行注册子系统或装载内容包。
5. 横切共享代码只能下沉到 `mgf-core`，不得在模块之间互 include 实现文件。

检查方式：构建系统按 target 声明 include 目录与链接库；另有一条 CI 检查 —— 在 `mgf-core` 源码上执行 `grep -rn "minEngine\|ME_CLASS\|ME_STRUCT\|ME_PROPERTY"`，结果必须为空。

### 4.3 引擎面与语言面：可迁移边界

**判据（唯一一条）**：任何进入核心可迁移层的类型、函数、文件，都不得出现 minEngine 符号 —— 不 include 引擎头，不继承引擎基类，不使用 `ME_*` 宏，不出现引擎类型名（`MEObject`、`DataAsset`、`AssetHandle`、`GameplayTag`、`GameplayTagContainer`、`Subsystem` 及其变体），不依赖引擎的字符串/容器/智能指针别名。核心层只用语言标准库与自定义值类型。

核心可迁移层装什么（剥离引擎后仍成立的**规则与值**）：

| 核心层内容 | 为什么可迁移 | 引擎侧对应物（仅适配层出现） |
| --- | --- | --- |
| `ContentId{kind, name}`、名字合法性规则、稳定 id 承诺 | 任何引擎都有「稳定字符串 id + 种类分片」的需求 | DataAsset 资产路径、AssetMeta |
| `TagName` 值类型与层级语义（`A.B.C` 隐含父） | tag 是通用词汇表概念 | `GameplayTag` 句柄、`GameplayTagManager` |
| `AttributeValue` / `AttributeModifier` / 聚合函数 | 纯算术与排序规则 | ME_STRUCT 包装、反射属性 |
| 增量属性表与显式覆盖列表的数据形态与合并规则 | 结构本身与引擎无关 | 反射数组属性、Instanced 引用 |
| 效果描述（修饰器集合 + 准入条件 + 生命周期枚举） | 结算规则 | DataAsset 字段 |
| 图文档结构（节点/边/payload 引用/派生状态）与校验规则 | 图是数学对象 | DataAsset + 多态 MEObject |
| 背包接口语义（TryAdd/TryRemove/TryQuery 的返回与不变量）与容量策略接口 | 契约与能力模型 | 反射派生类 |
| 失败问题列表（kind + 位置 + 细节）与三级失败分类 | 诊断模型 | 日志、断言宏 |
| 事件通道名（tag）、事件种类枚举、订阅句柄契约 | 通知模型 | `GameplayEventSystemComponent` |

引擎适配层装什么（把规则接到宿主上）：

- 反射注册：`ME_CLASS` / `ME_STRUCT` / `ME_PROPERTY` / header-tool 生成的反射代码、`ObjectManager::NewObject` 的实例化工厂。
- 资产加载：DataAsset 派生定义类、`DataAssetLoader` 的多态实例化、`AssetManager` 的 AssetTypeId 分派、内容包索引。
- 序列化落盘：`Serializer` / Archive、`ToFile` / `FromFile` / `ResolvePendingObjectRefs`、`DiskVersion` 闸。
- 子系统挂载：`GameInstanceSubsystem` / `WorldSubsystem` / Tickable 变体、SubsystemCollection 的初始化顺序。
- 事件总线：`GameplayEventSystemComponent` 的 `Dispatch` / `Subscribe` / `Unsubscribe`，包成 RAII 句柄。
- tag 绑定：静态构造期注册、名字↔句柄转换、`GameplayTagContainer` 的构造与查询。

判据的落地检查（三条，均可在 Wave1 起执行）：

1. `mgf-core` 全源码 grep 引擎符号为空（见 4.2 检查方式）。
2. `mgf-core` 的编译单元只依赖标准库与自身头文件（构建 target 上不挂引擎链接）。
3. 核心层的头文件里，每个公开类型的字段类型都能用「另一个语言重写为等价 struct」来描述；出现无法描述的字段即为越界。

## 5 跨块契约（最重要的一节，其余 spec 必须逐条遵守）

本节每条契约都是可检验的陈述：体例为「规则 + 可检验」。编号 C1..C47 供其他 spec 引用，例如「背包容量策略遵守 CORE-F04 的契约」。每条若有实现形式差异，必须回来改本文档，不允许单点例外。

### 5.1 内容与实例的身份规则（稳定 id、引用形态、AssetRef vs 裸指针）

**C1 内容 id 是二元组且全生命周期稳定。** 每份内容定义携带 `ContentId{kind, name}`；`name` 限定为 `[A-Za-z0-9_.-]` 的 ASCII 串，同一 `kind` 内全局唯一。发布后的 id 不得修改；资产文件改名、移动、拆分都不改 id。id 由数据显式给出，不由资产路径推导。
可检验：注册表装载时对重复 id 与非法字符各自报一条问题项；同名不同 kind 允许通过；有一条用例把资产挪到别处后仅按 id 仍能查到定义。

**C2 定义之间的引用一律用 ContentId，不用资产引用。** 规则字段（例如「掉落物引用」「前置科技引用」「payload 指向的技能」）只允许 `ContentId` 类型；资产引用（路径、句柄）只允许出现在装载边界——内容包索引、关卡/场景引用、宿主配置。理由：资产引用把加载顺序与依赖图泄露进 gameplay 规则，且无法用 id 做跨包重定位。
可检验：核心层的规则结构体字段类型里不出现任何资产类型；测试在定义 A 引用定义 B 时，允许 B 尚未装载，解析在装载后统一完成（C13）。

**C3 AssetRef 是加载期的强引用，ContentId 是内容层的弱引用。** 资产句柄只在装载期存在，装载完成后运行时对象一律通过注册表按 id 查询；不得把资产句柄存进实例状态、不得跨子系统传递裸指针作为长期引用。
可检验：实例的持久化数据里不含句柄或指针；注册表对外只给 const 访问（C4）。

**C4 内容定义只读，可写状态只在实例上。** 注册表返回的句柄是 const 语义；实例构造、片段挂载、效果施加都不得写回定义字段。
可检验：走「创建一个实例 → 施加效果 → 读回定义」的用例，定义字段逐字段与装载时一致。

**C5 实例状态只有三段，不再有枚举键。** 实例 = `Definition 引用（按 ContentId）` + `tag 键的增量属性表` + `显式 fragment 覆盖列表`。这三段之外不允许出现「实例私有字段白名单」；需要新状态时，是新增一个片段或一条 tag 键，不是给实例类加属性。（消歧）「tag 键的增量属性表」与属性容器是同一结构：容器有 base / 修饰器集合 / current 三个隔间，增量表只是 base 隔间的持久化投影；current 与修饰器集合不落盘，读档后重聚合重建。
可检验：实例类的反射属性集合与这三段一一对应；新增一种状态不需要改实例类的字段表（用例：通过内容装配一个带新 tag 键的实例，不改代码）。

**C6 定义只存基值，不存派生值。** 定义里不得出现「当前值」「已结算值」「缓存结果」；所有派生值在装载或变更后由重聚合得到（重聚合规则见 CORE-F02）。
可检验：定义类的字段表里没有语义为 current/cached 的字段；有一条对账用例在装载后重算并比对。

### 5.2 数据驱动边界（什么进 DataAsset、什么必须进代码）

**C7 可以只存在于数据里的三样东西**：数值与开关、装配关系（哪几个片段、片段参数、引用哪些内容 id）、以及内容包的组织（哪些定义属于哪个包）。这三样改动不得要求重新编译。
可检验：仅修改数值与装配关系后，不重建二进制即通过装载与全部契约用例。

**C8 必须存在于代码里的五样东西**：GameplayTag 词汇表（引擎只允许静态构造期注册）、片段种类枚举（判别串）、错误与问题种类、结算与聚合规则、序列化 schema 版本与迁移分支。任何「需要新代码分支才能执行的新语义」都必须先在代码里取得契约身份。
可检验：新增一种片段必然伴随代码变更（枚举 + 规则实现）—— 用例：在数据里写一个未注册的片段种类，装载必须失败并指出未知种类；仅改数值不得失败。

**C9 反射限制决定嵌套形态。** 由于反射属性没有 inline struct 类别，任何嵌套内容只能有两种形态：改用 Instanced 对象引用（一对一）或在数组中放 Instanced 对象（一对多），或者扁平化为 `ContentId` 引用交由注册表解析。禁止把 ME_STRUCT 直接作为 DataAsset 的反射属性。
可检验：定义类的属性表里没有 struct 类别属性；有一个 header-tool 生成结果检查项（生成代码里 struct 属性数为零）。

**C10 内容包是一份索引加若干定义资产。** 装载以「包」为单位，包内定义互相引用必须闭包可解析；跨包引用必须在包依赖声明里列出，否则装载期报错误。内容包索引必须显式声明它**提供**的定义集合与它**依赖**的定义集合；闭包在装载前算完，装载后与注册表实际结果交叉核对，不一致即问题项。
可检验：故意制造跨包引用但不在依赖声明里，装载失败并指出缺失的包。

### 5.3 序列化契约（schemaVersion、只存增量不存派生、引用解析时机、失败策略）

**C11 只存增量与身份，不存派生。** 持久化文档内容 = 实例身份 + Definition 的 `ContentId` + tag 增量表 + 显式覆盖列表 + 文档 `schemaVersion`。由定义推导出来的字段、由修饰器算出的当前值、图节点的派生状态一律不写盘。持久化形状不含效果实例集合与修饰器集合；因此跨存档的持续效果（buff）不在本框架保证范围内，读档后由上层按需重新施加。
可检验：对同一实例执行 save→load→save，两次字节序列等价（属性按确定顺序输出）；文档里不含当前值字段。

**C12 每类持久化文档带整型 schemaVersion，缺失或未知一律拒绝。** 版本号是文档自身字段，与引擎的 `$engineVersion` 闸各管一段（引擎管二进制兼容，我们管语义兼容）。当前版本只有一条路径：版本等于 1 正常读，其他值拒绝并报问题项。不写「空迁移函数」。
可检验：把 `schemaVersion` 改成 0 或 2，装载失败并说明不支持的版本。

**C13 引用解析分两段，失败不静默。** 第一段反序列化只还原结构与 id；第二段在引擎完成对象引用解析（`ResolvePendingObjectRefs`）之后，按 id 从注册表解析强引用。解析失败的条目全部收集成问题列表，不逐条静默置空。**本条同时约束资产装载路径**：资产侧内部对象引用（含片段对象、payload 对象）同样两段解析，第一段只还原结构与 id，第二段在引擎完成对象注册后进行；未完成第二段前不得做片段/payload 校验。
可检验：构造一份引用了不存在 id 的文档，装载返回包含全部缺失 id 的问题列表（至少两条同时报告）。

**C14 「省略」与「显式为零」必须可区分。** 增量表用「条目存在性」表达覆盖，不能用哨兵数值表达；反序列化后条目数必须与序列化前一致。
可检验：写入一条值为零的增量后往返，条目数不变且查到的是零而不是默认值。

**C15 不提供存档槽与跨会话迁移。** 本框架只保证「实例状态快照」的自洽往返；存档槽、自动存档、旧版本内容迁移、在线存档兼容全部在范围外，登记为技术债，由使用方在其上层实现。
可检验：代码里不存在存档槽概念；文档里有一条技术债引用（TECH_DEBT 中已登记）。

**C16 写盘不在 tick 内发生。** 序列化与落盘只允许在加载闸口或显式请求路径上执行（与 C26 一致）。
可检验：tick 路径的调用图上不出现序列化 API（代码审查项 + 一条运行期断言：tick 深度大于零时序列化入口直接返回失败）。

### 5.4 校验与失败策略（加载期 fail-fast / 运行期断言 / 降级；三级表格）

**C17 三级归类是强制的，每一类故障必须落进其中一级。**

| 级别 | 判据 | 行为 | 例子 |
| --- | --- | --- | --- |
| 加载期 fail-fast | 由数据或代码词汇表不一致引起，且无法在运行期安全猜测 | 终止装载，返回**完整**问题列表（不只第一条），不启动内容 | 重复/非法 ContentId、未注册的 tag、未知片段种类、未知 schemaVersion、包引用不闭包、图节点 id 重复、边指向不存在节点、payload 类型不在白名单、背包容量为负 |
| 运行期断言 | 框架不变量被破坏，说明代码有 bug 而非数据有错 | 调试期断言并打印不变量名与上下文；发布期走兜底返回值 + 错误日志，不继续执行非法状态 | 重聚合后当前值与缓存不一致、同一个效果被重复移除、容器内数量为负、订阅句柄双重释放 |
| 允许的降级 | 只影响可选内容的完整性，不影响核心状态一致 | 记录警告并继续，且必须能通过开关关闭降级（关闭后升为 fail-fast） | 可选片段缺失实现（跳过该片段；指**数据引用了未编译进当前二进制的可选片段种类**，装载期报一条降级问题并跳过该片段——这不是「新增片段无需改代码」）、可选边目标缺失（丢弃该边）、内容包为空（允许启动空注册表） |

可检验：每一类都有一条对应用例（装载失败返回问题列表 / 断言在不变量被破坏时触发 / 降级产生警告且开关关闭后变为失败）。

**C18 错误聚合优先于快速中断。** 装载期所有校验必须先把问题收集完再一次性返回，问题项包含种类、定位（哪份定义、哪个片段、哪个字段或索引）与细节文本。
可检验：一份同时含三种错误的资产，返回的问题项数量为三。

**C19 未知 tag 是 fail-fast，不是警告。** 内容里出现的每个 tag 名字都必须在词汇表里已注册；未注册的 tag 每个报一条问题，并在消息里给出「需要新增的词汇表条目名」，让修复动作明确。
可检验：写一个不存在的 tag 进内容，装载失败且消息包含该 tag 的完整名字。

**C20 断言不得成为唯一防线。** 任何依赖断言的路径都必须同时给出发布期行为；断言关闭后不允许出现未定义行为或静默错误状态。
可检验：以断言关闭配置运行同一套用例，非法输入仍返回失败结果码。

**C21 失败状态对调用方可见且不可忽略。** 装载/操作入口返回结构化结果（成功 / 问题列表 / 失败种类），不得用布尔 + 全局标志；调用方忽略结果时，调试期断言提示。
批量操作可以返回「部分接受」的聚合摘要，但必须同时携带每一个被拒项的独立原因，且不得用于掩盖整体失败；单条操作只有成功/失败两档。
可检验：所有公开操作入口返回结果类型；有一条静态检查项：值为布尔且语义为「是否成功」的公开函数为零；批量入口的聚合结果可逐项枚举被拒原因。

### 5.5 更新与通知模型（tick 相位、事件驱动、禁止在何处做重活）

**C22 状态变更只在 Variable 相位发生。** 属性结算、效果到期推进、背包变更、图迁移的脚步都挂在 Variable 相位（GI 的 Tickable 子系统 → Scene WorldSubsystem → Scene::Tick 这条链上）。Fixed 相位只做与固定步长强相关的推进，且必须由 GI 子类显式派发 —— 引擎不会自动遍历 GI 子系统。`GameInstance::TickSubsystems` 的遍历顺序 = 子系统集合的创建顺序，引擎不保证其语义顺序；任何跨子系统的帧内次序必须由单一帧驱动器显式固定（C30）。
可检验：一条运行期断言在 Fixed 相位调用通用的「结算/变更」入口时报错；GI 子类里能定位到显式派发 Fixed 步进的代码点。

**C23 不在 tick 里做重活。** 资产装载、内容包解析、tag 词汇校验、序列化写盘、创建/销毁实例这类操作必须在加载闸口或显式请求路径上完成。tick 里的工作上限：遍历已知集合 + 纯算术 + 事件投递。
可检验：tick 调用图不触达装载/序列化/反射实例化 API（审查项 + 一条计数器用例：一帧内反射实例化次数为 0）。

**C24 事件只做冒泡通知，不做载荷传输。** channel 用 GameplayTag；事件里不带业务数据；需要数据的接收方回查注册表或实例（单一真值，C31）。
可检验：事件类型定义里只有通道（tag 容器）一个字段；发送者与业务数据一律不可用，接收方自行回查（C31）——存在用例证明接收方回查后得到与发送方一致的状态。

**C25 订阅必须用 RAII 句柄，禁止裸回调长期驻留。** 句柄析构即退订；销毁顺序敏感的对象必须在 `OnDeactivate` / `Shutdown` 里让句柄先失效。
可检验：对象销毁后再广播，不崩溃且不再回调；句柄双重释放触发断言（C17 运行期断言类）。

**C26 广播期间不得改动订阅集合。** 订阅/退订请求在广播过程中被排队，广播结束（帧末 drain）后统一生效；禁止依赖「新订阅在本次广播中立刻收到」。
可检验：在一次广播里订阅同一通道，本次广播不触发新订阅，下一次触发。

**C27 不依赖广播顺序与重入深度。** 引擎重入上限是 16，是硬限不是语义承诺；任何对顺序敏感的流程必须写成显式状态机（在 Variable 相位推进），不得串成事件链。
可检验：审查项——不存在「A 事件处理中派发 B 事件并依赖 B 先完成」的路径；状态机推进有独立用例。

**C28 通知去抖。** 同一帧内对同一对象的同类变更合并为一次通知，按 (对象, 通道) 去重；去重不丢最后一次状态。
可检验：一帧内对同一对象连续改三次，接收方收到一次通知且读到最终状态。

**C29 每个状态只有一个写入点。** 属性只能由效果应用/移除路径修改；背包只能由 TryAdd/TryRemove 路径修改；图状态只能由迁移路径修改。其他模块只读。
可检验：审查项 + 一条用例：直接调用底层写接口在调试期断言失败。

### 5.6 子系统与所有权（谁持有真值、生命周期、PIE 隔离）

**C30 全局服务一律是子系统，不造并行 Manager 单例。** 复用引擎的 Engine / GameInstance / World 子系统与 Tickable 变体；选择判据是生命周期：跨场景且随会话 → GameInstance 子系统；随场景 → World 子系统；进程级且无会话状态 → Engine 子系统。
可检验：代码里没有自造的全局单例注册表；每个服务都能在子系统的反射列表里找到。

**C31 真值归属表是强制的。**

| 状态 | 真值持有者 | 生命周期 | 只读访问者 |
| --- | --- | --- | --- |
| 内容定义与注册表 | GameInstance 子系统（内容注册表） | 随会话，跨场景 | 所有 gameplay 模块 |
| 属性与效果实例状态 | 实例对象自身（由所属子系统持有句柄） | 随实例 | 结算子系统、UI |
| 背包实例状态 | 背包实例自身，由所属子系统持有 | 随实例 | 装备、交易 |
| 图文档与派生状态 | 图实例（由持有者子系统管理），派生状态可重算 | 随实例 | 任务/科技模块 |
| 事件总线 | Scene 作用域组件（引擎机制） | 随场景 | 全体（只投递） |
| 加载问题列表 | 装载器（一次性产物） | 装载期 | 宿主、编辑器 |

可检验：每个状态在表里唯一一行；审查项——不存在两个模块同时写同一状态。

**C32 PIE 隔离。** 所有 gameplay 状态必须挂在 GameInstance 或 Scene 上下文中，禁止静态/全局可变状态（词汇表注册除外，它是编译期常量）。每份 GameInstance 拥有独立的注册表与子系统集合。
可检验：两个 GI 实例并存时，注册表装载计数与实例集合互相独立；静态可变变量的审查项为零。

**C33 不假设子系统初始化顺序。** SubsystemCollection 的初始化顺序由引擎决定；跨子系统依赖必须在 `OnInit` 里惰性获取，不得在构造函数或静态初始化期访问其他子系统。
可检验：审查项——构造函数里不出现获取其他子系统的调用；有一条把初始化顺序打乱仍然通过的用例。

**C34 关闭期不回调。** `Shutdown` 期间不得广播事件、不得再获取其他子系统；持有句柄的成员先释放再释放数据。
可检验：关闭路径的用例在打开「禁止广播」标志后跑通。

**C35 GameInstance 由宿主显式创建，框架不偷偷创建。** 项目设置指向我们的 GI 子类；Standalone 与 PIE 的创建点都在宿主里，且必须调用引擎提供的工厂。框架不提供「第二个会话入口」。
可检验：全仓 `CreateGameInstance` 调用点只有宿主里的两处（Standalone、PIE）；无其他创建路径。

**C36 跨边界只传 id 或带解析状态的引用。** 子系统之间不传裸指针；跨边界引用用 `ContentId` 或引擎对象引用（允许 pending 状态，解析失败按 C13 处理）。
可检验：子系统公开接口的参数与返回值里没有裸指针作为长期引用（审查项 + 一条用例：引用解析失败时上层收到明确失败结果）。

### 5.7 GameplayTag 词汇表治理

**C37 词汇表是代码契约，只能在静态构造期注册。** 引擎不支持运行期注册；因此每个 tag 在代码里以常量声明并注册一次，代码里禁止裸字符串字面量作为 tag 使用。
可检验：tag 使用处全部引用常量（审查项 + grep 检查：`GameplayTag(` 的实参不是字面量）。

**C38 命名分层。** 统一形如 `Domain.Category.Name`，领域段与模块对应（属性、效果、片段、图、背包、能力、UI）。层级隐含父节点，因此「命中父节点」不等于「命中子节点」，精确匹配必须用完整名。能力集合（某片段授予的能力列表）不是独立领域段，使用 `Fragment.Cap.*` 命名；「能力」一词在 `Ability.*` 段专指能力运行期（CORE-F07），两者不得混用。
可检验：注册表装载时对不符合分层规则的新 tag 提出命名问题（仅警告，因引擎已注册）；有一条用例证明查 `A.B` 不会命中 `A.B.C` 的精确判定。

**C39 内容里的 tag 一律写名字，加载期统一校验（C19）。** 内容不引用 tag 句柄、不引用 tag 索引；持久化同理（见 C40）。
可检验：内容与持久化里 tag 的出现形式只有字符串。

**C40 tag 容器不可持久化，必须写名字再重建。** `GameplayTagContainer` 持有 manager 裸指针且不可序列化；任何需要落盘的 tag 集合都写成名字数组，读回时重建容器。
可检验：持久化文档里不存在容器类型字段；往返后容器计数一致。

**C41 新增 tag 必须改代码，废弃 tag 必须保留注册。** 新增走代码变更（常量 + 注册）；废弃只做标记并停止在新的内容里使用，删除要伴随内容迁移与一次装载验证。
可检验：废弃 tag 仍在注册列表里（否则旧数据触发断言）；有一条检查项列出所有被标记废弃的 tag。

**C42 词汇表与内容版本耦合是显式的。** 内容包声明它要求的最小词汇表版本；词汇表版本小于要求时装载失败而不是猜测。
可检验：把内容包的最小词汇表版本调大，装载失败并给出版本差异。

### 5.8 命名、注释与代码组织约定（含「注释不得出现 ID 与章节号」）

**C43 注释规范。** 源码注释、日志字符串、测试用例名一律英文 Doxygen 风格（`/// ` + ```brief` / ```param` / ```return` / ```warning` / ```note`）；只写非显而易见的 why、契约、不变量、易错点。**禁止**出现 Feature / Slice / Bug / ADR / 技术债编号、设计文档章节号、需求编号与提交哈希；要解释原因就地把原因写清。
可检验：CI 在源码上 grep ID 模式（`[A-Z]+-F[0-9]+`、`S[0-9]{2}`、`TD-[0-9]+`、`§`）结果为空；测试用例名均为语义描述句。

**C44 命名。** 框架自有公开类型用 `MGF` 前缀（如 `MGFContentId`），避免与引擎 `ME` 前缀混淆；成员变量 `m_` 前缀、静态成员 `s_` 前缀、类型与函数 PascalCase；核心层类型不带引擎风格的反射宏残留命名。数据（内容资产的字段）反映内容语义而不是 UI 词汇。
可检验：审查项 + grep：核心层公开类型无 `ME` 前缀、适配层公开类型明确带 `MGF` 或明确的引擎派生语义。

**C45 文件组织。** 核心层一个概念一个头文件（id、tag、属性值、修饰器、增量表、图、背包语义、问题列表）；适配层一个定义族一个文件（内容定义与片段、实例、payload、子系统、序列化、事件适配）；测试一个主题一个文件，文件名描述主题而非编号。
可检验：目录结构审查；不存在超过约 600 行的巨型头文件（拆分触发点）。

**C46 依赖注入方向固定。** 适配层通过构造函数或初始化参数接收核心层规则对象；核心层从不调用适配层。回调只能由适配层向核心层注册，反向不允许。
可检验：核心层的符号引用表里不出现适配层符号（链接顺序验证：核心层单独链接可成功）。

**C47 文档引用不得反向指引。** 源码注释不得写「见某设计文档」；设计文档之间可以互相引用章节号与 Feature 编号（它们是文档体系的一部分）。
可检验：源码 grep `see docs/` 与 `见 design` 结果为空。

**C48 属性值只有一种数值类型。** 属性值只有 `float` 一种类型（非有限值不得提交）；需要整型语义的量（槽数、层数上限、次数、计数）不得建模为属性——它们必须是内容定义里的整数数据字段，或由显式取整规则从属性派生并注明舍入方向。
可检验：属性容器不接受非 float 值，提交 NaN/Inf 返回失败结果；有一条审查项：内容定义的整数字段不出现在属性表里（CORE-F04 的槽数、CORE-F02 的层数上限均走数据字段）。

## 6 可迁移性注记

逐条判断：去掉 C++ 与 minEngine 的具体 API 之后，本节每条是否仍然成立。判断标记：**成立**（结构本身与引擎无关）；**条件成立**（需要目标引擎提供某类基础设施，缺则自建）；**不成立**（依赖引擎特性的巧合，不能迁移，须在目标侧重做）。

| 条目 | 判断 | 说明 |
| --- | --- | --- |
| 三段切分：Definition + 实例增量 + 显式覆盖（5.1 / C5） | 成立 | 常量数据与运行期状态分离是通用模式（Lyra 的 Definition/Fragment/Instance 同理）；目标引擎若只有脚本对象，也同样成立 |
| 稳定内容 id 作为引用形态，而非资产路径（C1、C2） | 成立 | 把身份与存储位置解耦在任何引擎上都是正确做法 |
| tag 键替代枚举键做增量索引（C5） | 条件成立 | 需要目标引擎提供「字符串键 + 层级 + 词汇表校验」；没有 tag 系统时用一个自建词汇表模块即可，规则不变 |
| 词汇表属代码、内容加载期校验（5.7 / C37–C42） | 条件成立 | 依赖「能否运行期注册词汇表」。若目标引擎允许运行期注册，仍建议保持「内容声明的词汇必须来自代码声明集合，否则 fail-fast」，因为这是防止拼写错误的唯一低成本手段 |
| 属性 base/current 分离 + 全量重聚合、不做逆运算（C6） | 成立 | 数值稳定性要求与语言无关；这是本设计最值得迁移的一条 |
| 修饰器分桶 + 优先级排序（第 10 节 Q4） | 成立 | 纯算术与排序规则 |
| 效果与能力分层（效果结算 vs 能力编排） | 成立 | 与 Unreal GAS 的 Effect/Ability 切分同构，但不依赖任何引擎设施 |
| 内容定义用宿主引擎的资产对象承载（C9、C10） | 条件成立 | 需要「可反射、可引用、可序列化的资产对象」。目标引擎若无，用 JSON + 强类型加载器替代，契约（C1–C16）不变 |
| 反射缺失 inline struct 导致嵌套必须扁平化或引用化（C9） | 不成立（作为约束） | 这是本宿主反射能力的具体限制；迁移时应把「嵌套形态」重新按目标引擎能力决定，但「嵌套内容必须有单一权威来源」的意图成立 |
| 持久化只存增量 + schemaVersion + 显式拒绝未知版本（5.3） | 成立 | 与引擎无关；存档槽缺失属宿主问题 |
| 引用解析两段式（结构 → id 解析）（C13） | 条件成立 | 需要「延迟解析对象引用」的能力；多数引擎提供，缺则用两遍扫描实现，语义不变 |
| 事件只做冒泡、RAII 订阅、帧末 drain、不依赖顺序（5.5） | 条件成立 | 需要「按通道订阅 + 可退订」。目标引擎若有强类型事件总线，可省掉 tag 通道，但「无 payload + 单一真值 + 不依赖顺序」必须保留 |
| 更新只在可变相位、tick 里不做重活（C22、C23） | 成立 | 任何有固定/可变步长区分的运行时都适用；即使没有固定步长，也应保留「加载与结算分离」 |
| 全局服务做成引擎子系统、真值归属表单点（5.6） | 条件成立 | 需要某种生命周期容器（服务容器/依赖注入）。目标引擎若无子系统，用一个显式生命周期的服务容器实现，所有权规则不变 |
| PIE 隔离要求状态不落全局（C32） | 成立 | 多实例编辑器是现代引擎共性；这条在无 PIE 的引擎上也无害 |
| 三级失败策略（5.4） | 成立 | 诊断分级与语言无关 |
| 背包只定接口语义、容量策略数据化、几何与槽位解耦（见 CORE-F04） | 成立 | 这条最容易被引擎带着写歪，正因为与引擎无关才值得写进总纲 |
| 图文档 = 节点 + 边 + payload 引用 + 节点状态表（决策状态持久、派生状态可重算）（见 CORE-F05） | 成立 | 图结构是数学对象；只有 payload 的承载方式受引擎反射影响 |
| 「核心层不得出现引擎符号」这条判据本身（4.3） | 成立 | 这是元规则，任何引擎/语言都能执行 |

结论：不成立项只有一条，且它是**宿主反射能力的限制**而非设计意图，迁移时应重新按目标引擎能力落地。其余条目可以原样写进另一种语言的实现，代码重写、设计保留。

## 7 失败模式与反例

以下每条都说明「会怎样腐坏」「如何被发现」。这些都是本设计刻意要避免的形态，评审时应逐条确认当前文档确实堵住了它们。

1. **双真值（属性既存 base 又存 current 并各自做增量修改）。** 腐坏过程：current 由一系列增量加减维护，某次移除路径漏掉一次减，current 慢慢漂移；越到后期越无法解释当前值从哪来。发现方式：装载后全量重聚合对账（C6），漂移立即暴露为不一致。
2. **用枚举键做实例增量的索引。** 腐坏过程：新增一种属性必须改枚举，枚举又被多个模块引用，最后变成「加一个属性要改五个文件」；跨模块编译依赖上升，插件化不可能。发现方式：让一个内容包在不改代码的前提下引入新 tag 键（C5 用例），改不动就是复发。
3. **内容定义里塞资产引用。** 腐坏过程：定义 A 引用资产 X、X 里又引用定义 B，装载顺序不可控，出现「读到半个内容库」的中间状态；重命名资产即断链。发现方式：装载期强制两段式解析（C2/C13），任何绕过都会在缺失依赖时失败。
4. **裸字符串 key 拼写错误。** 腐坏过程：`"Attr.Healt"` 与 `Attr.Health` 是两个东西，拼错只在运行时表现成「数值没生效」，且没有任何日志。发现方式：词汇表常量 + 加载期未知 tag fail-fast（C19/C37）会把拼写错误变成装载失败。
5. **事件订阅悬垂（lapsed listener）。** 腐坏过程：对象销毁时忘了退订，之后每次广播都调到已释放内存；崩溃点远离根因，排查成本极高。发现方式：RAII 句柄 + 销毁后广播用例（C25），以及关闭期禁止广播的断言（C34）。
6. **在 tick 里同步装载资产或解析内容包。** 腐坏过程：帧时间出现尖峰，且装载内部可能广播事件，形成重入；重入深度一旦超过引擎上限就是硬崩溃。发现方式：tick 调用图审查 + 反射实例化计数为 0 的用例（C23）+ 重入断言。
7. **PIE 下用静态全局保存 gameplay 状态。** 腐坏过程：两个实例共享一份注册表与实例集合，编辑器里一切正常，多实例时互相污染，且问题表现为「随机」而非崩溃。发现方式：双 GI 实例独立性用例（C32）+ 静态可变变量审查项。
8. **先做编辑器面板再做数据形态。** 腐坏过程：数据形态被面板的交互模型绑架（例如为了拖拽方便而把引用改成资产路径），之后规则层被迫接受不可序列化/不可迁移的字段。发现方式：本设计把「无面板」写进非目标；一旦出现「为了面板而改数据形态」的提案，评审应直接打回。
9. **背包基类把上限与扩容逻辑写死。** 腐坏过程：派生类无法表达「无上限」或「可扩容」，只能复制基类再改，行为分叉且无法用同一套契约测试覆盖。发现方式：三种容量策略共用同一套契约用例（详见 CORE-F04）；派生不通过即为复发。
10. **规格文档各自发明契约。** 腐坏过程：七份 spec 平行撰写，每份都在局部自洽地重新定义 id / 失败策略 / 事件语义；集成时只能选一个，其余全部返工。发现方式：每份 spec 的评审必须逐条对照第 5 节（C1–C47）并标注「遵守 / 例外 + 理由」。

## 8 与既有引擎机制的边界

三栏清单。**复用** = 直接用引擎机制，框架不包装；**包装** = 引擎机制不变但框架提供一个更窄、更安全的门面；**自建** = 引擎没有，框架自己实现。另列「明确不自建」，防止重复造轮子。

| 分类 | 机制 | 说明 |
| --- | --- | --- |
| 复用 | GameInstance 与 CreateGameInstance / CreateGameInstanceForPIE | 会话宿主；框架只提供子类与创建点，不改引擎工厂 |
| 复用 | Subsystem 家族（Engine / GameInstance / World + Tickable 变体）与 SubsystemCollection | 生命周期与发现机制；框架只写子类 |
| 复用 | GameplayTag / GameplayTagManager / GameplayTagContainer | 词汇表与容器语义；框架只做常量声明与校验 |
| 复用 | GameplayEventSystemComponent | Scene 作用域事件投递、tag 通道、退订语义 |
| 复用 | DataAsset / DataAssetLoader / AssetManager | 内容定义载体与装载分派 |
| 复用 | Serializer / Archive / DiskVersion | 反射驱动的读写与引擎版本闸 |
| 复用 | 反射（ME_CLASS / ME_STRUCT / ME_PROPERTY / ObjectManager::NewObject / ReflectionSystem） | 类型系统与多态实例化 |
| 复用 | 模块契约（MinEngine_GameModuleEntry） | 唯一装配入口 |
| 包装 | tag 名字 ↔ 句柄绑定与「名字数组 ↔ 容器」转换 | 保证 C39/C40；包装层是唯一允许出现裸 tag 名字的地方 |
| 包装 | 资产引用（路径/句柄）的解析门面 | 只在装载边界暴露；规则层看不到资产类型（C2/C3） |
| 包装 | 事件总线 RAII 订阅句柄 + 帧末 drain + 去抖 | 补齐引擎事件系统的生命周期与顺序坑（C24–C28） |
| 包装 | 反射实例化工厂（按类名创建，带白名单） | 供多态 payload 使用；白名单防止任意类被内容指定（C9 / Q7） |
| 包装 | 装载问题列表 | 把引擎的日志/断言式报错转成结构化结果（C18） |
| 自建 | 属性聚合与效果结算（base/current、修饰器分桶、全量重聚合） | 引擎无 GAS |
| 自建 | 实例增量表与显式覆盖列表的合并规则 | 引擎无对应物 |
| 自建 | 内容注册表与装载校验（id 唯一性、tag 校验、包闭包、版本） | 引擎只负责按类实例化资产 |
| 自建 | 背包接口语义、容量策略、几何与槽位解耦 | 引擎无对应物 |
| 自建 | 图文档结构、校验、派生状态重算 | 引擎无对应物 |
| 自建 | 持久化文档的 schemaVersion 与语义迁移判定 | 引擎只管引擎版本 |
| 自建 | 能力运行期（CORE-F07，可砍） | 引擎无 GAS |
| 明确不自建 | Manager 单例 / 服务定位器 | 与 C30 冲突；生命周期交给子系统 |
| 明确不自建 | 第二套资产系统或第二套事件系统 | 会造成双真值与双退订语义 |
| 明确不自建 | 存档槽与自动存档设施 | 非目标；登记技术债 |
| 明确不自建 | 运行期反射注册内容类型 | 与 C8/C37 冲突 |

## 9 实现波次与验收判据

四波固定顺序，每波结束都必须可编译、可验证；验证基线在 Wave1 落地时从 docs-only 升级为 tests-required（同步 PROJECT_CONTEXT 与 WORKFLOW_PROFILE）。每波只依赖前面波次已交付的契约条目。

### Wave1 工程骨架 + Framework（GameInstance 注入）+ Content + Attributes

- 产物：CMake 工程与六个 target；游戏 SHARED 模块导出 C 入口；GI 子类（含 Fixed 相位显式派发骨架）；内容注册表子系统；属性与效果结算子系统（瞬时效果）；加载闸口；问题列表；doctest 测试可执行 + ctest 注册。
- 验收判据（全部可执行）：
  1. `ctest` 全绿；至少覆盖 C1、C5、C6、C11、C13、C14、C17、C19、C30、C32、C43 各一条用例。
  2. 核心层引擎符号 grep 为空（4.2 / 4.3 检查项）。
  3. Standalone 宿主能装载一个示例内容包并打印注册表摘要（定义数、片段数、问题数 = 0）。
  4. 两个 GI 实例并存时注册表与实例集合互相独立（C32）。
  5. 属性重聚合对账用例通过：瞬时效果施加后当前值与从基值重算结果一致（C6 / 失败模式 1）；完整的施加—移除对账移入 Wave4（随 Duration/Infinite 与层数一起）。
  6. 重复 id、非法 id、未知 tag、未知片段种类、未知 schemaVersion 各返回问题列表（C17/C19）。
  7. 源码 ID 与章节号 grep 为空（C43）；测试名为语义描述。

### Wave2 Inventory

- 产物：背包接口语义与结果码；容量策略接口；至少三个派生（无上限 / 有上限 / 可扩容）；物品实例上的几何占位片段；背包派生类持有的二维网格；装备/交换的显式操作集合（其数量与边界、拆分语义由 CORE-F04 的契约承接，不新增总纲契约）。
- 验收判据：
  1. 三个派生通过同一套契约用例（试加、试移除、部分移除、容量不足、越界索引），证明语义一致而策略不同（失败模式 9）。
  2. 几何与槽位解耦用例：多格占位物品在网格中占用正确格位，旋转/放置失败返回明确失败码；槽位语义不受几何影响。
  3. 背包变更不在 Fixed 相位生效（C22）；通知去抖且只报最终状态（C28）。
  4. 背包状态只存增量（持有物 ContentId + 数量 + 占位信息），往返等价（C11/C14）。

### Wave3 Graph

- 产物：图文档结构与校验；多态 payload（基类 + 反射派生 + 类名白名单）；派生状态重算；节点/边的最小推进接口（供任务/科技模块使用，不自带具体玩法）。
- 验收判据：
  1. 坏图（重复节点 id、悬空边、payload 类型不在白名单、payload 缺失）全部装载期拒绝并给定位（C17）。
  2. 决策状态写盘、派生状态不写盘；装载后重建的派生状态与运行中逐帧推进到同样输入的结果一致（C11 + 失败模式 2 的对偶）。
  3. 一种图对应一种解析业务：新增一种图业务不改图文档结构，只新增 payload 类型与解析器（C8）。
  4. payload 内部的内容引用全部走 ContentId 并通过 C13 解析。

### Wave4 Samples 与能力（CORE-F07，可砍）

- 产物：一份示例内容包（属性、片段、物品、配方/科技图各一），可在编辑器里填、可在 Game 宿主装载；能力运行期（若保留）：能力编排、目标侧施加前 tag 准入、层数上限、可中断。
- 验收判据：
  1. 示例内容装载零问题，且示例是「用现有契约表达」而非新增契约（新增即回退去改文档）。
  2. 若保留 CORE-F07：能力可施加与移除，且移除后属性重聚合与从未施加一致；目标侧准入门槛拒绝时返回明确失败码；层数上限由 CORE-F02 的堆叠契约覆盖，中断随持续激活进 Wave4 之后。
  3. 若砍掉 CORE-F07：Wave4 只交付示例内容，能力相关契约回到待决问题（第 10 节）并标注 Deferred 理由。

## 10 待决问题

每条给出选项与建议。建议不是决定，作者可直接改判。

**Q1 内容 id 的形态。** 选项：(a) `(kind, name)` 两段，kind 决定注册表分片；(b) 单一全局字符串（如 `item.sword.iron`）；(c) 分层字符串 + 独立种类字段。
建议 (a)。理由：kind 决定分片与资产类型，显式字段比解析字符串可靠；命名字符串里再带 kind 会形成两处真值。
什么会推翻它：若作者希望 id 可跨种类移动（同一个名字在物品与方块之间共享语义），则 (b) 更合适。

**Q2 fragment 覆盖列表的表达方式。** 选项：(a) 覆盖项 = (片段种类, 动作：替换/追加/移除, 参数)；(b) 整类片段整体替换（无动作维度）；(c) 有序数组按索引覆盖。
建议 (a)。理由：只有种类 + 动作能同时表达「只改一个参数」与「整个换掉」，且不受装配顺序影响；索引覆盖在插入新片段后全错。
什么会推翻它：若实践中几乎总是整体替换，可退到 (b) 并在文档里删掉动作维度。

**Q3 tag 增量表的物理形态。** 选项：(a) 有序 `vector<TagName, 值>`，查询时建索引；(b) 哈希表。
建议 (a)。理由：序列化需要确定顺序（C11 往返字节等价），且增量表条目数通常很小；哈希表反而要额外排序。
什么会推翻它：单个实例的增量条目数上千时，(a) 的线性查找会成为瓶颈，此时改为「哈希表 + 序列化时排序」。

**Q4 修饰器的合成语义。** 选项：(a) 分桶：先全部加法桶、再全部乘法桶，桶内按 priority 排序；(b) 单一有序列表按 priority 逐个应用；(c) 每属性绑定聚合公式。
建议 (a)。理由：分桶是业界验证过的稳定语义（加法桶不关心顺序，乘法桶乘积可交换），避免「顺序不同结果不同」的调试地狱；priority 只用于同桶内的显式覆盖。
什么会推翻它：若出现必须「先乘后加」的效果，需要新增桶并写清顺序，属于语义破坏性变更，必须回来改本文档。

**Q5 效果的时间模型在第一版的范围。** 选项：(a) Wave1 只做瞬时效果，持续效果留给 CORE-F02 的明确非目标；(b) 一开始就做 duration + period。
建议 (a)。理由：YAGNI；持续效果会立刻引入到期推进、重入、堆叠与暂停语义，这些与 Wave1 的目标（验证 base/current 重聚合）无关，且小 GAS 的价值不依赖它。
什么会推翻它：若第一批示例内容就必需「增益 10 秒」，则把 duration 纳入 Wave1 并把 period 留到 Wave4。

**Q6 背包几何的责任边界细化。** 决策已定：几何占位信息挂在物品实例上（由片段赋予），二维网格由背包派生类持有。仍需决定：网格坐标原点与旋转语义是否属于核心层契约。
建议：核心层只定义「占位形状（宽×高）与旋转枚举」与「网格是另一套坐标」这条边界；原点与扫描顺序由派生类定义。理由：让核心层保持可迁移，同时禁止派生类偷偷把几何塞回槽位语义。
什么会推翻它：若多种游戏共用同一套网格放置算法，把算法下沉到核心层更省重复。

**Q7 图 payload 的多态与类型安全。** 选项：(a) 基类 + 反射子类 + 内容包声明允许的 payload 类型白名单；(b) 单一 payload 类 + 判别 tag + 字段并集；(c) payload 也为 DataAsset。
建议 (a)。理由：白名单让「内容指定任意反射类」变成可控面，且解析器按业务分派；字段并集会让一类图的字段污染另一类。
什么会推翻它：若 payload 需要被非引擎工具（外部编辑器）读写，(c) 更容易被第三方解析。

**Q8 内容包的资产粒度。** 选项：(a) 每个定义一份资产 + 一份索引资产；(b) 一大份资产装一个包的所有定义。
建议 (a)。理由：合并冲突小、可增量装载、编辑器里可单独保存、失败定位精确到文件；代价是资产数量变多。
什么会推翻它：若资产体积成为装载性能瓶颈（数千小文件），改为 (b) 并在索引里保留定义级定位能力。

**Q9 如何测试 fail-fast 而不让测试进程 abort。** 选项：(a) 装载校验一律返回问题列表，断言只用于不变量；(b) 用子进程做 death test。
建议 (a)，并把它写进契约（C17/C18）。理由：可测性是设计约束，不是测试技巧；断言留在真正的不变量上。
什么会推翻它：若某类错误必须在代码里以 abort 表达（例如词汇表自相矛盾），单独用 (b) 覆盖该点。

**Q10 属性数值类型。** 选项：(a) 浮点；(b) 定点/整数。
建议 (a)，并在技术债里登记「定点化」作为可选项。理由：第一版目标是验证规则而不是数值精度；定点化会污染所有算术语义。（R2 注：C48 已把「属性只有 float、整型语义走数据字段」定为契约，本问题收窄为「是否在 float 之上再做定点化」。）
什么会推翻它：若出现必须逐帧确定性重放的用例（回放/联机），定点化需要提前。

**Q11 编辑器宿主第一版的边界。** 选项：(a) 只支持打开/新建/填写/保存 DataAsset，无面板、无预览；(b) 提供最简属性面板。
建议 (a)。理由：与「不做编辑器工具」的决策一致；数据形态由契约定义，不由面板定义（失败模式 8）。
什么会推翻它：若手工填写的成本高到影响内容生产，再做 (b)，且必须先证明面板不改变数据形态。

**Q12 词汇表版本号是否引入。** 契约 C42 要求内容包声明最小词汇表版本。选项：(a) 引入一个整型词汇表版本；(b) 不做版本，只做未知 tag fail-fast。
建议 (a)。理由：tag 只增不删时 (b) 够用；但一旦出现「重命名 tag」就必须有版本才能给出可读的迁移提示，成本只有一个整数。
什么会推翻它：若决定「tag 永不重命名」（只废弃不重命名），(b) 足够，C42 可以删掉。
