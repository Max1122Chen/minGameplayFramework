# CORE-F07 能力运行期（小 GA，可砍）

> 状态：Draft
> 作者：项目作者
> 最后更新：2026-10-26
> 关联契约：C2、C3、C4、C5、C6、C7、C8、C11、C13、C14、C17、C18、C19、C20、C21、C22、C23、C24、C25、C27、C29、C30、C31、C32、C33、C36、C37、C38、C41、C44、C45、C46
> 上游特性：CORE-F01（总纲，唯一契约源）；并行依赖 CORE-F02（属性与效果）、CORE-F03（内容定义）、CORE-F05（图模型）、CORE-F06（会话与子系统）
> **可砍：** 若第一版不做能力编排，框架仍然成立。砍掉的替代路径是「把编排下沉到业务模块」——由业务在自己的显式操作函数里按序调用 CORE-F02 的效果施加入口，准入条件写成业务侧的显式判定。框架失去的是「编排的可复用形态」，而不是任何规则能力。

## 1 问题与动机

### 1.1 可砍声明与替代路径

本 spec 描述的是**能力运行期**：把「谁在什么条件下、对谁、花多少、按什么顺序、施加哪些效果」这套编排从业务代码里提取成一个可复用的运行期。它与 CORE-F02 的边界是硬边界：

- CORE-F02 负责**数值**：属性基值与当前值、修饰器合成、效果的结算与施加。
- CORE-F07 负责**编排**：闸门、成本、冷却、授予与撤销、结束策略。

这条切分在总纲第 6 节被判定为「成立」，与 Unreal GAS 的 Effect / Ability 切分同构，但不依赖任何引擎设施。

砍掉本 spec 不破坏总纲任何契约条目。总纲 §8 已把「能力运行期」列为**自建且可砍**，总纲 §9 Wave4 已写明「若砍掉 CORE-F07：Wave4 只交付示例内容」。

替代路径（砍掉后的写法）如下，它是**允许的**，只是不可复用：

```cpp
// Sketch, not a final signature. Stand-in for what a game module would write
// when no ability runtime exists: the gate, the cost and the effect order are
// all spelled out at the call site, so the next caller copies them.
MGFResult CastFireball(MGFInstance& caster, MGFInstance& target)
{
    if (!caster.HasTag(Tag::Ability_Blocked_Stunned)) { /* ... */ }
    if (!target.HasTag(Tag::State_Flammable)) { /* ... */ }
    if (caster.GetAttribute(Attr::Mana) < 20.0) { /* ... */ }
    effects_.Apply(caster, costFireball_, cause);   // cost
    effects_.Apply(target, fireballHit_, cause);    // applied effects
    return MGFResult::Success();
}
```

### 1.2 砍掉之后缺什么，以及后续补入的成本

这一节是给作者的决策依据，不是论证「必须做」。

| 砍掉后缺的东西 | 现象 | 后续补入的成本 |
| --- | --- | --- |
| 准入判定的统一位置 | 每个业务函数自己写 if，判定组不一致：有的查施法者 blocked tag 不查目标，有的顺序相反 | 补入时要把散落在业务里的判定回收成数据；已发出去的内容无法批量修正，只能逐个业务函数改 |
| 成本的原子性 | 业务侧先扣蓝再判条件，条件失败时蓝已被扣掉；或先判后扣但中途 return 漏掉一条 | 补入时每个业务函数都要重写成「先全查后全写」，这是纯人工审计，无法靠编译期发现 |
| 授予与撤销的句柄语义 | 用布尔字段「已学会」表示能力，撤销路径靠人手清标志；同一能力被两个来源授予时无法分辨该不该真撤销 | 补入时要引入来源追踪并迁移既有存档/内容；若第一版没有存档（总纲 C15），成本主要在内容与业务代码两侧 |
| 冷却 | 冷却计时散落在各业务里，有的用帧数有的用秒，重启后语义不一致 | 补入成本低（冷却本身无内容侧结构），但需要先确立时钟源 |
| 效果与编排的分层 | 业务直接写属性（绕过 CORE-F02 的单一写入点），总纲 C29 在 Wave4 起被事实性违反 | **这是最贵的一项**：一旦出现旁路写属性，C6 的全量重聚合对账会在业务侧失效，回退要重审每个 gameplay 模块 |

量化结论：接入成本按「受影响的可写路径条数」计，而不是按代码行数。第一版若只有一份示例内容，砍掉后补入约等于新增一份 spec 加一次业务侧改写；若第一版之后已有三四个业务模块在用替代路径，补入成本是它的数倍，且 C29 需要先做一次全仓审计。

**R3 复核（结论仍成立）。** 总纲 R2 的 A12(b) 与 G1 已把 §9 Wave4 的判据改成分「若保留 / 若砍掉」两种情形，本节的替代路径与成本结论不受这次改写影响：表中的成本按「受影响的可写路径条数」计，依赖的是「判定与写入散落在业务里」这一事实，与波次判据的措辞无关；砍掉一侧的交付要求见 §10.3（对应总纲 Wave4 判据 3）。

### 1.3 为什么仍然值得先写

- 它是唯一能让「准入条件、成本、效果顺序」进入**数据**的机制。没有它，这些只能进代码，而总纲 C7 要求「数值与开关、装配关系」可只存在于数据里。
- 它与 CORE-F02 / CORE-F03 / CORE-F05 的分工必须现在切清。切分点写下来的成本远低于事后从业务代码里反推。
- 它天然验证 C29（单一写入点）与 C21（结构化结果）这两条最容易在实现阶段被妥协的契约。

### 1.4 来自旧项目的两条教训

旧项目 CardGameDemo 的小 GAS 是本 spec 的负样本，两条教训被直接采纳为契约：

1. **F13 教训：数据里出现了用来关掉框架默认行为的开关字段。** 典型形态是 `costApplyTiming`（成本在效果前/后/不扣）、`manualResolve`（不自动结算，等业务手动调）、`skipCooldown`。每一处这样的字段都意味着：框架有一个默认行为，而数据可以把它关掉；随后框架的每个不变量都要在「开关打开」和「开关关闭」两种形态下分别成立，测试矩阵翻倍，而且两个形态的语义差从未被写清。本 spec 的处理见 §4.3 与 K3：**差异化只能通过「装不装配某个片段」「选哪个 handlerId」「引用哪份内容」表达，不允许有用例语义的布尔/枚举开关。**
2. **成本与效果没有原子性。** 旧项目里成本是一段手写扣减，条件只在扣减前判一次，条件与扣减之间的任何失败都留下半截状态。本 spec 的处理见 §4.6 与 K9：**所有可能失败的判定都在任何写入之前完成，写入阶段按「不可能失败」排序，因此不需要回滚，也不写事务日志。**

## 2 目标与非目标

### 2.1 目标

- **G1 定义与逻辑分离有一个可检验的形态。** 能力定义是内容（CORE-F03 的内容定义 + 片段），逻辑按 `handlerId` 在代码里注册；两者之间只有一个字符串契约，装载期即可校验（K1）。
- **G2 一条固定顺序的激活管线。** 闸门 → 成本 → 冷却 → 实例创建 → 结束策略，顺序不可由数据配置，每段标明是机制还是策略（K6）。
- **G3 成本与效果走同一个入口。** 能力运行期不出现第二条写属性的路径（K4、K5）。
- **G4 授予与撤销有句柄语义与来源追踪。** 重复授予幂等，多来源各自撤销互不影响，同时刻只有一个能力实例（K11、K12）。
- **G5 目标侧施加前准入补齐。** 采纳 UE 的 `applicationTagRequirements` 思路：施加前对 owner / source / target 三侧做 tag 准入，并与「持续准入」明确分工（K8）。
- **G6 可砍的落地形态。** 砍掉时 Wave4 仍然有可交付物，且不需要任何其他 spec 跟着改（第 10 节）。

### 2.2 非目标

本版明确不做，且**不在本 spec 留下任何占位接口**（留占位就是留双路径，与总纲 §7 重构纪律冲突）：

- **网络复制与预测。** 不做权威端/客户端拆分、不做预测回滚、不做能力激活的复制。总纲 §2.2 已把网络同步列为非目标。
- **输入绑定。** 能力不知道按键、不知道手柄、不知道 UI 按钮；「按下 Q 触发」是输入层到显式请求路径的一行调用。
- **技能队列与优先级。** 不做排队、不做「前摇期间按下一个技能则缓存」、不做打断优先级比较。多个激活请求按到达顺序逐个求值，失败的请求不排队。
- **动画蒙太奇与表现。** 不做动作期、不做取消窗口、不做表现层事件。表现层通过总纲 C24 的事件通道自行回查状态。
- **持续效果与持续激活。** 与总纲 Q5 的建议一致：第一版只有瞬时效果，因此能力的第一版也只有瞬时激活（结束策略只有 Instant）。持续激活所需的「中断」「ongoingTagRequirements 违约撤销」列在待决问题 Q3。**跨存档的持续效果不在本框架保证范围**（C11）：读档后 current 等于 base，需要「buff 读档后仍挂着」的业务由上层在读档完成后重新施加；能力也不携带「哪个持续效果还挂着」的跨存档状态（与 CORE-F02 非目标的口径一致）。
- **能力树、天赋图、解锁链。** 图模型归 CORE-F05，本 spec 只消费它的节点激活钩子。
- **目标选择器（TargetSelector）。** 不做范围查询、不做队伍过滤。目标由调用方给定；需要选择逻辑时由 handler 在代码里做（handler 是代码，允许引用内容）。
- **层数上限与堆叠。** 堆叠是修饰器与效果的语义，属 CORE-F02；本 spec 不引入独立的「能力层数」概念（见 §9.4 的一致性差异记录）。

## 3 术语

只列本 spec 新增的概念。共享概念（内容定义、ContentId、片段、实例、tag 键、失败三级分类、schemaVersion、RAII 订阅句柄等）一律指向总纲 §3 与 §5，不在此重复定义。

| 术语 | 定义 |
| --- | --- |
| 能力定义 AbilityDef | 一份内容定义（`kind = ability`），承载闸门条件、成本效果引用、表现效果引用与 `handlerId`；只读，遵守总纲 C4 |
| 处理器 Handler | 代码对象：一个 `handlerId` 对应一份实现，负责数据表达不了的那部分逻辑（目标分支、条件组合、多次施加的顺序） |
| 处理器注册表 HandlerRegistry | 组合根在装配期填充的 `handlerId → Handler` 只读映射；运行期不可增删 |
| 闸门 Gate | 激活前的准入判定：owner / source / target 三侧各自的 required 与 blocked tag 条件；无副作用 |
| 成本 Cost | 一组有序的瞬时效果引用，施加到 owner 或 source 上；无副作用地可查询 |
| 冷却 Cooldown | 同一 `(owner, abilityId)` 两次成功激活之间的最小时间间隔；由片段的存在性表达 |
| 激活记录 ActivationRecord | 纯运行期结构：一次成功激活的产物（序号、起始时刻、结束策略、来源令牌）；不落盘、不进实例字段表 |
| 授予 Grant | `(owner, abilityId, sourceToken)` 三元组；同一三元组只存在一条 |
| 来源令牌 SourceToken | 授予的来源标识：内容装配（定义 id）或图节点（图实例 + 节点标识）；由值类型承载，不用裸字符串 |
| 授予句柄 GrantHandle | RAII 句柄：析构即撤销该来源的授予（遵守总纲 C25 的句柄语义） |
| 施加前准入 ApplicationAdmission | 激活前对三侧 tag 的一次性判定（对应 UE 的 `applicationTagRequirements`） |
| 持续准入 OngoingAdmission | 激活存活期间对同一份条件结构的重评估（对应 UE 的 `ongoingTagRequirements`）；本版非目标，见 Q3 |
| 结束策略 EndPolicy | 一次激活如何结束的枚举；本版只实现 Instant，且该枚举不由数据给出（见 §4.8 与 K3） |

## 4 设计

### 4.1 总体形状：三层，而不是两层

能力由三个不同寿命的东西组成，混成一层是本 spec 最容易出的错：

| 层 | 是什么 | 寿命 | 落盘 | 遵守的契约 |
| --- | --- | --- | --- | --- |
| 能力定义 AbilityDef | 只读内容定义 | 随内容注册表（会话） | 是（它是内容） | C1、C2、C4、C6 |
| 能力实例 AbilityInstance | owner 持有的可写 gameplay 对象；实例类与有效片段视图（定义装配 + 覆盖列表合并结果）由 CORE-F03 提供，本块**只使用、不自行合并覆盖**，实例形态因此仍是定义引用 + tag 键增量表 + 显式覆盖列表 | 随授予集合非空 | 按 C11 只有增量 | C5、C11 |
| 激活记录 ActivationRecord | 一次成功激活的运行期产物 | 一次激活 | 否 | 本 spec 的 K14 |

为什么激活记录不能做成能力实例的字段：总纲 C5 规定实例只有三段，不允许「实例私有字段白名单」。激活序号、冷却到期时刻这些既不是 tag 键增量（它们不是 gameplay 属性，UI 不该读到它们），也不是覆盖项。把它们塞进增量表会让「属性表」变成杂物间，并让 C11 的往返等价承诺覆盖一堆本不该落盘的量。因此本 spec 把激活记录明确为**非 gameplay 对象**，并把这个判定写成 K14 的可检验形式。

依赖形状（只画方向，不画完整类图）：

```text
  CORE-F03 内容定义 + 片段
        |
        v  (ability 定义: handlerId / 闸门 tag 名 / 效果引用)
  CORE-F07 能力运行期 ──> CORE-F02 效果入口 (唯一写属性的路径)
        ^                        ^
        |  (节点激活/去激活钩子)   |
  CORE-F05 图模型          CORE-F02 的属性与修饰器
```

能力运行期只向下依赖效果入口与内容注册表；它**不** include 图模块头（K13）。

### 4.2 能力定义：数据与逻辑分离的具体形态

能力定义是一份内容定义，因此它遵守 CORE-F03 的全部规则（片段装配、覆盖列表、引用形态）。它额外携带下列字段，字段集合封闭（K2）：

| 字段 | 资产侧形态 | 语义 | 缺省 |
| --- | --- | --- | --- |
| 内容身份 | 由 CORE-F03 的 id 字段给出，`kind = ability` | 稳定身份（C1） | 必填 |
| `handlerId` | 单条字符串 | 代码契约：指向处理器注册表的一个条目 | 必填 |
| `ownerRequired` / `ownerBlocked` | tag 名字数组 | 施法者侧施加前准入 | 可空数组 |
| `sourceRequired` / `sourceBlocked` | tag 名字数组 | 来源侧（赋予能力的载体，例如装备或图节点）施加前准入 | 可空数组 |
| `targetRequired` / `targetBlocked` | tag 名字数组 | 目标侧施加前准入 | 可空数组 |
| `costEffects` | 有序效果引用数组 | 成本；见 §4.6 | 可空数组 |
| `appliedEffects` | 有序效果引用数组 | 表现；由数据表达的那部分效果 | 可空数组 |
| 冷却片段 | 片段装配（存在性） | 冷却时长由片段参数给出；不装配即无冷却 | 不装配 |

三条形态约束：

1. **六个 tag 数组是扁平的字符串数组，不是嵌套结构。** 总纲 C9 禁止把 ME_STRUCT 直接作为 DataAsset 反射属性，所以「三侧 × 两类」只能摊平成六个数组或一个带前缀约定的数组。本 spec 选择摊平：字段名自带侧别，加载期校验不需要解析前缀。若 CORE-F03 最终选择「统一带前缀的单数组」形态，以 CORE-F03 为准并回来改本节。
2. **效果引用数组是 ContentId 序列，其资产侧编码就是 CORE-F03 的 `MGFContentIdRef`**（两个 primitive 字段：`kind` + `name`）。本节不定义第二套编码（C2 要求引用一律用 ContentId；`MGFContentIdRef` 是唯一的引用编码，F04 / F05 / F07 的引用字段一律引用它）。
3. **没有 `enabled` / `isPassive` / `costApplyTiming` / `manualResolve` / `skipCooldown` 这类字段。** 见 §4.3。

`handlerId` 与 ContentId 是两种不同的东西，不允许互相冒充：

| | ContentId | handlerId |
| --- | --- | --- |
| 归属 | 内容层身份（C1） | 代码契约（C8 第五类「结算与聚合规则」的同族） |
| 稳定性 | 发布后永不改 | 随代码走，改名即破坏已发布内容 |
| 校验时机 | 装载期查重复与字符集 | 装载期查注册表是否命中 |
| 谁给 | 数据 | 数据里写，但合法取值集合来自代码 |

```cpp
// Sketch, not a final signature.
/// @brief Turns an authored ability definition into one activation.
/// @warning Implementations must reach attributes only through the effect
///          gateway; a direct attribute write bypasses re-aggregation.
class MGFAbilityHandler
{
public:
    /// @brief Pure query stage: return a refusal code without touching state.
    /// @param context Resolved owner, source and target of this activation.
    virtual MGFResult CanActivate(const MGFActivationContext& context) = 0;

    /// @brief Execute stage: runs only after every refusal check passed.
    /// @param context Same context the query stage accepted.
    virtual MGFResult Activate(const MGFActivationContext& context) = 0;
};

// Internal: activation is split in two stages so that no write can happen before
// every refusal check has passed; see the cost commit rule.
```

### 4.3 不允许用数据关掉框架的默认行为

这是本 spec 从旧项目学到的第一条硬约束（§1.4）。判据形态如下：

框架的默认行为是**固定**的（§4.5 的五段顺序、§4.6 的两阶段提交、§4.9 的引用计数撤销）。数据只能表达**做什么**，不能表达**不做哪一步**。合法的差异化表达只有三种：

| 想表达的差异 | 合法手段 | 非法手段（禁止） |
| --- | --- | --- |
| 这个能力不花钱 | `costEffects` 为空数组 | `hasCost = false` 开关 |
| 这个能力没有冷却 | 不装配冷却片段 | `skipCooldown = true` 或 `cooldownSeconds = -1` |
| 这个能力的成本在表现之后扣 | **不存在这种需求**：成本永远在表现之前（否则失败原子性无法成立） | `costApplyTiming = After` |
| 这个能力的结算要等业务手动触发 | 换一个 `handlerId`，由该 handler 的 `Activate` 决定何时施加 | `manualResolve = true` |
| 这个能力允许在失控状态下施放 | 把该状态移出 `ownerBlocked` | `ignoreBlockedTags = true` |

反例（旧项目的形态，本 spec 禁止）：

```cpp
// Sketch, not a final signature. Do not add fields like these: each one asks the
// runtime to skip a step whose invariants then have to hold in two shapes.
struct MGFBadAbilityDef : MGFContentDef
{
    bool m_hasCost = true;
    bool m_skipCooldown = false;
    int  m_costApplyTiming = 0;  // 0 = before applied effects, 1 = after, 2 = never
};
```

正例：差异全部由「装不装配片段」「引用哪份内容」「选哪个 handlerId」表达，字段集合恒定，因此 §7 的校验规则也只有一份。

### 4.4 处理器注册表与 handlerId 契约

- `handlerId` 是 ASCII 字符串，形如 `Domain.Action`，字符集与 ContentId 的 `name` 段相同（C1 的字符集规则复用，不新造）。它有命名空间段但没有层级语义（不是 tag）。
- 注册发生在**组合根**（总纲 §4.1：游戏 SHARED 模块的 C 入口），运行期只读。适配层与能力运行期都不得自行注册（C46：回调只能由适配层向核心层注册）。
- 注册表是**代码契约的运行时索引**，不是内容：它不需要序列化，不参与 schemaVersion。
- 装载期对每个 `ability` 定义的 `handlerId` 做命中检查，未命中即 fail-fast（C17 第二类、C19 同族）。不做「运行期降级为空实现」——那会让一个拼写错误变成「能力没反应」。
- 同一 `handlerId` 注册两次是装配期错误，按 fail-fast 处理；发布期不静默覆盖。

处理器注册表的归属要分两层看，这两层不是同一件事：

- **映射本身是代码契约表，不是会话子系统。** `handlerId` → 处理器实现的映射在代码里静态登记，由组合根在装配期构造一次、此后只读；它不持有 gameplay 真值，也不参与结算。CORE-F06 §4.2 的子系统清单写明这张表由组合根持有只读对象、不占子系统名额——因此本 spec **不需要新增子系统**，F06 的五个（内容注册表、实例仓储、会话事件总线、配置与诊断、帧驱动器）已经够用。
- **运行期的激活记录与冷却时钟才是会话状态**，按 CORE-F06 的真值归属表落位（随实例与所在场景，owner 是场景对象），同样不另立子系统。

注册表与内容注册表同寿命（C31 的「内容定义与注册表」行），原因是它与内容定义一起在加载闸口被校验，而不是因为它要挂到同一个子系统上。这个归属若与 CORE-F06 的归属表冲突，以 CORE-F06 为准并回来改本节。

### 4.5 激活管线：五段，顺序固定

```text
  [1] 闸门 Gate            (owner / source / target 三侧施加前准入 + handler 纯查询)
       |  失败 -> 返回 GateFailed(具体子原因)，状态不变
  [2] 成本检查 CostCheck   (纯查询，不写)
       |  失败 -> 返回 CostUnavailable(具体条目)，状态不变
  [3] 成本提交 CostCommit  (施加 costEffects，有序)
       |  此处起不再有任何可失败的数据错误
  [4] 表现施加 Effects     (施加 appliedEffects，有序；handler 的 Activate)
  [5] 冷却登记 + 激活记录  (写运行期表，无失败路径)
       |  成功 -> 返回 Activated(activationIndex)
```

机制与策略的归属：

| 段 | 机制（代码固定，不可配置） | 策略（数据或 handlerId 决定） |
| --- | --- | --- |
| 1 闸门 | 三侧判定都执行、全部执行完才汇总（不做短路）、判定无副作用 | 六组 tag 名字、handler 的额外拒绝条件 |
| 2 成本检查 | 校验每个成本效果「可施加」且无副作用；全查完再返回 | `costEffects` 的内容与顺序 |
| 3 成本提交 | 效果必须已经通过第 2 段校验；施加顺序 = 列表顺序 | 同上 |
| 4 表现 | 一次激活内只有一次表现阶段 | `appliedEffects` 的内容与顺序；handler 内的分支逻辑 |
| 5 冷却与记录 | 冷却记录的唯一写点；激活序号单调递增 | 冷却时长（片段参数）；是否存在冷却（片段存在性） |

为什么顺序不可配置：可配置的顺序会让「状态不变」这条原子性承诺无法用一条用例覆盖（每种顺序都要单独证明），而收益只有一个极端少见的场景（先表现后扣费）。总纲 C27 要求顺序敏感的流程写成显式状态机而非可配置链，本段是同一取向。

为什么管线里没有独立的「实例创建」段：能力实例的创建与销毁由授予集合派生（§4.9 不变量 1），不发生在每次激活里；每次激活创建的是激活记录（§4.1）。若把实例创建放进激活管线，同一能力在被授予后到首次激活之间就没有实例，闸门与冷却也就无处落脚；把实例挂在授予上、把记录挂在激活上，是「能力被拥有」与「能力被执行」两件事各自一个真值。这是本 spec 相对「激活时才建实例」这一常见做法的一处有意偏离，理由与代价都记在 §4.1 与 §4.9。

时序的相位约束：整条管线只允许在 Variable 相位或显式请求路径上执行（C22、C23，见 K16）。第 5 段写冷却依赖时钟，时钟只在 Variable 相位推进；因此在 Fixed 相位调用激活一定失败（K16 的可检验形式）。

### 4.6 成本：用什么承载，以及原子性怎么成立

**承载：成本是一组有序的瞬时效果引用，不是「属性键 + 数值」。**

理由三条：

1. 总纲 C29 规定属性只能由效果应用/移除路径修改。若成本写成「直接扣 AttributeCurrent」，能力运行期就成了第二条写属性的路径，C6 的全量重聚合会对不上。
2. 成本常常不是单属性扣减（例如同时扣法力与耐久、或消耗一个物品效果）。
3. 效果引用让「成本可查询」免费成立：CORE-F02 已经有「这个效果能否施加」的判定，能力侧不再实现第二套。

**成本效果必须是「无施加条件的瞬时效果」，装载期校验。** 这条把「提交阶段不会失败」变成不变量：

- 若成本效果带自己的施加条件，则第 2 段校验通过后条件仍可能在提交时改变（同一次激活内 tag 被前面的效果改掉），提交就可能中途失败，原子性立刻退化为需要回滚。
- 因此 §7 定义问题种类 `ability.cost_effect_conditional`，fail-fast 拒绝带条件的成本效果。要在成本里表达条件，把条件写进能力的闸门（数据）或 handler 的纯查询（代码）。

**原子性靠两阶段提交，不靠回滚。**

- 所有可能失败的判定（闸门、成本检查）都在任何写之前完成。
- 写入阶段（成本提交、表现施加、冷却登记）按「不会因数据错误失败」的顺序排列。数据层面这一条由装载期不变量保证；代码层面若仍失败，是 bug，按 C17 运行期断言处理并返回失败码（C20：断言不能是唯一防线，发布期要有兜底返回值）。
- 不写事务日志、不做逆运算回滚。理由：回滚需要「记录每个写以撤销它」，这笔账一旦存在就必须覆盖所有写入路径，成本远高于把可失败判定前置。

**handler 若需要更强的原子性，必须自己先全查再施加。** handler 的表达能力强于数据（它可以做分支和多次施加），因此它的原子性由它自己负责；本 spec 只要求它经同一入口施加（K4），并在文档与接口注释里写明这条责任。

### 4.7 冷却：表达方式与时钟

**第一版提供冷却，理由与形态如下。**

旧项目 CardGameDemo 明确没有冷却，因此这条不是「沿用」，而是本 spec 新增的最小机制。提供它的理由：

- 冷却的表达成本极低：一个片段的存在性 + 一个时间戳，不需要效果的持续时长（总纲 Q5 建议第一版不做持续效果，若冷却依赖「持续效果改属性」，本条建议会与 Q5 冲突）。
- 它是编排层的东西，不属于数值层；放到业务里会立刻分叉（有的用帧数有的用秒）。

**表达方式：片段存在性，不是哨兵数值。** 装配了冷却片段 = 有冷却；未装配 = 无冷却。片段参数只有 `seconds`（非负浮点）。用 `0` 或 `-1` 表示「无冷却」违反 C14 的「省略与显式为零必须可区分」精神：`0` 秒在语义上是有效值（两次成功激活之间不得有可观测间隔差），不能兼作「没有」。

**计时用独立计时器，不用属性。** 理由：

- 用属性承载（例如 `Attr.Cooldown.Remaining`）需要一条持续效果每帧递减，而第一版没有持续效果（总纲 Q5）；用属性承载等价于提前引入持续效果。
- 属性是真值状态、要按 C11 参与往返；冷却到期时刻是一个可以从「时钟 + 起始时刻」算出的派生量，落盘违反 C11 的「只存增量不存派生」。
- 独立计时器与「事件驱动时长模型」一致的做法：不每帧遍历扫描所有冷却，而是**记录到期时刻**（`startTime + seconds`），在激活时比较当前时钟。检查是 O(1)，没有每帧递减的成本，也不会出现「两处各自递减」的双真值。

**不落盘，重启后归零。** 这是 C15（不提供存档槽）的直接后果，必须在文档里说明：第一版没有任何跨会话状态，冷却也不会跨会话。若将来做存档，冷却到期时刻是一个时间戳，落盘与否是存档层的决定，不是本 spec 的（见 Q5）。

**冷却记录不随撤销销毁。** 撤销授予后若立刻重授予，冷却必须仍然生效；否则「撤销再授予」成为绕冷却的稳定手法。因此冷却记录按 `(owner, abilityId)` 存放，寿命随 owner；owner 销毁时随之清理（不泄漏）。

### 4.8 结束策略

结束策略回答「一次激活何时算结束」。本版只有 **Instant**：`Activate` 返回即结束，激活记录在同一次调用内建立并立即归档（只保留序号与时刻用于冷却与调试）。

三条约束：

1. **结束策略不由数据给出。** 数据里没有 `duration`、`isChanneled`、`endOnInterrupt` 之类字段。理由同 §4.3：每个这样的字段都会引入「激活存活期间」的一套新不变量（中断、违约撤销、销毁顺序），而不能用「不装配片段」表达。
2. **结束策略由 handlerId 决定。** 将来的持续策略实现落在新的 handler 类别里，新增一类 handler 是代码变更（C8），装载期即可知道数据引用了它。
3. **中断（interrupt）在 Instant 下无意义。** 因此第一版不提供 `Interrupt` 入口；公开 API 里不预留空实现（总纲 §7：不允许静默双路径）。需要中断时的迁移见 Q9。

### 4.9 授予与撤销：句柄、去重、来源追踪

数据形态（运行期，不落盘）：

```text
  grants:   (owner, abilityId, sourceToken) -> 存在性        // 一个三元组一条
  instances: owner -> { abilityId -> AbilityInstance }       // 由 grants 派生维持
  cooldown:  (owner, abilityId) -> expiryTime                // 不随撤销销毁
```

规则：

1. **不变量：`instances[owner][abilityId]` 存在当且仅当该 owner 有至少一条 `(owner, abilityId, *)` 的授予记录。** 这是唯一的能力实例创建/销毁判据，没有任何其他入口能创建实例。
2. **重复授予是幂等的。** 同一三元组再次授予返回同一个 `GrantHandle` 内容（次数为 1），不产生第二条记录、不重建实例。同一 owner 不同来源授予同一能力 → 两条记录、一个实例（引用计数语义）。
3. **撤销按三元组。** 一个来源的 `GrantHandle` 析构只撤销自己那条记录；记录集合空时才销毁实例。因此「装备 A 和装备 B 都给这个能力」时，卸下 A 不会让能力消失——这是旧项目里靠手清布尔标志做不到的，也是本 spec 引入来源追踪的唯一理由。
4. **句柄语义遵守 C25。** `GrantHandle` 是 RAII 值，析构即撤销；拷贝语义明确为移动或不拷贝（两者择一，写进接口注释）；双重释放触发运行期断言（C17 第二类）。持有者在 `OnDeactivate` / `Shutdown` 里先让句柄失效（C34）。
5. **撤销不等待进行中的激活。** Instant 下没有「进行中的激活」，因此撤销是同步的、无需排队；这一点使第一版不引入撤销队列（将来持续激活时见 Q9）。
6. **来源令牌是值类型，不是裸字符串。** 判别 + 标识字段：内容装配 → 定义 ContentId；图节点 → 图实例引用 + 节点标识（后者由 CORE-F05 提供的值类型）。裸字符串会让「来源消失」与「来源拼错」无法区分。

```cpp
// Sketch, not a final signature.
/// @brief Owns one source claim on an ability and revokes it on destruction.
/// @warning Moving transfers the claim; copying is deleted so that a claim can
///          never be revoked twice.
class MGFGrantHandle
{
public:
    MGFGrantHandle(MGFGrantHandle&& other) noexcept;
    MGFGrantHandle(const MGFGrantHandle&) = delete;
    ~MGFGrantHandle();

private:
    // Internal: holds the owner, the ability id and the source token.
    MGFGrantKey m_key;
    MGFAbilityRuntime* m_runtime = nullptr;
};
```

### 4.10 能力来源之二：图节点激活钩子

能力只有两种来源（K12）：

1. **内容装配**：CORE-F03 的片段装配里有一个「授予能力」的片段，内容是能力定义的 ContentId 列表。授予在实例构造时发生，来源令牌 = 该内容定义的 ContentId。
2. **图节点激活**：CORE-F05 的节点在被激活时通过钩子授予能力。来源令牌 = (图实例, 节点标识)。

对接约定（对 CORE-F05 的接口要求，本节不假手图内部结构）：

- 能力运行期只暴露两个函数：`GrantFromNode(owner, abilityId, nodeToken) -> GrantHandle` 与 `RevokeByToken(nodeToken)`。后者撤销该节点的全部授予，用于节点去激活、图卸载、图实例销毁三条路径。
- **图节点不持有能力内部状态。** 节点不知道自己授予了几个能力、也不查询冷却；能力运行期不读图结构（K13 的可检验形式是「不 include 图模块头」）。
- **由谁解析 payload：CORE-F05 的 payload 解析业务。** 总纲规定「一种图对应一种解析业务」；「这个节点的 payload 指向哪个能力 ContentId」由该业务的解析器在节点激活时给出，能力运行期只收 `abilityId`。
- **节点去激活的时序在 Variable 相位推进**（C22、C27：状态机推进，不串事件链）。因此授予与撤销都只在该相位生效；图在 Fixed 相位推进时不得直接调用本 spec 的入口。
- 若 CORE-F05 最终提供的钩子不是「激活/去激活」而是「状态迁移」，以 CORE-F05 为准并把节点令牌换成迁移携带的节点标识；能力侧的语义不变（K11 只依赖「来源可标识、可撤销」）。
- **钩子形态已定（CORE-F05 §9.4）**：激活与去激活是解析器上的 `OnActivated` / `OnDeactivated`，节点标识是值类型 `MGFNodeId`；卸载钩子**已提供**——`OnGraphUnloading` 在卸载 / 销毁前调用一次，携带图实例 id 与只读 Active 名单，钩子内不得提交迁移、不得落盘，且**不提供逐节点卸载钩子**（卸载不是状态迁移，业务真正需要的只是那张 Active 名单）。因此「图卸载」这条路径就是：在 `OnGraphUnloading` 里枚举 Active 名单、逐个 `RevokeByToken`。若该钩子在未来被移除，卸载路径退化为按节点令牌撤销（K11 只依赖「来源可标识、可撤销」）。

### 4.11 目标侧准入：施加前与持续的分工

Unreal GAS 把准入拆成两组要求：`applicationTagRequirements`（施加前判一次）与 `ongoingTagRequirements`（存活期持续判）。本 spec 采纳这个拆分，因为二者不能互相替代：

| | 施加前准入 ApplicationAdmission | 持续准入 OngoingAdmission |
| --- | --- | --- |
| 何时判 | 激活管线第 1 段，判一次 | 激活存活期间，每次相关 tag 变更后重判 |
| 判定对象 | owner、source、target 三侧 | 同左，复用同一份条件结构 |
| 违约后果 | 本次激活不开始，返回 `GateFailed` + 子原因 | 中断该次激活（移出激活记录、按撤销路径收尾） |
| 为什么不能省 | 没有它，成本会在不该花的时候被花掉 | 没有它，「施加后目标变成不可施加」这件事只能靠每帧轮询发现 |
| 本版是否做 | 做（K8） | 不做（无存活期，见 Q3） |

关键点：**两者共享同一份条件结构与同一个求值函数。** 若各写一套，迟早出现「施加前认为可以、持续期认为不可以」的语义漂移。因此 §4.2 的六组字段是唯一权威，持续准入在将来只是「换个调用时机」。

为什么能力侧要做目标准入，而不是全靠 CORE-F02 的效果施加条件：效果的施加条件回答「这个效果能不能贴到这个目标上」（数值层的局部问题）；能力的准入回答「这次编排能不能开始」（编排层的全局问题，涉及来源与 owner）。二者作用点不同，且能力必须在花钱之前就知道答案。若只靠效果条件，成本已经被扣掉才会发现表现效果贴不上。

### 4.12 能力与效果的边界：唯一入口

**能力施加效果的唯一入口，是 CORE-F02 的效果施加入口。** 这条要在两处同时成立：

1. 数据声明的效果列表（`costEffects`、`appliedEffects`）由能力运行期按序调用该入口施加。
2. handler 的代码逻辑施加效果时，也调用同一入口。handler 不允许持有属性写接口、不允许自建结算。

因此「能力施加效果」的调用图里只有一条边：

```text
  激活管线 / handler ──> EffectGateway.Apply(target, effectIds, cause)
                              └─> 属性全量重聚合（CORE-F02）
```

需要 CORE-F02 提供的接口（§9 会再列一次）：

- 「可施加查询」：给定目标与效果 id，无副作用地返回能否施加 + 原因码。
- 「施加」：给定目标与效果 id 序列，施加并触发重聚合，返回结构化结果。
- 「cause 标识」：一次施加的可追溯标识（用于 C29 审计与调试），本 spec 建议它就是 `SourceToken` 的扩展形态；若 CORE-F02 已定义等价概念，以它为准。

施加上下文里的其他字段由 CORE-F02 定义，本块不新增也不解读：例如 `contentHint`（可选的内容 id 提示，用于效果内部再引用内容），它与图节点 payload 是**同名不同物**的两个概念——后者是 CORE-F05 的节点内联对象。本块只负责把 `cause` 传进去。

反例（本 spec 禁止，且可 grep）：

```cpp
// Sketch, not a final signature. Never do this from a handler: it writes the
// current value directly, so re-aggregation has no chance to correct it.
owner.mutableAttributes().SetCurrent(Attr::Mana, mana - 20.0);
```

### 4.13 边界情况

| 情况 | 处理 |
| --- | --- |
| 冷却中再次激活 | 返回 `CooldownActive` + 剩余秒数；不排队、不扣费、不改任何状态 |
| 同一次激活被同一帧调用两次 | 顺序求值：第一次成功并登记冷却与序号，第二次按冷却规则拒绝（无冷却的能力则两次都成功，序号递增） |
| owner 销毁 | 撤销其全部授予记录、销毁全部能力实例、清理其冷却记录（随 owner 寿命，不泄漏）；句柄持有者释放时按 C25 安全（运行期记录已不可见，句柄析构是空操作并计数） |
| target 在激活中被销毁 | 闸门第 1 段前校验目标有效性；`GateFailed` 子原因 `target_invalid`。管线内不持有裸指针跨段（C36） |
| 撤销后立刻重授予 | 冷却仍生效（§4.7 末条）；能力实例销毁重建，激活序号是否重置见 Q8，本版建议**不重置**并对 owner 单调 |
| 成本效果引用在装载期缺失 | 属 C13 第二段解析失败，装载期 fail-fast 并列出缺失 id；运行期不出现「缺成本」的能力 |
| `handlerId` 未注册 | 装载期 fail-fast（§4.4）；运行期不可能出现 |
| 冷却片段参数为负 | 装载期 fail-fast（`ability.cooldown_negative_duration`） |
| 提交阶段意外失败（数据不变量被破坏） | 运行期断言 + 返回失败码（C20）；不尝试回滚（§4.6） |
| 内容重新装载（切换内容包） | 本版不支持运行期内容注册（总纲 §2.2），因此能力定义集合在一个加载闸口内固定；「重新装载」等于重建注册表与能力运行期（会话级） |

## 5 契约

每条为「规则 + 可检验」，并标注它细化了总纲的哪条契约。

**K1 定义与逻辑分离，接口是一个字符串契约。** 能力定义只承载数据（闸门 tag 名、效果引用、`handlerId`、片段装配）；一切无法用数据表达的逻辑在代码里按 `handlerId` 注册。装载期校验 `handlerId` 命中，未命中 fail-fast。
细化 C8（必须存在于代码里的东西）、C2（引用形态）。
可检验：新增一个能力只需「加一份内容资产 + 一个 `handlerId` 常量 + 一份处理器实现」，不改框架代码；把 `handlerId` 写成未注册值，装载失败且问题项包含该字符串。

**K2 能力定义的字段集合封闭。** 字段集合等于 §4.2 的表格，不允许多一个。新增字段必须先改本 spec。
细化 C7、C8。
可检验：一条用例断言能力定义类的反射属性名集合与契约表逐字段相等（顺序无关）；多一个字段即失败。

**K3 禁止用数据关闭框架默认行为。** 能力定义中不得出现语义为「跳过/手动/时机/开关」的字段；差异化只能通过片段存在性、`handlerId` 选择、内容引用表达。
细化 C7、C8、C14（省略与显式为零可区分）。
可检验：字段集合用例（K2）自动覆盖；另加一条审查项——能力定义类属性名不匹配 `(Skip|Manual|Timing|Policy|Override|Enable)` 词表，命中即为违规。

**K4 能力施加效果只有唯一入口。** 能力运行期（含全部 handler）不得直接读写属性，只能调用 CORE-F02 的效果入口。
细化 C29（每个状态只有一个写入点）、C6（只存基值、重聚合）。
可检验：能力运行期源码 grep 属性写接口为 0 命中；一条对账用例：同一 owner 上「经能力施加的效果集合」与「直接施加等价效果」得到逐字段相同的当前值。

**K5 成本由无条件的瞬时效果引用承载。** `costEffects` 是有序效果 ContentId 列表；引用的效果不得自带施加条件（装载期 fail-fast）。
细化 C2、C4（定义只读）、C13（引用两段解析）。
可检验：写一份带条件的成本效果，装载失败并指向该效果与字段；把成本引用改成不存在的 id，装载失败并列出缺失 id。

**K6 激活管线五段且顺序固定。** 闸门 → 成本检查 → 成本提交 → 表现 → 冷却登记与激活记录。不存在重排阶段的数据手段。
细化 C27（不依赖事件链，顺序写成显式流程）、C29。
可检验：一条用例用阶段回调记录实际执行顺序，与契约序列逐项相等；内容资产里不存在影响阶段顺序的字段（K2 覆盖）。

**K7 闸门是唯一准入位置且无副作用。** owner / source / target 三侧的 required 与 blocked 条件全部求值后再汇总（不短路），并在任何写入前完成。
细化 C19（未知 tag fail-fast）、C24（无 payload 通知，闸门不依赖事件）。
可检验：三组各一条用例（缺 required / 命中 blocked / 通过）；一次被拒绝的激活后，属性、冷却、激活记录的字节快照与激活前逐字段一致。

**K8 施加前准入与持续准入分工明确。** 施加前准入三侧判一次，失败返回 `GateFailed` + 子原因；持续准入在 tag 变更后重评估，共享同一条件结构与求值函数。本版只实现施加前准入。
细化 C22、C24。
可检验：求值函数只有一处实现（grep 三侧条件的求值调用点唯一）；施加前失败的失败码含子原因（`owner_missing_required` 等），且用例覆盖三侧各一条。

**K9 两阶段提交，不回滚。** 所有可能失败的判定前置；写入阶段按不失败排序；提交阶段若失败视为不变量破坏，断言 + 失败码，不尝试撤销。
细化 C17（运行期断言类）、C20（断言不是唯一防线）、C21（结果可见）。
可检验：构造「成本有两条效果、第二条不可施加」的用例，激活返回 `CostUnavailable` 且状态零变化；再构造断言关闭配置，提交阶段的意外失败仍返回失败码而不是继续执行。

**K10 冷却由片段存在性表达，独立计时，不落盘。** 装配冷却片段 = 有冷却；参数只允许非负秒数；到期时刻由单一世界时钟 + 起始时刻算出，不做每帧递减；冷却记录按 `(owner, abilityId)` 存放，不随撤销销毁。
细化 C14、C11（只存增量）、C22（时钟只在 Variable 相位推进）。
可检验：不装配冷却的能力连续两次激活均成功；装配后第二次在冷却内失败并返回剩余秒数；任何持久化文档中不存在冷却字段（grep schema 定义）。

**K11 授予与撤销按来源令牌引用计数。** 授予三元组唯一；重复授予幂等；一个来源的句柄析构只撤销自己那条；实例集合非空才存在。
细化 C25（RAII 句柄语义）、C5（实例状态只有三段）。
可检验：两个来源授予同一能力 → 实例 1 个、记录 2 条；撤销一个来源后能力仍可激活；撤销两个后能力不可激活且实例计数为 0；同一句柄二次释放触发运行期断言。

**K12 能力来源封闭为两种。** 内容装配与图节点激活；运行期不存在「凭空创建能力」的公开入口。
细化 C2、C36（跨边界只传 id）。
可检验：授予入口的调用点只有两处（内容装配构造路径、图节点钩子）；全仓 grep 找不到第三条创建能力实例的路径。

**K13 能力运行期不依赖图结构。** 与 CORE-F05 只有两个函数的接触面（按令牌授予、按令牌撤销），不 include 图模块头、不读节点数据。
细化 C36、C31（真值归属单一）。
可检验：能力运行期源文件的 include 列表不含图模块头（grep）；节点去激活后能力不可激活（用例）。

**K14 能力实例与激活记录分离。** 能力实例遵守 C5 的三段形态；激活记录是纯运行期结构，不进入任何实例字段表、不进入任何序列化 schema。
细化 C5、C11。
可检验：能力实例类反射属性集合 = 三段（用例）；全仓 schema 定义中不出现激活记录类型（grep）；写盘文档里不含激活序号与冷却到期时刻。

**K15 结构化结果与封闭失败码。** 激活、授予、撤销入口都返回结构化结果（成功 / 失败码 / 附带数据如剩余冷却或问题列表），不用布尔。
细化 C21。
可检验：公开入口返回类型检查（静态审查项：语义为「是否成功」的 bool 返回公开函数为零）；失败码来自一个封闭枚举，用例对每个枚举值至少覆盖一次。

**K16 相位与重活限制。** 激活、授予、撤销只允许在 Variable 相位或显式请求路径执行；管线内不做资产装载、不做反射实例化、不做序列化。
细化 C22、C23。
可检验：Fixed 相位调用激活返回失败码（或调试期断言）；激活路径上的反射实例化计数为 0（覆盖到激活调用的计数器用例）。

**K17 词汇表与命名。** 能力侧新增 tag 全部走代码常量并在静态构造期注册；两段名字各指一件事，不得混用（C38）：`Ability.*` 只指**能力运行期**自己的 tag（`Ability.Gate.*`、`Ability.State.*`），「某片段授予的能力标签集」属内容定义族、命名在 `Fragment.Cap.*` 段（CORE-F03 的 CapabilityTags），不是独立领域段；内容里只出现 tag 名字字符串。
细化 C37、C38、C41。
可检验：grep 能力运行期与能力内容的 tag 使用处，实参不是字面量；装载期未知 tag fail-fast（C19 用例）；能力定义里引用的 tag 只能是两类——`Ability.` 段的运行期 tag，或既有领域段的既有 tag（含 `Fragment.Cap.*` 的能力标签集），新造领域段即失败（审查项 + 命名用例）。

## 6 数据与序列化

### 6.1 进 DataAsset 的字段

只有三类（与 C7 对齐）：数值与开关、装配关系、内容引用。

| 数据 | 承载 | 说明 |
| --- | --- | --- |
| 闸门六组 tag 名字 | 能力定义的字符串数组字段 | 加载期按 C19 校验 |
| 成本 / 表现效果引用 | 有序 `MGFContentIdRef` 数组（CORE-F03 的唯一引用编码：`kind` + `name`） | 加载期按 C13 两段解析 |
| 冷却时长 | 冷却片段参数（非负浮点） | 片段存在即生效 |
| `handlerId` | 单条字符串 | 代码契约，加载期查注册表 |

不写进 DataAsset 的：任何「当前值」「剩余冷却」「激活序号」「授予集合」。它们要么是派生（重聚合得到），要么是纯运行期（§4.1 的激活记录）。

### 6.2 派生与运行期状态

| 状态 | 类别 | 是否落盘 | 重新得到的方式 |
| --- | --- | --- | --- |
| 属性当前值 | 派生（C6） | 否 | 全量重聚合 |
| 冷却剩余 | 派生（时钟差） | 否 | 无（会话外不存在） |
| 授予集合 | 运行期真值 | 否 | 由内容装配与图状态重建（图状态本身是 CORE-F05 的持久化责任） |
| 激活序号 | 运行期真值 | 否 | 从 0 重来 |
| 激活记录 | 运行期瞬时 | 否 | 不需要 |

### 6.3 本 spec 不新增持久化文档

这是本 spec 最重要的一条数据结论：**CORE-F07 不定义任何自己写盘的文档，因此它没有自己的 schemaVersion。**

- 能力定义是内容资产，其版本由内容包与 CORE-F03 的装载校验负责（C10、C42）。
- 能力实例按 C11 只有增量；它的持久化形态与任何其他实例完全一致，本 spec 不新增字段。
- 授予集合不落盘。理由：C15 已把存档槽列为范围外；一旦能力运行期自己写盘，就凭空造出第二份「哪些能力已学会」的真值（违反 C31），而它的正确来源是内容装配与图状态。

因此「往返等价」在本 spec 的可检验形式是**否定式**：写盘文档的字段集合不因能力功能而增加任何一项。

### 6.4 ContentId 引用编码只有一份

能力数据里的效果引用与图 payload 里的能力引用都用 CORE-F03 的 **`MGFContentIdRef`**（`kind` + `name` 两个 primitive 字段）；本 spec 不定义第二套编码。若 CORE-F03 未来改用别的编码，只改资产侧字段类型，§4.2 与 K2 的语义不变（它们约束的是「有序 ContentId 序列」这一层，不是编码）。

## 7 校验与失败

### 7.1 三级分类在本 spec 的落点

| 级别 | 本 spec 的具体落点 |
| --- | --- |
| 加载期 fail-fast | `handlerId` 未注册或重复注册；成本/表现效果引用缺失（C13 第二段）；成本效果自带条件；冷却时长为负；能力定义出现未知字段；能力定义里的 tag 未注册（C19）；能力定义的内容 id 非法或重复（C1） |
| 运行期断言 | 激活记录被移除两次；提交阶段意外失败；`GrantHandle` 双重释放；冷却剩余为负；能力实例存在但没有对应授予记录（不变量 4.9-1 被破坏）；Fixed 相位调用激活 |
| 允许的降级 | 可选内容包未装载导致某能力定义整体缺失时，引用它的图 payload 按 C17 降级（丢弃该边/该授予并警告）；能力定义引用的表现效果属于可选包且缺失时，警告并跳过该条效果（该降级有开关，关闭后升为 fail-fast） |

### 7.2 问题种类清单

| 种类码 | 级别 | 触发 | 消息必须包含 |
| --- | --- | --- | --- |
| `ability.handler_missing` | fail-fast | `handlerId` 在注册表里没有 | 定义 id、`handlerId` 原值、已注册数量 |
| `ability.handler_duplicate` | fail-fast（装配期） | 同一 `handlerId` 注册两次 | 该 `handlerId`、两个注册点的模块名 |
| `ability.handler_empty` | fail-fast | `handlerId` 为空或字符集非法 | 定义 id、原值与允许字符集 |
| `ability.cost_effect_conditional` | fail-fast | 成本引用了一个自带施加条件的效果 | 定义 id、效果 id、条件字段位置 |
| `ability.cost_effect_missing` | fail-fast（C13 第二段） | 成本效果 id 未解析 | 定义 id、全部缺失 id |
| `ability.applied_effect_missing` | fail-fast（C13 第二段） | 表现效果 id 未解析 | 同上 |
| `ability.tag_unregistered` | fail-fast（C19） | 六组 tag 里有未注册的名字 | 定义 id、字段名、完整 tag 名、需要新增的词汇表条目名 |
| `ability.field_unknown` | fail-fast | 定义出现 §4.2 之外的字段 | 定义 id、字段名 |
| `ability.cooldown_negative_duration` | fail-fast | 冷却片段参数为负 | 定义 id、片段位置、原值 |
| `ability.instance_without_grant` | 运行期断言 | 实例存在但授予记录为空 | owner 标识、能力 id |
| `ability.double_remove` | 运行期断言 | 同一激活记录被移除两次 | owner、能力 id、激活序号 |
| `ability.submit_failed` | 运行期断言 | 提交阶段失败（不变量破坏） | owner、效果 id、失败原因 |
| `ability.phase_violation` | 运行期断言 | Fixed 相位或 tick 内装载路径调用激活 | 当前相位、调用点 |

### 7.3 激活结果失败码（封闭集合）

`Activated`、`GateFailed`（子原因：`owner_missing_required` / `owner_blocked` / `source_*` / `target_*` / `target_invalid` / `handler_refused`）、`CostUnavailable`（附未满足的效果 id 列表）、`CooldownActive`（附剩余秒数）、`AbilityNotGranted`、`PhaseViolation`、`InternalInvariant`（附问题列表）。

封闭集合的含义：新增一个失败码需要改代码（C8），并且必须同时补一条用例（K15）。

## 8 可迁移性注记

逐条判断：去掉 C++ 与 minEngine 的具体 API 之后是否成立。

| 条目 | 判断 | 说明与条件 |
| --- | --- | --- |
| 定义（内容）与逻辑（`handlerId` 注册表）分离 | 成立 | 任何语言都能表达「数据给出名字，代码按名字查表」；条件是该语言能在启动期建一张不可变映射 |
| 字段集合封闭、禁止跳过开关（K2、K3） | 成立 | 是纪律而非设施；目标侧只需一个可枚举字段的反射或一份手工清单 |
| 五段固定管线（K6） | 成立 | 顺序是设计决策，与语言无关 |
| 成本以效果引用承载（K5） | 条件成立 | 需要目标侧的效果系统提供「可施加查询」与「施加」两段式接口；若只有一次性 `Apply`，需先补查询，否则原子性无处成立 |
| 两阶段提交、不回滚（K9） | 成立 | 「把可失败判定前置」与语言无关；不依赖事务设施，这是它的价值 |
| 授予引用计数 + RAII 句柄（K11） | 条件成立 | 需要确定性的析构或等价的 `defer`/`finally`/`with` 结构；GC 语言需改用显式 `Release` 并由所有权类型包裹 |
| 来源令牌是值类型（K11） | 成立 | 值类型在任何语言都能表达 |
| 目标侧施加前准入（K8） | 成立 | 纯判定，无设施依赖 |
| 冷却用到期时刻而非每帧递减（K10） | 成立 | 需要「一个世界时钟」；若目标侧只有帧计数，冷却单位改为帧并保留同一条「只记录到期点」的规则 |
| 图节点钩子对接（K13） | 条件成立 | 需要图模型提供节点生命周期通知（激活/去激活/卸载）；若图只有迁移函数，需在图侧暴露迁移结果供订阅 |
| 能力运行期的会话状态要有生命周期容器（§4.4） | 条件成立 | 需要某种生命周期容器（与总纲第 6 节同一条件）；不新增子系统，用既有的实例与场景容器，无容器时用显式生命周期的服务对象 |
| 层数上限 / 堆叠（不做） | 不成立 | 本 spec 不承担；若迁移时目标侧需要，属效果堆叠语义，不是编排语义 |

## 9 与其它块的关系

### 9.1 依赖方向与真值归属

| 关系 | 方向 | 谁持有真值 | 本 spec 需要对方提供 |
| --- | --- | --- | --- |
| CORE-F02 属性与效果 | 能力 → 效果（单向） | 属性当前值与修饰器在 CORE-F02 | 「可施加查询」「施加」「cause 标识」三个接口——**已向 CORE-F02 提出，等其 §9.3 定稿形态**，定稿前本块按最小接口编程（一次可施加查询 + 一次施加 + 一个可追溯标识），签名变化只影响适配层；另需成本效果「无条件」这一属性可被查询（用于装载校验） |
| CORE-F03 内容定义 | 能力 → 内容（单向） | 内容定义与注册表在 CORE-F03 | `ability` 这个 kind 的登记；片段装配机制（冷却、授予片段）；引用编码 `MGFContentIdRef`（CORE-F03 的唯一编码）；装载期问题列表的接入点 |
| CORE-F05 图模型 | 图 → 能力（运行期调用方向：CORE-F05 的解析器在钩子里调用本块的授予接口；不是依赖方向） | 图状态在图实例 | 三个钩子与节点标识类型（CORE-F05 §9.4 已定）：`OnActivated` / `OnDeactivated`（解析器钩子）与卸载钩子 `OnGraphUnloading`（卸载前一次，携带图实例 id 与只读 Active 名单，钩子内不得提交迁移或落盘，不提供逐节点卸载钩子），节点标识 `MGFNodeId`；payload → 能力 ContentId 的解析业务 |

除组合根在装配期调用本块的授予与注册接口外，本块**不被任何 gameplay 块 include 依赖**：没有 gameplay 块需要在源码里依赖能力运行期来实现自己的规则（唯一例外是内容里的「授予能力」片段，那是数据而非依赖）。这个装配边的不对称性要写清：组合根 include 本块的头并在启动时注册处理器，**本块不 include 任何 gameplay 模块头**（§10.2 第 10 条的 grep 判据覆盖能力运行期的 include 与引擎符号），因此该边的存在不改变依赖方向，也不进入任何 gameplay 规则——它是一次性的启动注入，不是规则依赖。表中「图 → 能力」一行说的是这条运行期调用方向（业务侧解析器在 CORE-F05 的钩子里调授予接口），同样不是依赖方向。

### 9.2 我需要对方提供的接口（最小集）

先写接口的状态，因为在对方定稿前把签名当契约是两边对不上的根源：下面第 1、2 条**已向 CORE-F02 提出，等待 CORE-F02 §9.3 给出定稿形态**；定稿前本块按**最小接口编程**——只要「一次可施加查询 + 一次施加 + 一个可追溯标识」三件语义，不依赖签名与结构，签名变化只影响适配层的一个实现文件。第 4 条已由 CORE-F05 §9.4 满足（含卸载钩子，见下）。

1. 可施加查询（无副作用，附原因码）。名字暂记 `EffectQuery::CanApply(target, effectIds)`，等 CORE-F02 §9.3 定稿。
2. 施加（唯一写属性入口，返回结构化结果）。名字暂记 `EffectGateway::Apply(target, effectIds, cause)`，等 CORE-F02 §9.3 定稿；`cause` 是可追溯标识，若 CORE-F02 已有等价概念以其为准。
3. `ContentRegistry::Find(ContentId) -> const AbilityDef*`（C4 的只读语义）。
4. 节点激活、去激活、卸载三条上的钩子与节点标识类型（Variable 相位推进，C22）：**已满足**（CORE-F05 §9.4）——`OnActivated` / `OnDeactivated` / `OnGraphUnloading` 三个钩子与 `MGFNodeId` 均已定；`OnGraphUnloading` 在卸载前调用一次、携带图实例 id 与只读 Active 名单、钩子内不得提交迁移或落盘，不提供逐节点卸载钩子。若该钩子在未来被移除，卸载路径退化为按节点令牌撤销（K11 只依赖「来源可标识、可撤销」）。
5. 问题列表的追加接口（C18 聚合，不逐条中断）。

### 9.3 我向对方提供的接口

1. `GrantFromNode(owner, abilityId, nodeToken) -> GrantHandle` / `RevokeByToken(nodeToken)`（给 CORE-F05）。
2. `HandlerRegistry::Register(handlerId, handler)`（给组合根，装配期调用）。这张表是**代码契约表**而不是会话子系统：组合根构造一次、此后只读，CORE-F06 §4.2 的五个 GI 子系统清单里没有它，也不需要第六个；运行期的激活记录与冷却才是会话状态，按 CORE-F06 的真值归属表落位（随实例与所在场景）。
3. 「授予能力」片段所需的装载期校验入口（给 CORE-F03，用于把 `ability.handler_missing` 等并入统一问题列表）。

### 9.4 与总纲的一处边界差异（记录，不自行改契约）

本节记录一条**曾经存在、现已解决**的边界差异。总纲 §9 Wave4 判据 2 的原措辞是「若保留 CORE-F07：能力可施加/中断/移除…层数上限可配」，当时的差异分析如下（保留作为「为什么这两项不在本块边界」的记录）：

- 「移除」对应授予撤销（K11），成立。
- 「中断」在只有瞬时激活的第一版没有语义（§4.8）。若要满足该条，必须先引入持续激活（Q3 + Q9），成本是把「激活存活期」的一整套不变量引入第一版。
- 「层数上限」是效果堆叠语义（CORE-F02），不是编排语义。本 spec 不引入「能力层数」。

处理结论（R3 关闭）：总纲 R2 的 A12(b) 已把该条判据改为「能力可施加与移除，且移除后属性重聚合与从未施加一致；目标侧准入门槛拒绝时返回明确失败码；层数上限由 CORE-F02 的堆叠契约覆盖，中断随持续激活进 Wave4 之后」，与本 spec 的设计一致，**本条关闭**——本 spec 不再向总纲提改动请求，§10.2 的判据已按同一口径对齐。总纲 §9 Wave4 的判据同时已分成「若保留 / 若砍掉」两种情形，砍掉一侧由 §10.3 承接。

### 9.5 模块归属（遵守总纲 §4.1 / §4.2）

| 内容 | 模块 | 理由 |
| --- | --- | --- |

## 10 实现波次与验收判据

### 10.1 波次归属

本 spec 落在总纲 §9 的 **Wave4**（与「样本内容」同波），因为它是唯一依赖 Wave1–Wave3 全部产物（内容定义、效果、实例、图钩子）的块。

内部再分两步，便于「临门砍掉」：

- **F07-a（管线本体）**：定义字段、处理器注册表、五段管线、成本原子性、施加前准入、授予与撤销、冷却。产出可跑通全部 K 契约的用例。
- **F07-b（图钩子对接）**：与 CORE-F05 的节点钩子接线。若 CORE-F05 的钩子形态未定，本步可后置而不影响 F07-a 的验收。

### 10.2 验收判据（可执行）

1. `ctest` 全绿，且至少覆盖 K1、K2、K3、K6、K7、K9、K10、K11、K14、K15 各一条用例。
2. `handlerId` 未注册的能力内容装载失败，问题列表包含该字符串（K1）。
3. 能力定义类的反射属性名集合与 §4.2 字段表逐字段相等（K2/K3）。
4. 一条用例记录管线实际执行顺序，与 K6 的序列逐项相等。
5. 闸门三侧各一条拒绝用例，失败码子原因正确（K7/K8）；这就是总纲 Wave4 判据 2 的「目标侧准入门槛拒绝时返回明确失败码」。
6. 「成本两条、第二条不可施加」的原子性用例通过，状态快照零变化（K9）。
7. 冷却用例：无冷却连发两次成功；有冷却第二次拒绝并给出剩余秒数；写盘文档中无冷却字段（K10）。
8. 授予与移除用例：两来源一实例、逐来源撤销、全撤销后不可激活、句柄二次释放触发断言（K11/K12）；「移除」即总纲 Wave4 判据 2 的「能力可移除」，移除后该能力不可再激活。
9. 对账用例：经能力施加的效果与直接施加等价效果的当前值逐字段一致（K4）。
10. grep 检查：能力运行期源码中属性写接口 0 命中、字面量 tag 0 命中、图模块头 include 0 命中（K4/K13/K17）；`mgf-core` 引擎符号 grep 为空（沿用总纲 4.2 检查项）。
11. 示例内容装载零问题，且示例只用既有契约表达（新增契约即回退改文档）。
12. 断言关闭配置下重跑 2–11，失败路径仍返回失败码而不是继续执行（C20）。

### 10.3 砍掉时的验收判据

若作者决定砍掉本 spec（状态标 Deferred），Wave4 仍必须满足（对应总纲 §9 Wave4 判据 3 的「若砍掉」一侧）：

1. 示例内容包（属性、片段、物品、配方/科技图各一）装载零问题。
2. 内容里不出现 `ability` kind 的任何定义（避免留下「数据里引用了不存在的能力」的半成品）。
3. `FEATURE_REGISTRY` 中 CORE-F07 状态改为 Deferred，并写明解冻条件（例如「出现第二个业务模块重复实现准入+成本，或内容规模超过 N 条需要数据化准入」）。
4. 替代路径的写法（§1.1）作为示例内容的一部分被记录，让后来者看得见它为什么不可复用。

## 11 待决问题

每条给选项、我的建议、以及会推翻建议的条件。

**Q1 能力定义是否独立 kind。** 选项：(a) `kind = ability` 的独立内容定义；(b) 能力是挂在任意实例定义上的片段（无独立身份）；(c) 能力就是图 payload，无内容定义。
建议 (a)。理由：`costEffects` / 六组 tag / `handlerId` 需要一个可被 ContentId 引用的稳定身份（图 payload 要引用它，C2 要求引用一律用 ContentId），片段没有身份，payload 又不该承担数值数据。
什么会推翻它：若能力绝不被任何其他内容引用（只由输入直接触发），(b) 更省一层；但只要图要授予能力，(b) 立刻不成立。

**Q2 冷却第一版是否提供。** 选项：(a) 提供（本 spec 的 §4.7）；(b) 不提供，冷却归业务。
建议 (a)。理由：表达成本是一个片段 + 一个时间戳，而放到业务里必然分叉成帧数/秒两种口径；且它与「暂不做持续效果」不冲突（到期时刻法不需要持续效果）。
什么会推翻它：若第一版示例内容完全没有冷却需求，优先砍它（它比管线本体更好砍），并把 Q2 的结论记为 Deferred。

**Q3 持续准入（`ongoingTagRequirements`）是否第一版。** 选项：(a) 不做，只在文档里保留分工定义；(b) 做，与施加前准入共享条件结构。
建议 (a)。理由：持续准入必须有「激活存活期」，而存活期需要持续激活（总纲 Q5 建议第一版不做持续效果），二者绑定。
什么会推翻它：若第一批示例内容就必需「施加后目标失去资格要自动失效」，则 (b) 提前，并同时引入持续激活的最小形态（此时 CORE-F02 的持续效果也必须提前）。

**Q4 能力状态是否需要新增子系统。** 选项：(a) 不新增——`handlerId` 映射是组合根持有的只读**代码契约表**（装配期构造一次，不占子系统名额），运行期的激活记录与冷却是**会话状态**，按 CORE-F06 的真值归属表落位（随实例与所在场景）；(b) 新增第六个 GI 子系统统一承载两者；(c) 把两者都塞进内容注册表子系统。
建议 (a)，并已按作者裁定落定（R3 / B11），本条保留为记录。理由：CORE-F06 把会话内 GI 子系统封闭为五个，那张清单就是所有权清单；而 `handlerId` 映射不持有 gameplay 真值、随代码走，本来就不该出现在所有权清单里。此前问「子系统归属确认」正是把代码契约表与会话状态混成了一件事。
什么会推翻它：若运行期激活状态在 CORE-F06 的真值归属表里找不到落点（既不属于实例也不属于场景），例如需要一份跨场景的全局冷却；那时必须先改 CORE-F06 的归属表，而不是在本 spec 里开第六个子系统。

**Q5 授予集合是否需要持久化。** 选项：(a) 不落盘，由内容装配与图状态重建；(b) 落盘为实例增量的一部分。
建议 (a)。理由：C15 已把存档槽列为范围外；若能力运行期自己写盘，就造出第二份「学会哪些能力」的真值（违反 C31）。
什么会推翻它：若存档层落地时图状态不持久化，则授予必须由其他来源重建，(b) 成为唯一可行解，届时应改 C11 的文档集合而不是在本 spec 里偷写。

**Q6 成本是否允许部分成功。** 选项：(a) 绝不允许（全查全写）；(b) 允许按顺序扣到失败为止。
建议 (a)。理由：部分成功等价于引入「半截状态」，它要求每个调用方都能处理「扣了一半」的情形，而 C6 的重聚合对账无法察觉这类差异（数值仍然自洽）。
什么会推翻它：没有合理场景；若出现，应作为新契约回来写，而不是在本条上放宽。

**Q7 `handlerId` 是否需要版本或弃用策略。** 选项：(a) 不引入版本，改名即破坏已发布内容，靠装载期 fail-fast 暴露；(b) 引入 `handlerId@v2` 之类的版本段。
建议 (a)。理由：与 C37/C41 对 tag 的取向一致（只增不删、废弃只标记）；`handlerId` 的合法集合来自代码，装载期 fail-fast 已经能把改名变成一次明确的装载失败而不是静默失效。
什么会推翻它：若框架被第三方用作 SDK 且需要并行支持两个语义版本，才需要 (b)。

**Q8 激活序号是否对 owner 单调还是对能力单调。** 选项：(a) 按 `(owner, abilityId)` 单调，撤销不重置；(b) 按能力实例单调，撤销即从 0 重来。
建议 (a)。理由：序号是调试与日志的定位手段，撤销后重置会让「第 3 次施放」在两个实例里都出现，日志无法对齐；成本只是一个计数器。
什么会推翻它：若序号需要参与玩法（例如「每第三次施放强化」），则它必须变成效果可读的属性，那是 CORE-F02 的堆叠/计数语义，本 spec 应让位。

**Q9 中断入口是否预留。** 选项：(a) 不预留任何入口（本 spec 的 §4.8）；(b) 预留 `Interrupt(handle)` 的空实现并在 Instant 下始终失败。
建议 (a)。理由：总纲 §7 的重构纪律明确禁止「先留着，以后再收」的静默双路径；一个永远失败的公开入口会诱导调用方写不可达分支。
