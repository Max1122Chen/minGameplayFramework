# CORE-F03 内容定义、片段与内容注册表

> 状态：Draft
> 作者：项目作者
> 最后更新：2026-10-26
> 关联契约：C1、C2、C3、C4、C5、C6、C7、C8、C9、C10、C11、C12、C14、C17、C18、C19、C21、C23、C29、C30、C31、C32、C37、C38、C39、C42、C43、C44、C45、C46
> 上游特性：CORE-F01 框架分层与跨块契约（总纲）。下游消费方：CORE-F02（属性与效果）、CORE-F04（背包）、CORE-F05（图模型）、CORE-F06（会话与子系统）

## 1 问题与动机

总纲把「内容定义 = 只读原型」「实例 = 定义引用 + tag 键增量 + 显式覆盖列表」定成了唯一形态（C4、C5），但把两件事留白了：**定义里到底装什么**，以及**「片段」在数据与代码两侧分别长什么样**。这个留白必须在写第一个物品之前补上，否则每加一种内容就会长出一套局部约定，而总纲的失败模式 2（用枚举键做增量索引）与失败模式 10（各 spec 自行发明契约）会同时复发。

参考宿主把这件事摊得更清楚。它的 DataAsset 派生类由 DataAssetLoader 按 AssetMeta::RuntimeClassName 多态实例化，反射属性只有 primitive / object / objectptr / array / delegate 五类，**没有 inline struct**（总纲 §1.1 第 7 行，C9）。这意味着最常见的「键值对表」都不能直接写成字段，必须变成「一个一两个字段的小对象类 + 对象数组」。业务参考实现里，物品定义的反射字段是 Id、MaxCount、OverridesExisting、m_Fragments 四项——一个扁平字段表、一个片段数组、加一个语义含糊的布尔开关。那个布尔开关就是「两套 override 语义打架」的种子：当实例侧既可以改字段又可以改片段集合，而定义侧还有一个「是否覆盖已存在项」的开关时，任何一次读值都无法从数据本身判断它来自哪一层。

第三件事是分片边界。总纲要求注册表按 ContentId 查询、装载期 fail-fast、问题列表一次返回、跨包引用必须声明（C1、C10、C17、C18），但没有定「注册表是对象还是服务」「闭包什么时候算完」「装载顺序为什么无关」。这三条不写清，实现会自然地落到「谁先装载谁赢」——一种看起来能跑、但每次改动资产顺序都可能改变行为的形态。

因此本文档的定位是：**在总纲的分层与契约之内，把「内容定义 + 片段 + 注册表」这三件东西的数据形态、判别方式、装配规则与校验落点定死**，并给后续每种内容种类一条唯一的扩展路径。

## 2 目标与非目标

### 2.1 目标

- **G1 一个能承载多种内容的定义基类。** 物品、方块、效果定义、图定义、任务定义共用同一套身份、片段宿主与只读语义；新增种类只改四处代码，不改基类、不改注册表、不改实例形态。
- **G2 一种不依赖 C++ 类型系统的片段判别方式。** 「按种类查询」只用数据字段与表驱动索引，不用 dynamic_cast、不用 typeid、不用类名字符串比较；这条同时就是可迁移判据。
- **G3 一份消灭「两套 override」的分工规则。** 明确 tag 键增量表与显式覆盖列表各自的地址空间，给出可 grep 的交界判据。
- **G4 一个装载顺序无关的注册表。** 顺序无关性由三条结构性决定保证（闭包先算、容器排序、覆盖直接寻址），而不是靠约定。
- **G5 一张与 CORE-F06 的边界表。** 本文只定容器与校验，不定子系统生命周期。

### 2.2 非目标

- **不做具体游戏内容。** 本文只描述食物 / 药水 / 装备 / 容器四类物品「如何用片段组合表达」，任何实际数值、实际资产、示例包都在 Wave4（总纲 §9）。
- **不做内容热重载。** 内容包在加载闸口一次性装载并冻结；运行期不新增、不替换、不重新注册定义（总纲 §2.2）。
- **不做编辑器面板。** 第一版只保证定义资产的字段可被现有 Inspector 填写与保存（对应总纲 Q11 的 (a)）。
- **不做定义之间的继承与优先级。** 第一版定义是扁平的；引入方式写在 §4.11，形态留在 §11 Q1。
- **不定义实例快照文档本身。** 属性、效果、背包、图的持久化字段归 CORE-F02 / F04 / F05；本文只负责其中的覆盖列表形态与实例内容的三段形态（C11 的一段，见 §4.18）。
- **不定义属性聚合与修饰器结算。** 那是 CORE-F02；本文只规定「片段里的数值字段必须能被表达为 tag 键基值或对象属性」这条约束。
- **不做运行期片段种类注册。** 新增片段种类必然伴随代码变更（C8）。

## 3 术语

只列本文新增的概念；共享概念不在本文重新定义，见总纲 §3 术语表（ContentId、Fragment、Instance、TagKey、Definition、ContentPack、ContentRegistry、fail-fast、加载闸口）。

| 术语 | 定义 |
| --- | --- |
| 片段种类 FragmentKind | 用于判别片段的稳定字符串，形如 Fragment.分类.名字。分类段不使用 Cap（Cap 保留给能力标签，见 §4.7）。身份不来自 C++ 类型层次，来自代码里声明的种类表条目 |
| 种类表 KindTable | 代码侧的唯一权威表：片段种类 → 反射类名、多重性、赋予的能力 tag 集合。装载期用它校验数据，运行期用它建索引 |
| 定义族 DefinitionFamily | 一种内容种类在资产侧的落地：一个反射资产子类 + 一条准入表（必需片段、允许片段）。物品族、方块族、效果族、图定义族、任务族各一份 |
| 准入表 AdmissionTable | 定义族的片段准入规则：必需片段种类集合、允许片段种类集合。前者缺失即 fail-fast，后者之外的种类出现即 fail-fast |
| 装配集合 AssembledSet | 某一份定义（或某个实例）实际拥有的片段集合。由定义数据给出，或由定义数据 + 覆盖列表推导 |
| 覆盖项 OverrideEntry | 实例侧对装配集合的一次结构性改写：片段种类 + 动作 + 参数，动作三选一（替换 / 追加 / 移除） |
| 实例内容 InstanceContent | 实例的内容形态：Definition 引用 + tag 键增量属性表 + 显式覆盖列表。三段且只有三段（C5） |
| 有效片段视图 FragmentView | 定义的装配集合与覆盖列表按种类合并后的只读视图；按种类取（Find / TryGet）与枚举全部（All）。派生值，不写盘 |
| 能力标签集 CapabilityTags | 由装配集合派生的 tag 集合：所有片段声明的能力标签的并集，命名一律落在 Fragment.Cap.*。回答「这个定义能不能被吃 / 装备 / 打开」，不写盘。与 Ability.*（能力运行期，CORE-F07）不是一回事，两者不得混用 |
| 定义基属性表 DefinitionBaseTable | 定义侧的 tag 键基值表，回答「未受任何修饰时属性是多少」。与实例增量表构成「存在性覆盖」关系，不是第二套 override |
| 内容包索引 PackIndex | 一份资产，声明包 id、依赖包集合、它提供的 ContentId 集合、它包含的定义资产清单 |
| 提供集合 ProvidedSet | 包索引里声明的「本包提供哪些 ContentId」。闭包在装载任何定义之前就能算完 |
| 冻结 Seal | 注册表从「可写」进入「只读」的显式步骤。冻结后任何写入都是运行期断言级别的不变量破坏 |

## 4 设计

### 4.1 三层结构一览

   定义资产 (DataAsset, 反射, 双栖)        注册表 (纯对象, 装载期可写)         实例 (运行期可写)
     ContentId{kind,name}                    kind 分片 → name 有序表            ContentId 引用
     定义基属性表 (tag → 基值)        ──►    冻结后只读, 按 id 查询      ◄──      tag 键增量表
     装配集合 (片段对象数组)                 问题列表一次返回                    显式覆盖列表
     能力标签集 (派生, 不写盘)               包所有权映射 (运行期, 不写盘)       能力标签集 (派生, 不写盘)

读写方向只有一条：数据 → 装载 → 注册表 → 实例装配；反方向只有持久化写盘（编辑器保存资产、实例快照落盘）。运行期不存在从实例写回注册表或写回定义的路径（C4、C29）。

### 4.2 定义基类：提供什么、不提供什么

#### 4.2.1 提供

| 提供项 | 形态 | 依据 |
| --- | --- | --- |
| 稳定身份 | 两个数据字段：m_Kind、m_Name，拼成 ContentId。id 不由资产路径或类名推导 | C1 |
| 片段宿主 | 一个对象数组 m_Fragments，元素是片段基类的 Instanced 实例；装载期建立「种类 → 下标」索引 | C9、C5 |
| 定义基属性表 | 一个对象数组 m_BaseAttributes，元素是 MGFAttributeEntry 小对象（tag 名 + 数值）。**细化 C5/C6**：定义侧也有一份 tag 键基值表；它与实例增量表是「存在性覆盖」关系（C14），不是第二套 override | 细化 C5、C6 |
| 能力标签集 | 派生值，装配期算一次：所有片段声明的能力 tag 的并集 | C6、C11 |
| 只读闸 | 一个显式的冻结步骤；冻结后任何写入触发运行期断言 | C4、C17 |
| 版本字段 | m_DefinitionVersion（整型），**只被记录，不被分支**（见 §6.5） | 细化 C12、C15 |
| 作者备注 | 继承自宿主 DataAsset 基类的纯文本字段，无 gameplay 语义 | — |

#### 4.2.2 不提供

- **不提供实例状态。** 定义里没有「当前值」「剩余耐久」「已消耗次数」；这些只在实例上（C4、C5）。
- **不提供业务逻辑。** 定义不知道「被吃会怎样」「被挖会掉什么」。消费方读片段与能力标签集后自己决定；定义上不挂任何虚函数供业务覆写。
- **不提供跨 def 引用解析。** 定义里的引用字段一律是 ContentId 值（C2）；解析归注册表在装载第二段完成（C13），定义对象永远持有未解析的 id。
- **不提供继承与优先级。** 第一版没有「基于某定义」的字段（§4.11）。
- **不提供版本迁移分支。** 唯一会拒绝未知值的版本号是持久化文档的 schemaVersion（C12），由消费方文档类型自己持有；定义资产不引入第二个文档版本号。
- **不提供类型判别辅助。** 定义上不挂「我是不是某种子类」的查询；种类判别在注册表分片上，品类判别在能力标签集上（§4.7）。

### 4.3 定义族与扩展点

「新增一种内容种类」= 下面四处，且只有这四处：

1. **一个反射资产子类**（通常零新增字段，见 K20）。它承载该族在装载期的分派（AssetMeta::RuntimeClassName）与编辑器里的填写形态。
2. **两条表项**：种类表（新增片段种类时）与定义族准入表（kind → 资产类、必需片段集合、允许片段集合）。
3. **内容包索引条目**（数据，非代码）：把新定义资产列进包，并把它的 ContentId 加进提供集合。
4. **消费方业务代码**：读片段、判能力、执行行为。

未来种类的落点：

| 未来种类 | 落地方式 | 特别说明 |
| --- | --- | --- |
| ItemDef | 物品定义族；准入表允许「可食用 / 可使用 / 可装备 / 可打开 / 堆叠 / 几何占位」等片段 | §6 的四个示例 |
| BlockDef | 方块定义族；准入表允许「可挖掘 / 掉落 / 方块视觉」等片段 | 与物品共享片段种类是允许的（掉落片段两者可用） |
| 效果定义 | 效果定义族（kind = effect）：字段由 CORE-F02 拥有（EffectDef），本文只登记「效果」这个 kind 名，并把该族的片段准入表置空（必需集合与允许集合都是空集） | 效果定义**不用片段装配修饰器**：把修饰器列表放进片段会把 F02 的类型拖进本文。本文除 F02 自身拥有的效果定义字段外不引用 F02 类型 |
| 图定义族 | 图定义族（kind = graph）：图文档本身作为一种内容种类登记到注册表，准入表与业务分派由 CORE-F05 给出 | **payload 不是独立资产、也不是 ContentId 引用**：它只是节点里的内联对象，由 CORE-F05 登记与校验。本文只提供「图定义族」这一份族的机制，不设 payload 族 |
| 任务定义 | 任务定义族；准入表允许「目标 / 奖励 / 前置」等片段 | 前置引用是 ContentId，允许目标未装载（C2） |

### 4.4 片段：身份是种类串，不是类型

片段基类只承担三件事：一个种类字段、一个作者备注、被反射实例化的能力。

示意，不是最终签名：

    namespace mgf
    {
        /// @brief Discriminant of a fragment, taken from the code-side kind table.
        class FragmentKind
        {
        public:
            /// @brief Stable string form, unique among all declared kinds.
            const std::string& ToString() const;

        private:
            std::string m_Name;
        };

        /// @brief Base of every fragment. Holds identity; carries no behaviour.
        class FragmentBase
        {
        public:
            /// @brief Kind assigned by the loader from the kind table, never typed by hand in code.
            const FragmentKind& GetKind() const { return m_Kind; }

            /// @brief Authoring note; carries no gameplay meaning.
            const std::string& GetNotes() const { return m_Notes; }

        private:
            FragmentKind m_Kind;
            std::string m_Notes;
        };
    }

三条设计决定，逐条给理由：

1. **种类是数据字段，不是「靠类名推断」。** 若种类由反射类名推导，那么「数据说自己是什么」和「对象实际是什么」就成了两处真值，而内容作者改一处、代码改另一处时无法发现。改为：种类写在数据里，代码侧种类表给出「这个种类的反射类名应当是什么」，装载期比对两者，不一致即一条问题项。真值只有一处：**种类表**。数据与类名都是对它的引用，任何一方偏离都会在装载期暴露（K3）。
2. **基类不新增判别性虚函数。** 基类本身作为 MEObject 派生已带虚表，但判别不走它：GetKind 是非虚的数据访问，任何持有基类指针的代码都能取到种类，不需要向下转型（K4）。
3. **片段基类不定义 Update / OnEquip 这类钩子。** 一旦有钩子，片段的「种类」就开始承担行为分派，等价于把类型层次搬回来。行为归消费方：它拿到片段、读出参数、自己执行。

### 4.5 片段：多重性、必需与准入

#### 4.5.1 多重性按种类声明

每个片段种类的种类表条目里有一个多重性：单例（默认）或多例。

| 多重性 | 同一宿主上重复出现 | 能被覆盖列表寻址 |
| --- | --- | --- |
| 单例（默认） | 装载期 fail-fast，报出种类名与两处定位 | 能 |
| 多例（须显式声明） | 合法，按装配顺序保留 | **不能** |

#### 4.5.2 重复单例的策略判断

三个候选：静默去重 / 后者覆盖 / 报错。选择**报错（fail-fast）**，理由三条：

- 静默去重把「复制粘贴同一个片段并改了参数」这种最常见的手误变成沉默：作者以为改的是生效值，实际上生效的是先出现或后出现的那份。
- 后者覆盖让「资产数组顺序」成为语义。顺序会被编辑器重排、被资产合并冲突打乱，于是同一份数据在不同机器上行为不同——直接违反 §4.14 的装载顺序无关承诺。
- 有序多例 + 下标身份是第四个候选（总纲 Q2 已否决索引覆盖），同理会腐烂。

多例片段只用于「同一宿主上若干同类条目，彼此无主次」的情形（例如一份掉落表里的多条掉落项），且它们不参与覆盖列表（见下条理由）。

#### 4.5.3 为什么多例片段不能被覆盖列表寻址

覆盖项的键是片段种类。多例种类在同一装配集合里可能有若干成员，键无法唯一定位其中一个。若为此引入「种类 + 下标」键，就回到总纲 Q2 已否决的索引覆盖（插入新成员后全错）。因此规则是：**一个覆盖项只能指向单例种类**；需要「替换多例集合里的某一项」时，正确做法是把那一项提升为独立的单例种类，或把该集合表达为 tag 键属性。

#### 4.5.4 必需与准入

每个定义族在准入表里声明两个集合：

- **必需集合**：该族任何定义都必须具备的片段种类。缺失即 fail-fast。
- **允许集合**：该族定义可以出现的片段种类全集。出现集合外的种类即 fail-fast。

允许集合是防「片段乱组合」的唯一低成本手段：没有它，一个物品定义可以挂上方块的挖掘片段，装载成功、运行期才在消费方炸掉，而炸点离根因很远。代价是每次新增一个跨族共享的片段种类都要改准入表——这是代码变更，符合 C8 的意图。

### 4.6 片段：查询接口（不依赖 RTTI）

片段容器 = 有序数组（装配顺序）+ 装载期建好的「种类 → 下标」索引。四个查询：

示意，不是最终签名：

    namespace mgf
    {
        /// @brief Read-only view over one assembled fragment set.
        class FragmentSet
        {
        public:
            /// @brief Returns the single fragment of this kind, or nullptr when absent.
            const FragmentBase* Find(const FragmentKind& kind) const;

            /// @brief Returns every fragment of a repeatable kind, in assembly order.
            std::vector<const FragmentBase*> FindAll(const FragmentKind& kind) const;

            /// @brief Returns all fragments in assembly order.
            const std::vector<const FragmentBase*>& All() const;

            /// @brief True when any fragment of this set grants the capability tag.
            bool HasCapability(const TagName& capability) const;

            /// @brief Table-driven typed view; checks the kind string before the cast.
            /// @warning The caller passes a kind from the code-side table, never a literal.
            template <typename TFragment>
            const TFragment* As(const FragmentKind& kind) const;
        };
    }

- **Find / FindAll**：字符串键查表，无 RTTI。跨语言等价物是「数组 + 字符串键映射」，任何语言都有。
- **All**：装配顺序遍历。顺序只在「同一多例种类的成员之间」有意义，不构成跨种类的语义（§4.14）。
- **HasCapability**：能力查询的正解，见 §4.7。
- **As**：唯一的类型化入口。它先比种类串，再 static_cast；且只在**拥有该种类业务语义的代码**里允许调用（K4 的 grep 判据把范围限定在查询层实现）。这不是 dynamic_cast：判别依据是数据，转型只是同一种类内的类型还原，跨语言时它退化成「按种类分派的一次函数调用」。

反例警戒：不要提供 As 的无种类重载（靠类名或 RTTI 猜具体类型），那是把类型系统重新变成判别依据。

### 4.7 能力标签集：用 tag 表达「能否做某事」

「查这个定义能不能被吃」有三种实现，逐一判断：

| 方案 | 判断 |
| --- | --- |
| C++ 接口（如 IEatable）+ 向下转型 | 不采用。查询退化成 RTTI 或虚表偏移；跨语言没有对应物；而且「能否吃」是内容语义，不是内存布局语义 |
| 按片段种类硬编码判断（Has(可食用)） | 部分采用但不够。判定点散落在消费方，新增「能吃」的表达方式就要改所有判定点 |
| 能力 tag 集合（本设计） | 采用。片段种类在种类表里声明它赋予哪些能力 tag；定义的能力标签集 = 并集，装配期算一次，是派生值 |

命名落点：能力 tag 一律挂在片段领域段下的 Cap 分类里，形如 Fragment.Cap.Equippable、Fragment.Cap.Edible；**不新增总纲 C38 的领域段**，理由是不动既有词汇表分区、且能力本来就由片段赋予。

与 Ability.* 的分界要写死：**Ability.* 段专指能力运行期（CORE-F07 的 Ability.Gate.*、Ability.State.*），Fragment.Cap.* 专指「某片段授予的能力标签」。** 两者是不同概念——前者是运行期状态与门控的 tag，后者是内容侧的静态标签——不得互相顶替。因此本文的 tag 举例一律用 Fragment.Cap.* 形态，不用 Ability.* 形态；反过来说，F07 文档里出现 Ability.* 也不等于能力标签集。

能力标签集是派生值：不写进定义资产、不写进实例快照（C6、C11）。它唯一的来源是装配集合，因此「覆盖列表改了装配集合 → 能力标签集随之改变」是自动的，不需要额外同步——这正是把能力做成派生而非字段的收益。

### 4.8 为什么是组合，而不是继承（中毒的剑 = 毒定义派生物品定义）

具体落点用一个常见需求说明：「中毒的剑」与「普通的剑」并列存在，且之后还要出现「中毒的药水」「着火的食物」。

若用继承表达（毒物品定义继承物品定义、毒药水定义继承药水定义）：

1. **组合爆炸。** 物品 × 毒 × 药水 × 着火 × 附魔 = 类数量相乘，且每个类都要过一遍 header-tool 生成反射代码、重建二进制。这直接违反 C7：数值与装配关系的改动不得要求重新编译。
2. **语义分裂。** 一份「中毒」行为被写在毒物品定义里，就无法作用于已经定义的药水；想复用只能再写一个毒药水定义，两处实现逐渐分叉。
3. **判别点变多。** 消费方开始出现「这是不是毒」「是不是药水」的类型判断，判别依据从数据漂回类型层次；这与 K4 的可迁移判据直接冲突。
4. **实例无法重定向。** 一个普通剑的实例无法在运行中「变成中毒的」，因为它指向的定义 id 没变；改 id 就等于换了一份定义，破坏「实例 = 定义引用 + 增量」的稳定形态（C5）。
5. **持久化被类型绑架。** 存档要能表达「这是中毒的剑」，就得写具体 C++ 类名或一份子类路径；C11 要求只存 ContentId + 增量，两者不兼容。
6. **作者被迫重写。** 给现有 30 把剑加毒，继承方案要求每把剑都换成新类；组合方案只是多挂一个片段。

规则一句话：**当两条定义的区别是「内容作者会不断叠加组合的特征」时，它是片段；当区别是「注册表分片、资产类型、装载准入集合都不同」时，它才配拥有独立的定义族。** 前者对应 C8 的「片段种类是代码词汇表」，后者对应 §4.3 的四处扩展点。

### 4.9 覆盖列表：形态与合并语义

覆盖列表是实例状态的第三段（C5），采纳总纲 Q2 的建议：覆盖项 = 片段种类 + 动作 + 参数。

示意，不是最终签名：

    namespace mgf
    {
        /// @brief One structural rewrite of an instance's assembled fragment set.
        class OverrideEntry
        {
        public:
            /// @brief Fragment kind this entry addresses; unique within one override list.
            const FragmentKind& GetKind() const;

            /// @brief Replace, append or remove.
            EOverrideAction GetAction() const;

            /// @brief Full fragment object for replace and append; absent for remove.
            const FragmentBase* GetParams() const;

        private:
            FragmentKind m_Kind;
            EOverrideAction m_Action;
            const FragmentBase* m_Params;
        };
    }

#### 4.9.1 语义表

| 动作 | 参数 | 前置条件 | 结果 |
| --- | --- | --- | --- |
| 替换 | 该种类的完整片段对象 | 定义上已有该种类（单例） | 装配集合里该种类的成员被整个换掉 |
| 追加 | 该种类的完整片段对象 | 定义上没有该种类（单例） | 装配集合多一个成员 |
| 移除 | 无 | 定义上已有该种类（单例） | 装配集合少一个成员 |

三条前置条件不满足都是加载期 fail-fast（K11）：追加一个已存在的种类，说明作者想表达替换却写错动作；替换或移除一个不存在的种类，说明定义被改过而实例快照没跟上。这两种错都必须报出来，而不是容忍。

#### 4.9.2 关键判断：替换是整片段替换，不做字段级合并

理由与「两套 override 打架」的直接对治：

- 反射序列化不提供「作者是否显式写过这个字段」的元信息。一旦允许字段级合并，「未赋值」与「赋了默认值」就不可区分，只能拿哨兵值近似——C14 已经禁止用哨兵表达省略。
- 于是字段级合并必然导致「合并后这个字段到底取定义值还是默认值」需要靠约定猜，这正是两套 override 语义打架的来源。
- 定成整片段替换后，**参数的每个字段在数据里都有一个确定值**（未填即该种类的类型默认值），不存在继承链（K8 的可检验项要求用例把这个行为写死）。

代价：想只改一个字段，就得把整份片段对象填全。这个代价由下一条抵消：**需要字段级精度的量，不允许建模成片段字段，必须建模成 tag 键属性。**

#### 4.9.3 序列化与唯一性

- 覆盖列表 = 「以片段种类为键的映射」，一个种类至多一条（K8）。序列化为按种类字典序排序的数组，保证 C11 的往返字节等价。
- 空列表 = 完全继承定义的装配集合。
- 不存在「应用顺序」语义：三个动作都按种类直接寻址，互不链式依赖（K8 的可检验项：打乱条目顺序，装配结果不变）。

### 4.10 覆盖列表与 tag 增量表的分工（消灭两套 override）

#### 4.10.1 地址空间不相交

| 想改的东西 | 落在哪 | 键 | 精度 | 持久化形态 |
| --- | --- | --- | --- | --- |
| 数值、开关、属性基值 | tag 键增量表 | tag 名 | 单个值 | 有序条目数组（C11、C14） |
| 装配结构：有没有某个片段、换成哪一个 | 显式覆盖列表 | 片段种类 | 整片段 | 按种类排序的条目数组 |

判定一句话：**如果这条状态能被某个片段的某个字段表达，它必须建模成 tag 键属性，走增量表；如果它回答的是「这个实例具备哪些片段」，它走覆盖列表。** 两者都不允许表达对方的对象（K9 用两条判据把它钉住：增量表的键不得是片段种类，覆盖列表的键不得是 tag 名）。

#### 4.10.2 与定义基属性表的关系（不是第三套 override）

实例增量表与定义基属性表的关系是**存在性覆盖**：某个 tag 键在增量表里有条目，就用条目值；没有条目，就用定义基属性表的值；两处都没有，就是「未定义」，消费方按自己的默认策略处理，且这个默认值不属于内容数据（C14 已规定条目存在性表达覆盖，不写哨兵）。

这不是 override 语义的第二份实现，而是同一条规则（存在性覆盖）的两个作用对象：增量表之于定义基属性表，覆盖列表之于定义的装配集合。两处都只有一条规则，与那种「字段表 + 开关 + 片段数组」三处并存的形态正好相反。

#### 4.10.3 装配只在加载闸口发生

覆盖列表的写入只有一个入口，且该入口带加载期上下文；运行期不存在「给实例加一个片段」的公开路径（K10）。运行期的行为差异靠 tag 键增量 + 效果表达（CORE-F02）。理由：

- 改装配集合会改变能力标签集，而能力标签集是派生值，运行期改动就要重新派生并触发一次全局重算——属于 C23 禁止在 tick 里做的重活。
- 「实例在运行中获得了新片段」意味着快照里的覆盖列表会被运行期逻辑写入，单点写入（C29）与去抖（C28）都要重新设计。第一版不做（YAGNI）。

### 4.11 定义之间的继承：第一版不做

Lyra 式的 Definition/Fragment/Instance 没有定义「同种类优先级」——当两份定义都能提供同一种片段时谁胜。本设计不靠隐式规则填补这个空白，理由：任何「先声明者胜」「子类胜」「显式程度高者胜」的规则，都要求读者记住一条不在数据里的优先级，并在多层组合时产生无法预测的合并结果。这与本设计「数据自解释」的方向相反。

第一版的规则：**定义是扁平的。** 复用有两态：

- 数值复用：在多个定义里重复声明同一条 tag 键基值（数据侧，有 C1 的稳定 id 兜底，重复成本低）。
- 结构复用：作者复制片段对象（编辑期操作），装载后是两份独立数据。

若将来必须做定义继承，唯一可接受的形态是**复用现有覆盖项词汇**：把「种类 + 动作 + 参数」列表用在定义上，装载期产出「有效装配集合」，再交给同一套实例装配路径。这样新增的只是「覆盖列表的一个作用对象」，不是第二套 override 语义。形态选择留在 §11 Q1。

### 4.12 注册表：分片、查询、遍历

#### 4.12.1 形态

示意，不是最终签名：

    namespace mgf
    {
        /// @brief Read-only index of every loaded definition, sharded by kind.
        class ContentRegistry
        {
        public:
            /// @brief Returns the definition with this id, or nullptr when absent.
            const ContentDef* Find(const ContentId& id) const;

            /// @brief Returns every definition of one kind, in name order.
            std::vector<const ContentDef*> FindByKind(const ContentKind& kind) const;

            /// @brief Returns every definition, ordered by kind then by name.
            std::vector<const ContentDef*> All() const;

            /// @brief Returns how many definitions a shard holds, zero when the shard is empty.
            std::size_t CountInKind(const ContentKind& kind) const;
        };
    }

- **按 kind 分片**，片内按 name 字典序存放。查询不跨分片：物品分片查不到时返回未找到，不回退到别的分片去找同名定义（K12）。
- **遍历顺序确定**：分片按 kind 顺序、片内按 name 顺序。这个顺序不是为了语义，而是为了「两次装载的摘要可比」与「测试可断言」——§4.14 与 §10 的验收都依赖它。
- **只读句柄**：查询返回 const 指针。C3 要求句柄不进实例状态，因此实例存 ContentId，需要时再查；快照往返后必须重新解析（C13）。
- **未找到不是错误**：查询返回空指针是正常结果；只有「一份数据里的引用解析不到」才是问题项（C18 的定位要给出引用方与被引用 id）。

#### 4.12.2 注册入口

只有一个，带装载上下文（包 id）。它做四件事：校验 id 字符与重复、校验片段种类与准入、写入分片、记录「id → 包 id」的所有权映射（运行期用，不写盘）。任何绕过它的写入路径都读不到，因为分片容器不对包外暴露（K13 的编译期判据）。

### 4.13 注册表：装载闭包与跨包引用

C10 要求「包内引用必须闭包可解析，跨包引用必须在依赖声明里列出」。落地成五步，顺序不可交换：

1. **读索引。** 包索引声明：包 id、最小词汇表版本（C42）、依赖包集合、提供集合、定义资产清单。
2. **算闭包。** 只看索引，不装载任何定义。缺包、依赖成环、两个包声明同一个 id、同一 id 被声明两次 → 各自一条问题项。这一步把「重复 id」这类冲突从「谁先装载谁赢」变成「装载前的静态判定」，是 §4.14 的基础。
3. **逐包装载定义资产。** 引擎侧完成反序列化与内部对象引用解析；**在引用解析完成之前不做任何片段校验**（K18），否则会把「悬空引用」误报成「未知片段种类」。
4. **注册。** 走到 §4.12.2 的入口，逐份定义校验并写入。
5. **交叉核对与汇总。** 索引声明的提供集合必须等于实际注册集合，偏差各报一条问题项（防止索引漂移）；全部问题一次返回（C18）；问题列表非空则闸口不开放（fail-fast）。

提供集合声明的代价是「索引与实际可能不一致」，交叉核对就是它的对治；不声明的代价是闭包只能靠装载后探测，跨包引用缺包时无法在装载前给出「你缺哪个包」的可读诊断。取舍留在 §11 Q6。

### 4.14 装载顺序无关性从哪来

不是靠约定，靠三条结构性决定：

1. **冲突在装载前发现。** 重复 id、缺包、环依赖都在第 2 步（只读索引）判定，此时还没有任何注册发生，因此不存在「先来后到」。
2. **容器按名字排序。** 分片内按 name 存放，All 按 kind 再按 name，因此遍历顺序与装载顺序无关。
3. **覆盖按种类直接寻址。** 覆盖项之间没有链式依赖，装配结果不依赖条目的处理次序。

反例警戒：不要引入「先注册者胜」或「后注册者覆盖」来消化重复 id。这两种做法都会把装载顺序变成语义，而且第二次装载同一份内容会得到不同的注册表。

### 4.15 注册表是子系统还是纯对象（与 CORE-F06 的边界）

判断：**容器本身是纯对象，宿主是 GameInstance 子系统。**

- 纯对象：ContentRegistry 没有单例、没有静态可变成员、不自我注册、不依赖引擎类型。这样它可被单元测试直接构造，也满足 C46（核心层不反向调用适配层）。
- 宿主是子系统：C30 要求全局服务一律是子系统；满足它的方式不是把容器做成子系统，而是让一个 GameInstance 子系统持有恰好一份容器并对外只暴露只读视图。C31 的真值归属表要求「内容定义与注册表」由 GameInstance 子系统持有，与此一致。

边界表：

| 关注点 | 归属 |
| --- | --- |
| 定义 / 片段 / 装配 / 覆盖 / 查询的数据形态与校验规则 | 本文（CORE-F03） |
| 注册表放进哪个子系统、初始化与关闭顺序、跨子系统惰性获取（C33） | CORE-F06 |
| 加载闸口的开合时机与「禁止在 tick 内装载」的落实（C23） | CORE-F01 契约 + CORE-F06 实现 |
| 问题列表的对外呈现（日志、编辑器、宿主摘要） | CORE-F06 的装载器 |
| 内容包索引的资产读取与 AssetTypeId 分派 | 适配层（本文定字段，CORE-F06 定装载流程） |

两个方向需要对方提供的接口（写清以便并行实现）：

- 本文需要 CORE-F06 提供：const 引用取得注册表的入口（惰性获取语义）、IsInLoadGate()（当前是否在加载闸口内，供 K10 与 §4.16 的断言使用）、装载器把问题列表转成宿主可见输出。
- CORE-F06 需要本文提供：唯一注册入口、冻结步骤、只读查询视图、问题项结构（C18 的定位字段，见 §7.3）。

### 4.16 生命周期与时序

    构造(空) ──装载中(可写)──► 冻结(只读) ──会话结束──► 销毁
                    │                            ▲
                    └── 问题列表非空 ── 闸口不开放 ┘（不进入冻结态，直接失败）

- **装载中**：唯一允许写入的窗口；此时可以注册、可以建种类索引；查询要能容忍半成品（供装载期自检用），但不对外暴露。
- **冻结**：显式一步，之后任何写入触发运行期断言（C17 二级）。冻结也把「种类 → 下标」索引与能力标签集作最终计算。
- **销毁**：随 GameInstance 子系统关闭（C34：关闭期不回调、不再取其他子系统）。实例侧只持有 ContentId，因此注册表先销毁也不会留下悬垂引用。

### 4.17 边界情况清单

| 情形 | 行为 |
| --- | --- |
| 空内容包 / 注册表一个定义都没有 | 允许启动（C17 允许降级一栏的既有例子），记一条警告 |
| 同一个定义资产被两个包索引列为自己的定义 | 闭包期一条问题项，指出两个包 id |
| 一个包声明的提供集合里有一个 id 它实际没提供 | 交叉核对报一条问题项 |
| 定义没有片段 | 合法（除非该族必需集合非空）；能力标签集为空 |
| 片段数组里同一单例种类出现两次 | fail-fast，报种类名与两处下标 |
| 覆盖列表指向定义上不存在的单例种类 | fail-fast（K11） |
| 覆盖列表里出现多例种类 | fail-fast（寻址不唯一，§4.5.3） |
| tag 增量表的键是片段种类 | fail-fast（K9） |
| 定义引用的 ContentId 未装载 | 装载第二段报问题项，列出全部缺失 id（C13） |
| 片段对象引用悬空（资产内部对象指针未解析） | 报「引用解析失败」，不报「未知片段种类」（K18） |
| 依赖成环 | 闭包期一条问题项，给出环路径 |
| 两个 id 仅大小写不同 | 见 §11 Q7（第一版按 C1 视为两个 id，是否收紧待作者定） |

### 4.18 实例与有效片段视图（本文提供，F04 / F05 / F07 只使用）

C5 把实例定成三段，但「实例类由谁拥有」与「定义装配结果和覆盖列表在哪里合并」在几份文档之间一度无人落笔。裁定：**这两件事都由本文提供**——覆盖合并规则本身就是内容定义族的知识（哪一段来自定义、哪一段被实例改写，只有定义族说得清），放在使用方会让 F04 / F05 / F07 各写一份合并实现。

- **实例类的内容形态严格是 C5 的三段，且只有三段**：Definition 引用（按 ContentId，保持未解析的 id 值）、tag 键的增量属性表（键是 tag 名）、显式 fragment 覆盖列表（按片段种类唯一）。**不得有第四段私有字段**，尤其不得为「好实现」加片段缓存、当前值快照、槽位数组。理由：一旦有第四段，C5 的「需要新状态时新增一个片段或一条 tag 键」立刻失效，各块会在实例上重新开洞。
- **有效片段视图**：把定义的装配集合与覆盖列表按种类合并后得到的只读视图，能按片段种类取单例（Find / TryGet）与枚举全部（All）。合并语义与 K8、K9 逐字一致——整片段替换（未填字段取类型默认值，不继承定义值）、地址空间与 tag 增量表不相交。视图是派生值，不写盘（§6.4 的「有效装配集合」一行就是它）。
- **实例类明确不持有**：属性 current 与修饰器集合（CORE-F02）、容器槽位与堆叠状态（CORE-F04）、图节点与遍历状态（CORE-F05）。这三样回答的都不是「这个实例持有哪几个片段」，因此不进本文的实例形态。

示意，不是最终签名：

    namespace mgf
    {
        /// @brief The three-part instance content fixed by the framework contract.
        /// @warning Never add a fourth part; new state is a fragment or a tag key.
        class InstanceContent
        {
        public:
            /// @brief Definition reference, kept as an unresolved id.
            const ContentId& GetDefinitionId() const;

            /// @brief Tag-keyed delta table; keys are tag names, never fragment kinds.
            const AttributeDeltaTable& GetDelta() const;

            /// @brief Structural rewrites; at most one entry per fragment kind.
            const std::vector<OverrideEntry>& GetOverrides() const;

            /// @brief Effective fragments: the definition set with overrides applied.

对外提供面因此变大一格：F04、F05、F07 不再各自写「定义片段 + 覆盖」的合并代码，也不再各自定义实例形态；它们在自己的文档与子系统里持有 F02 / F04 / F05 各自的状态，并通过本节的视图回答「这个实例现在有哪些片段」。

## 5 契约

体例：规则 + 可检验 + 细化的 C 编号。可检验项要么是一条用例（doctest 用例名语义化，不含编号），要么是一条可执行的 grep / 结构检查。

### 5.1 身份与定义形态

**K1 定义的身份只来自数据字段，不由资产路径、类名或文件名推导。** 细化 C1。
可检验：把一份定义资产改名并移动到另一个目录后装载，仅凭 ContentId 仍能查到同一份定义（用例）；kind 为空、name 为空、name 含字母数字与点线横线之外字符，三种情形各返回一条带定位的问题项（三条用例）。

**K2 定义族的反射属性只允许 primitive / object / objectptr / object 数组四类，禁止任何 struct 类别属性。** 细化 C9。
可检验：在定义族头文件上检查属性宏行的类型，不得是 struct 声明类型（脚本检查，结果为空）；header-tool 生成的定义族生成代码里 struct 类别属性计数为零。

**K3 片段身份是种类串，真值来自代码侧种类表；数据里的种类串与对象的反射类名不一致时 fail-fast。** 细化 C8、C44。
可检验：装载一份数据里写的种类是食物、但对象实际是药水片段的定义，返回一条指出「期望类名 / 实际类名 / 种类」的问题项（用例）；写一个种类表里没有的种类串，返回一条「未知片段种类」问题项（用例）。

**K4 片段查询路径不出现 RTTI。** 查询层的实现里不得出现 dynamic_cast、typeid、以及靠类名比较实现的判别。类型化访问只允许在拥有该种类业务语义的代码里，且必须先比对种类串再 static_cast。细化总纲 §4.3 可迁移判据。
可检验：对核心层与适配层的片段查询实现文件执行 grep（模式为 dynamic_cast 与 typeid），结果为空；一条用例只持有片段基类指针与种类串，取回参数并断言数值（证明判别不依赖具体派生类型）。

**K5 片段多重性按种类在代码表里声明，默认单例；单例种类的重复出现是 fail-fast。** 细化 C8、C17。
可检验：同一宿主上出现两次单例片段，装载失败并给出种类名与两处定位（用例）；多例种类出现两次合法且按种类取全部返回两条（用例）。

**K6 每个定义族声明必需片段集合与允许片段集合；缺必需、出现不允许的种类都是 fail-fast。** 细化 C17。
可检验：删掉某族的必需片段后装载失败并指出缺失种类（用例）；给物品族挂一个只属于方块族的片段，装载失败并指出该种类不在准入集合内（用例）。

**K7 空片段是合法语义：存在性即语义，不得用哨兵默认值表达「未设置」。** 细化 C14。
可检验：一份只有种类、其余字段全取默认值的片段，经保存装载后仍存在且条目数不变（用例）；片段源码里不存在语义为「未设置」的数值常量（审查项：需要可空语义的字段必须是可空对象引用，不是数值哨兵）。

### 5.2 覆盖与分工

**K8 覆盖项 = 片段种类 + 动作 + 参数；动作三选一；每个种类在列表中至多出现一次；替换与追加携带整份同种类片段对象，不做字段级合并。** 细化 C5，采纳总纲 Q2 的建议。
可检验：同一份实例快照里同一片段种类出现两条，装配被拒绝并报问题项（用例）；一条只填一个字段的替换项生效后，该片段其余字段取类型默认值而不是定义值（用例，用例名写明这个行为）；打乱覆盖项数组顺序，装配结果逐字段相同（用例）。

**K9 覆盖列表与 tag 增量表的地址空间不相交。** 覆盖列表的键只能是片段种类；tag 增量表的键只能是 tag 名。细化 C5、C11。
可检验：在 tag 增量表里写一个片段种类作键，装载失败（用例）；在覆盖列表里写一个 tag 名作键，装载失败（用例）；审查项——两处键在代码里不是同一个类型（编译期保证：覆盖项的键是片段种类，增量表的键是 tag 名）。

**K10 覆盖列表只在加载闸口内装配，运行期不存在修改装配集合的公开路径。** 细化 C23、C5。
可检验：tick 深度大于零时调用装配入口触发运行期断言（用例）；装配写入口在整个仓里只有一个调用点族（审查项 + 该入口签名带加载期上下文参数）。

**K11 覆盖动作的目标必须存在且状态匹配，否则 fail-fast。** 追加已存在的种类、替换或移除不存在的种类、覆盖多例种类，四种情形各一条问题项。细化 C17、C18。
可检验：四条用例各自返回一条带种类名与动作名的问题项。

### 5.3 注册表

**K12 注册表按 kind 分片，查询不跨分片回退。** 细化 C1、C2。
可检验：查询物品分片里不存在的名字返回未找到，不回退命中同名方块（用例）；同名不同 kind 的两份定义同时存在且各自可查（用例）。

**K13 注册表是纯对象：无单例、无静态可变成员、不自我注册；宿主是 GameInstance 子系统。** 细化 C4、C30、C32。
可检验：注册表类型里没有静态可变成员（grep 结果为空）；两个 GameInstance 并存时各自注册表条目数独立（用例）；注册表自身源码不 include 子系统或引擎头文件（grep 结果为空）。

**K14 装载结果与包的装载顺序、资产遍历顺序无关。** 细化 C10。
可检验：把同一闭包内的包按十种顺序装载，注册表摘要（按 kind、name 排序的定义列表 + 按种类与定位排序后的问题项列表）逐字节相同（用例）。

**K15 包索引声明提供集合与依赖集合，闭包在装载任何定义之前算完；索引声明与实际注册集合必须一致。** 引用 C10（其 R2 修订已把「索引声明提供集合与依赖集合、装载后交叉核对」写进正文）；本文只给 §4.13 的落地五步，不重复扩写。
可检验：制造跨包引用但不在依赖声明里，装载失败并指出缺失包名（用例）；声明了但未提供的 id、提供了但未声明的 id 各报一条问题项（两条用例）；两个包声明同一个 id，在闭包期即失败，且与装载顺序无关（用例）。

**K16 定义只读：装配与覆盖应用不写回定义。** 细化 C4、C29。
可检验：创建实例、施加覆盖、施加效果后，定义逐字段与装载时快照一致（用例）；定义查询接口只返回 const 指针（编译期：不存在非 const 重载）。

**K17 能力标签集是派生值，不写盘。** 细化 C6、C11。
可检验：给定定义查询能力 tag 得到预期真值，覆盖列表改变后能力标签集随之改变（用例）；定义资产与实例快照的字段表里都没有能力标签集字段（结构检查）；往返后重算的能力标签集相等（用例）。

**K18 定义资产装载分两段，片段对象引用解析完成前不做片段校验。** 引用 C13（其 R2 修订已把「本条同时约束资产装载路径」写进正文），本文只给落地顺序，不重复扩写。
可检验：构造一份片段对象引用悬空的定义，装载返回「引用解析失败」问题项，且不出现「未知片段种类」误报（用例）。

**K19 定义资产里的版本字段只被记录、不被分支。** 细化 C12、C15。
可检验：把版本字段改成任意值，装载结果与问题列表不变（用例）；该字段的读取点只有问题消息构造处（审查项的 grep 结果只命中一处）。

**K20 定义族资产子类默认零新增业务字段；新增字段必须在本文对应族的小节里写明「为什么不能表达为片段」。** 细化 C7、C8。

**K21 实例类的内容形态严格是 C5 的三段，不得出现第四段私有字段。** 细化 C5。

### 6.1 一份定义资产的字段清单

以物品族为例。资产类继承定义基类，**零新增字段**（K20）。

| 字段 | 类型 | 反射类别 | 写盘 | 说明 |
| --- | --- | --- | --- | --- |
| m_Kind | 字符串 | primitive | 是 | 定义所属分片，例如物品 |
| m_Name | 字符串 | primitive | 是 | 定义名，片内唯一 |
| m_DefinitionVersion | 整型 | primitive | 是 | 只记录不分支（K19） |
| m_BaseAttributes | MGFAttributeEntry 对象数组 | object 数组 | 是 | tag 键基值。因 C9 不能写成 struct，条目必须是小对象类 |
| m_Fragments | 片段基类对象数组 | object 数组 | 是 | 装配集合；顺序对单例种类无语义，对多例种类是成员顺序 |

MGFAttributeEntry 字段：m_Tag（字符串，tag 全名）、m_Value（浮点）。它存在的唯一理由是 C9：一对键值不能写成 struct，只能写成对象。

**引用编码只有一种：MGFContentIdRef。** 凡数据里保存「指向另一份内容的引用」的字段，一律用这个编码；F04、F05、F07 的引用字段必须引用它，不得各自定义第二种。

| 字段 | 类型 | 反射类别 | 写盘 | 说明 |
| --- | --- | --- | --- | --- |
| m_Kind | 字符串 | primitive | 是 | 被引用定义所属分片，例如物品 |
| m_Name | 字符串 | primitive | 是 | 被引用定义名，片内唯一 |

两个 primitive 字段，没有第三个：不许用嵌套对象承载（C9 下它会变成又一个对象类，且没有任何额外信息），也不许在字段里做字符串解析。

**为什么不用单个字符串。** 那会把两处真值问题一起引入：(a) 「kind 与 name」本来是两个独立字段、两套字符集校验与两条可分别定位的问题项；压成一个字符串后必须先切分才能校验，于是格式约定成了第二份真值，非法写法只能等到解析时才暴露，而问题项也无法指出「是哪一段非法」。(b) 同一条 id 在数据里会同时存在「拼好的字符串」与「结构化字段」两种形态，哪个是权威没有答案——K1 要求身份只来自数据字段，单字符串形态把这条要求绕回去了。反过来看，两个字段的代价只是「读的时候要取两次」，而它换来的是装载期可分别校验、可分别定位、可 grep。

### 6.5 DataAsset 双栖的往返等价

「双栖」在本设计里的意思是：**定义资产既是运行期内容的载体，也是它唯一的持久化形式**，不引入第二套磁盘格式。

- 装载：资产 → 反射反序列化 → 对象图（含 Instanced 片段对象）→ 引擎解析内部对象引用 → 本文的两段校验。
- 保存：编辑器把填写好的对象图经反射序列化写回资产，字段集合与装载时相同。
- 往返等价判据：**装载 → 序列化 → 反序列化 → 再装载**，注册表摘要（§4.14 定义的排序摘要）逐字节相同。派生项（§6.4）不参与比较，因为它们不写盘，也就无法通过这条判据被间接写盘。

等价的三个前提：

1. **确定顺序。** 分片按 name、覆盖项按种类、问题项按种类与定位排序输出；否则「摘要相同」在字节层面不成立。
2. **条目存在性优于默认值。** 空字符串、零值条目都要原样写出，不能省略（C14 的推广：省略只允许发生在「字段整体不存在」，例如移除动作没有参数对象）。
3. **不写派生。** 任何 §6.4 的项一旦进字段表，往返就不再等价（第一次装载算出的派生值会被当成输入读回）。

| 加载期 fail-fast | id 非法或重复、种类未注册、种类与类名不符、准入集合违规、重复单例片段、引用解析失败、覆盖项非法、跨包引用未声明、索引漂移、未知 tag、词汇表版本不足、未知 schemaVersion | 汇总**完整**问题列表一次返回，闸口不开放，不进入冻结态（C17、C18） |

| 允许的降级 | 可选片段缺失实现（跳过该片段；指**数据引用了未编译进当前二进制的可选片段种类**，装载期报一条降级问题并跳过该片段——这不是「新增片段无需改代码」）；空内容包（允许空注册表启动）；作者备注为空 | 记警告继续；降级必须能被一个开关关闭，关闭后升为 fail-fast（C17） |

### 7.3 定位字段的统一形态

每条问题项包含三段（C18 已定形态，这里细化它的定位段）：**问题种类 + 定位 + 细节文本**；定位至少给出「包 id 或资产路径」与「定义 id（若已解析出）」两层，涉及片段时再加「片段种类」与「数组下标或字段名」。理由：一份定义资产里出现三个错误时，作者要能一次改三处；只有装载失败四个字会把修复变成猜测循环。

### 7.4 断言不是唯一防线

K10、K13 的断言在发布配置下都必须有返回值路径：冻结后写入返回失败结果码，tick 内装配返回失败结果码（C20）。

## 8 可迁移性注记

逐条判断：去掉 C++ 与 minEngine API 之后是否仍成立。

| 条目 | 判断 | 说明与条件 |
| --- | --- | --- |
| 定义基类只持身份 + 片段宿主 + 基属性表，不含业务与实例状态 | 成立 | 这是「常量数据 vs 运行期状态」的通用分离 |
| 片段身份是数据字段里的种类串，判别走种类表 | 成立 | 任何语言都能做字符串键查表；不依赖 RTTI 是这条设计的核心可迁移性 |
| 能力标签集 = 片段声明 tag 的并集（用 tag 而不是接口） | 条件成立 | 需要目标侧有「字符串词汇表 + 加载期校验」；没有 tag 系统时用自建词汇表模块，规则不变 |
| 覆盖项 = 种类 + 动作 + 参数，按种类唯一 | 成立 | 纯数据结构与集合运算 |
| 覆盖列表与 tag 增量表地址空间不相交 | 成立 | 这是设计纪律，不是引擎特性 |
| 定义之间无继承（第一版） | 成立 | 适用任何语言；代价是作者侧重复，收益是可判定性 |
| 注册表是纯对象、宿主是生命周期容器 | 条件成立 | 需要目标侧有服务/子系统容器；没有时用显式生命周期的容器，所有权规则不变 |
| 分片容器按 name 排序以获得确定性遍历 | 成立 | 任何语言都能做有序容器 |
| 闭包在装载定义前由索引算完 | 成立 | 需要「索引声明提供集合」这一数据形态；这是本文的设计选择，不是引擎能力 |
| 定义资产承载内容（双栖） | 条件成立 | 需要「可反射、可引用、可序列化的资产对象」；目标引擎若没有，用 JSON + 强类型加载器替代，本文的字段表与校验规则原样保留 |
| 键值对必须写成小对象而不是 struct | 不成立（作为约束） | 这是本宿主反射能力的限制（C9），迁移时应按目标引擎能力决定是否回到原生 struct；「基属性表是 tag 键值」这一意图成立 |
| 种类串与反射类名的一致性由装载期比对 | 条件成立 | 需要目标侧能在运行期取到对象的类型名；没有时改为「种类串 + 构造工厂表」双向登记，判据不变 |
| 冻结后写入即断言 | 成立 | 任何语言都能实现只读闸 |
| 片段对象引用解析必须先于片段校验 | 条件成立 | 需要「延迟解析对象引用」；没有时用两遍扫描（先建对象、再连引用），顺序要求不变 |

结论：没有一条**设计意图**依赖引擎特性；不成立的两条都是宿主反射能力的限制（嵌套形态与 struct 禁令），迁移时按目标引擎重新决定承载方式，其余规则原样保留。

## 11 待决问题

每条给选项、我的建议、什么会推翻建议。

**Q1 定义之间是否允许继承（第一版）。** 选项：(a) 不做，定义扁平，复用靠重复声明或复制片段对象；(b) 允许「基于某定义」并用覆盖项词汇产出有效装配集合；(c) 允许但只允许整片段级继承，不许字段级。
建议 (a)。理由：继承会立刻引入「哪些字段是作者写的、哪些是继承来的」这一元信息，而反射序列化不提供它；这正是 §4.9.2 拒绝字段级合并的同一个理由。第一版扁平，代价只是作者侧重复。
什么会推翻：若示例内容（Wave4）里出现「同一套数值要出现在五个以上定义里且必须单点修改」，(b) 的收益就超过成本，届时按 §4.11 的形态引入。

**Q2 种类串由数据写还是由类名推导。** 选项：(a) 数据写种类串，装载期与种类表声明的类名交叉比对（本文）；(b) 不写种类串，运行期用反射类名查表得到种类。
建议 (a)。理由：数据自描述（不打开代码就知道它是什么）、可 grep、可做「数据与代码不一致」的诊断；(b) 把类型名变成数据语义，重命名类即改内容语义，且跨语言迁移时类名不可移植。
什么会推翻：若反射层无法在运行期给出对象类名（只能编译期取类型名），(a) 的交叉比对就没法做，只能退到「装配时由工厂按种类建对象」——那样 (b) 也无从谈起，仍然是 (a)。

**Q3 能力查询的载体。** 选项：(a) 派生 tag 集合（本文）；(b) C++ 接口 + 向下转型；(c) 在种类表里挂一个枚举位掩码。
建议 (a)。理由：接口方案把内容语义压进内存布局，跨语言无对应物；(c) 会重新引入「加一种能力要改枚举」，正是总纲失败模式 2 的形态。
什么会推翻：若能力判定要求每帧对上千实例做，字符串集合查询成为热点，(c) 的位掩码可作为能力标签集的内部表示（对外仍是 tag 查询），这属于实现优化，不改契约。

**Q4 替换动作的参数是整片段还是字段子集。** 选项：(a) 整片段，未填字段取类型默认值（本文）；(b) 字段子集对象，只有出现的字段被覆盖。
建议 (a)。理由：字段子集需要「作者是否写过该字段」的元信息，反射不提供；(b) 只能靠哨兵近似，与 C14 冲突，并且正是两套 override 语义打架的来源。需要字段级精度时改走 tag 键属性。
什么会推翻：若出现「片段有二十个字段，实例只想改其中一个」的高频场景，作者成本会很高；届时把该字段提升为 tag 键属性是正解，而不是引入字段子集。

**Q5 注册表遍历顺序。** 选项：(a) 按 kind 再按 name 字典序（本文）；(b) 按装载顺序（插入顺序）。
建议 (a)。理由：装载顺序无关性要有可断言的输出；插入顺序会让「摘要相同」这条验收依赖装载顺序本身。
什么会推翻：若某些逻辑确实需要「内容包内声明顺序」（例如默认选中项按作者顺序），那应当是数据里的一个显式排序字段，而不是容器的遍历顺序。

**Q6 包索引是否声明提供集合。** 选项：(a) 声明，并做与注册结果的交叉核对（本文）；(b) 不声明，闭包只在装载后靠探测判定。
建议 (a)。理由：跨包引用缺包时，只有 (a) 能在装载前给出「你缺哪个包」；重复 id 也能从「谁先装载谁赢」变成静态判定。代价是索引漂移，(a) 已用交叉核对对治。
什么会推翻：若包索引的维护成本被证明高于收益（例如定义频繁增删而索引经常忘改），可退到 (b) 并接受「跨包引用只能事后诊断」。

**Q7 仅大小写不同的两个 id 是否允许。** 选项：(a) 允许（按 C1 字面，视为两个 id）；(b) 拒绝（视为冲突，fail-fast）。
建议 (b)。理由：仅大小写不同的两个 id 对人眼不可辨，是资源问题与环境问题的常见来源；拒绝成本是一个比较函数。
什么会推翻：若作者明确要保留大小写作为种类内命名风格（两种风格并存），则 (a)，并在装载期对仅大小写不同的组合记一条警告。

**Q8 定义版本字段是否保留。** 选项：(a) 保留为只记录不分支的整型（本文）；(b) 不加，等真需要诊断再加。
建议 (a)。理由：装载问题消息里带上「定义修订号」能让作者定位到具体一次编辑；成本是一个整型字段与一条 grep 判据（K19）。
什么会推翻：若实现时发现「只记录不分支」的字段会被顺手用来做迁移分支（这正是 C15 禁止的），不如 (b)，把版本信息留给资产系统自己的元数据。

**Q9 效果定义族不靠片段装配（本轮裁定，按此执行）。** 裁定：EffectDef 的字段归 CORE-F02，本文只登记「效果」这个 kind 名并把该族准入表置空；「效果定义用片段装配修饰器」的设计删除，理由是它会把 F02 的类型拉进本文。执行后的余留：F02 文档里仍有一处把「图节点 payload」与物品并列称作一个定义族，与 F05 K7（payload 内联于节点、不是独立资产、不是 ContentId 引用）以及本文修订后的族表不一致，需 F02 侧改那一处括注；本文已按裁定只为「图定义族（kind = graph）」留族。
